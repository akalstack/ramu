# Learning and context efficiency

Ramu shares durable memories and reusable procedures across providers. Memory stays in the existing local SQLite store; generated procedures are managed separately from installed skills.

## Automatic learning

**Settings → Memory & skills → Learning & skills** offers Off, Review first (default for a new profile), and Automatic (opt in). Save changes before running maintenance. Review-first still uses model tokens to prepare proposals; it waits for you to apply them. A profile made by the release where Automatic was the default keeps Automatic until you change it, and a mode you chose is never overridden at startup. (A `review` choice that release had already moved to Automatic cannot be recovered.)

After a substantive turn finishes successfully, Ramu queues an idle review. Eligibility checks tool activity in that completed turn, rather than earlier turns. Greetings, acknowledgements, and connectivity tests with only an incidental tool call are skipped. Cancelled or failed turns are excluded. Background reviews wait for foreground threads and memory cleanup, have a one-minute settling delay, and share a rolling daily review limit (default five). **Run learning maintenance** bypasses the settling delay, while respecting activity and daily limits. Choose a maintenance model from your saved model steps, or use the source thread's model. The selected maintenance model also applies to memory cleanup; the review count limits learning reviews, while memory cleanup retains its existing daily schedule.

The model proposes durable memories, reusable skills, updates/consolidations of existing skills, and a session checkpoint. Proposals include their source thread and event boundary. A checkpoint records thread-local progress and unfinished verification; it does not declare the whole task complete. Reviews can leave the checkpoint empty when there is no meaningful progress to preserve. Durable preferences and reusable procedures belong in memories and skills. Saved checkpoints are available from **Session checkpoint** in the thread header, with their timestamp and event boundary; Settings retains pending checkpoint text for approval and the durable learning review history. Current user instructions and live evidence take precedence when memories or checkpoints disagree. Review the proposed text, apply it, dismiss it, or retry a failed/outdated review. Jobs survive service restarts and an already-applied job cannot write twice. Off pauses learning; existing memory cleanup has its own switch.

Only Ramu-generated, self-contained Markdown skills are automatically maintained. Ramu does not rewrite installed provider/plugin/user skills or their scripts. Managed skills appear in the thread's skill picker. Every provider loads them through its own skill system: Ramu keeps a per-scope export folder under the profile's `skills/export/` (global skills, plus the project's when a thread has one; the project's wins on a name clash) with each skill named `ramu-<name>`, and points the provider at it for that thread only. Claude Code loads it as the `ramu-managed` plugin, Codex adds it as a skill root of its own app server, and OpenCode lists it in its inline `skills` setting. Nothing is written to your own skill folders or provider config. Only active skills in the thread's scope are exported; disabled and archived ones disappear from the folder right away and from running providers when they next rescan skills, which is at the latest the next thread.

**Cursor and Antigravity** cannot be pointed at another folder for one thread, and only scan fixed skill folders, so Ramu symlinks (a junction on Windows) each exported `ramu-<name>` folder into the folder the provider scans in the thread's working directory: `<cwd>/.cursor/skills` for Cursor and `<cwd>/.gemini/skills` for Antigravity. Project and global skills both appear there, as in the export. For a thread without a project the directory is Ramu's own, and links are never written under your home folder. The links are created when a thread starts and updated whenever a skill changes, and stale ones are removed the same way. In a Git repository the entries are added to `.git/info/exclude` (never `.gitignore`), so the project shows no changes and tracked files are never touched. Ramu only creates or removes links whose name starts with `ramu-` and whose target is inside its export folder; a real file or folder, or a link pointing anywhere else, is left alone and logged. Links are not followed when removed, and a folder that is itself a link is never written through. Links and the `.cursor`/`.gemini` folder Ramu had to create stay behind when a project is removed from Ramu or Ramu is uninstalled; they are harmless but dangling, and cleaning them up is a follow-up. Provider-native loading does not report reads, so no provider records skill reads. Pin, disable, archive, restore, and inspect/restore revisions in Settings → Memory & skills. Unpinned skills are archived once they have gone the configured number of days without an update (Ramu cannot see when a provider loads a skill), so pin skills you rely on that rarely change. Consolidations require a surviving skill in the same scope and reject concurrent edits. Copies of generated `SKILL.md` files live under the profile's `skills/<id>/` directory; database revisions remain authoritative.

### Checkpoint refresh near a limit

When a provider's plan usage crosses **When to switch** (Settings → Access & Fallback; not when it is "only at the limit", and not once the provider is limited), Ramu writes a fresh checkpoint for idle threads on that provider whose checkpoint is behind their latest reviewable turn and that would switch automatically. It is an add-on: the handoff stays deterministic and never waits for it, and a failed call leaves the older checkpoint as it was. It follows the learning rules: nothing runs while Learning is off or while any thread is working or waiting for you, one thread is refreshed per five-second tick (newest first), each refresh counts as one of the daily reviews and stops at the budget, and a turn is tried once, also across a restart. In Automatic mode a review already queued for that turn is run at once instead. Unlike a review, a refresh proposes no memories or skills, so in Review first mode its checkpoint is saved without approval: a checkpoint is thread-local progress, is checked for credentials, and is marked historical when a handoff uses it. Background calls already route away from a provider over the threshold when automatic fallback is on, so the refresh does not spend the nearly exhausted login.

Reviews never spend tokens on input they have already seen. Before building a prompt, Ramu fingerprints the turn's trace, the thread's checkpoint, the memories and skills in scope, and the maintenance model. A review with nothing to read, or with the same fingerprint as the thread's last successful one, is marked dismissed with "Skipped: nothing to review" or "Skipped: nothing changed", does not use a daily review, and is remembered across restarts. A failed review records nothing and retries. **Retry** always asks the model again. Memory cleanup applies the same rule per scope: an automatic pass skips scopes whose notes and model are unchanged since the last pass, while **Run now** always asks.

**Credentials are refused.** A proposal is checked field by field before it can be applied, in either mode, and the same check guards memory writes, skill edits and the text sent to the learning and summary models (where credentials are replaced by `[redacted]`). It recognises known formats (Anthropic and OpenAI `sk-`, GitHub, GitLab, Slack, AWS, Google, Stripe, npm and SendGrid keys, JSON web tokens, private-key blocks, `Bearer` tokens, URLs with a password), `name=value` assignments such as `AWS_SECRET_ACCESS_KEY=…` or `password: …` (placeholders such as `$VAR` or `<token>` are fine), and long random-looking tokens (32 or more characters with letters of both cases and digits). Commit hashes, digests, UUIDs, paths and long identifiers are not flagged. A proposal that fails the check ends **failed** with the reason and nothing is written; this is a safety net, not a guarantee, so keep secrets out of threads.

Model-generated learning can be wrong. Review-first makes changes inspectable before they affect later work. Memory cleanup and learning cannot rewrite or archive user-confirmed or essential memories. Conflicting evidence must be recorded separately. The Memory page compares earlier text with the current note and restores a revision as a new user-confirmed edit.

## What Ramu learned

Reading every saved memory and skill one by one does not scale, so Ramu can write a short summary of what automatic learning did. It is an AI-written, **read-only** account, grouped by theme in plain language: new memories, new skills, merged and cleaned up, archived, and anything **worth a look**.

**Settings → Memory & skills → What Ramu learned** sets how often it is written (Off, Daily or Weekly, default Weekly), whether memories and skills are included, whether the latest summary shows on Home, and a **Run now** button. The history of summaries is listed below the controls. Save changes before running. It uses the same background model as learning (**Background model**) and the same rules: it waits for foreground threads, learning reviews and memory cleanup, and a one-minute settling delay applies to scheduled runs. **Run now** skips the delay and the interval but still waits for foreground threads.

**What is summarized.** The change log comes from history Ramu already keeps: memory revision history, skill revisions and learning jobs since the previous summary. Nothing new is tracked, except that skill revisions now record who made them (learning, cleanup, you, or a review thread). When nothing was learned in the period, the run is skipped before any prompt is built, so it costs nothing, even for Run now, which then says "Nothing new since <date>". Scheduled runs also use the shared background input gate: if the change log and the settings that shape the summary (included kinds and model) match the last successful summary, no model is called. Run now forces a run when there is something to summarize, and a failed run records nothing, so it retries. Changes you made yourself are only counted in a short "changed by you" line, never reported as learned, and the model never sees the text of notes you wrote or confirmed. The summary is data for you to read; links to items and the theme headings come from the change log, not from the model.

**Reading a summary.** Home shows the latest one with an unread dot, and a notification appears when a new one is ready. Opening it shows the summary, the linked memories and skills (a click opens them in Settings → Memory & skills), and the review threads started from it under **Discussed in thread**. **Looks good** marks it dismissed when nothing needs changing; it stays in the history list.

**Discussing it.** Typing in the box at the bottom and sending starts a regular thread with no project, shown under Threads with a small **Review** label. The thread is seeded with the summary text and item ids (as data, not instructions) and linked back from the summary. A summary can have several discussions. The thread runs in the most restrictive access mode and its Ramu connection exposes only memory and skill tools: no file, shell, Git, schedule or other Ramu tools. For Claude Code the built-in tools are also turned off; other providers rely on their own sandbox for the same guarantee, so keep that in mind when choosing a provider for review threads.

The thread can read any memory (`memory_search`, `memory_read`) and managed skill (`skill_inspect`), and edit them with `memory_update`, `memory_archive`, `memory_restore`, `memory_merge`, `skill_update`, `skill_archive` and `skill_restore`. Edits apply immediately and each one is a normal revision you can restore from the Memory page or the skill history. The usual protection applies by default: memories you wrote (user-confirmed) or marked essential, pinned skills, and installed provider, plugin or user skills are left alone by the AI. These protections are the default, not absolute: when your own latest message in the thread explicitly asks to change a protected item, the AI may do it by calling the tool with `userRequested` and a short quote of your words in `userRequest`. It must never set this on its own initiative or because the summary suggested it; without the flag, a protected item is refused and the thread tells you to edit it yourself or asks you. A protected memory stays protected after such an edit, and a pinned skill stays pinned. Installed skills can be rewritten this way (not archived): the previous `SKILL.md` text is kept as a revision, and `skill_restore` writes it back (keeping a copy of what it replaces). The transcript marks these rows "Protected item changed at your request" with your quoted words. Edits made in review threads are counted separately in the next summary.

## Ramu tool search

With **Settings → Threads → Ramu tool search** enabled, essential conversation controls remain directly exposed. Optional Ramu tools are discovered using `tool_search`, then called using `tool_invoke` with the returned schema. This searches only tools exposed by Ramu, including newly registered capabilities. It uses lexical matching and aliases, with no embeddings or vector database. It does not search provider-native tools or external MCP catalogs.

Invocation validates the original schema and runs the original scope checks. Tool exposure mode is fixed for a provider connection; changing the preference applies to new connections. The portable search/invocation interface works without native provider deferred-tool support.

## Continuity

Memory supports concise search followed by `memory_read` for full text and sources. Approved session checkpoints can reduce older tool output in same-thread provider handoffs while retaining original user requirements and recent events. `session_recall` retrieves original events by sequence number when a checkpoint omits necessary evidence. Files should still be inspected live with the provider's ordinary tools.

## Recall previous threads

**Settings → Memory & skills → Recall past conversations** is on by default and independent of automatic learning. Save to apply. Turning it off blocks new cross-thread searches and recalls immediately, including tools discovered earlier, while keeping your stored history and same-thread recall available.

Ask the agent about earlier work, for example, “How did we fix authentication last month?” `session_search` searches stored user and assistant prose across providers using local SQLite full-text search, without model calls for indexing or retrieval. Existing messages are indexed on upgrade; edits and deletions update the index. Provider reasoning, tool payloads, and helper transcripts are excluded from search.

Search defaults to the current project. `scope: "all"` explicitly searches all projects on this workspace server; project-free threads otherwise search only project-free history. Results include excerpts, thread titles, message sequence numbers and source links. On desktop, a source link opens and highlights the original message. The agent can pass the returned `sessionId` and `seq` as `startSeq` to `session_recall` to read surrounding events, using the same scope rules. Search has `offset`/`nextOffset` pagination; recall returns `nextSeq` for another page. Reasoning is omitted from recall. Retrieved history is evidence, not new instructions, and current files still need checking.

## Tool-aware skills

**Settings → Memory & skills → Tool-aware skills** is on by default and independent of automatic learning. Save to apply. Turning it off withholds conditional skills from the picker and provider exports and blocks new compatibility resolutions; ordinary skills stay available. Stored skills and revisions are kept, and enabling it restores the conditional exports. Running providers refresh their native skill lists when they next rescan, at the latest in the next provider session.

Skills can declare tools or toolsets they require, and tools whose absence makes them useful as a fallback. Installed skills accept these fields under `metadata.ramu`; existing `metadata.hermes` fields are also recognized:

```yaml
metadata:
  ramu:
    requires_tools: [shell]
    fallback_for_tools: [browser_open]
```

This example offers a shell procedure when `browser_open` is missing. `requires_toolsets` and `fallback_for_toolsets` work the same way with explicitly verified labels such as `terminal` or `browser`. Tool names match exactly, so use the names exposed by the runtime. All requirements must be present; a fallback is skipped if any of its listed alternatives is available. Skills without conditions keep their existing behavior.

The agent uses `skill_resolve` with its current `availableTools` and `availableToolsets` to list compatible skills, then passes a skill `id` to retrieve its procedure and supporting-file directory. Missing-tool fallbacks require `inventoryComplete: true`; otherwise Ramu withholds them because a tool may still exist in a deferred catalog. Ramu does not guess native tools from provider names. Compatibility uses the agent-reported inventory and does not grant permissions or execute anything.

Conditional skills load through a small provider-native wrapper that asks the agent to resolve compatibility before using the procedure. Wrappers stay stable when different providers share a checkout, and require a fresh resolution after a provider or tool change. Project skill precedence, disabled/archived status, and installed-skill protections still apply. Learned skills can carry the same optional `activation` fields; review threads can inspect or update those fields through `skill_inspect` and `skill_update` (`activation: null` clears an override).

## Validation

`pnpm check` covers shared contracts, queue persistence, review budgets, stale revisions, protected memory, tool invocation validation, and provider guidance. Add focused unit or integration tests for future learning behavior changes. After building, `pnpm test:desktop-smoke` checks desktop startup with an isolated profile and simulated providers. Real-provider quality needs opt-in live evaluations; simulated tests establish application behavior.

## Installing external skills

Ask the agent to find a skill or install one from a repository, URL, git address or local folder. `skill_find` wraps the skills.sh search CLI; `skill_install` asks whether the skill belongs to this project or all projects when you have not specified a scope. It stages one skill using pinned `skills@1.7.2` with telemetry disabled, then shows its source, description, scope and file list for your approval. Scripts require a second approval and are skipped by default. Ramu copies approved files and never executes skill scripts during installation.

Staging runs in a temporary directory, never your project or a provider’s home folder. Symlinks, unsafe paths and special files are rejected. The import limits are 10 MiB per file, 25 MiB total and 1000 entries. Local sources are checked for symlinks before the CLI copies them. A preview expires after 30 minutes or a service restart; an update also refuses to overwrite a skill changed while approval was pending.

**Settings → Memory & skills → Installed skills** accepts a source link or absolute local path and optional skill name. Preview, inspect the instructions/files, and approve installation. Each card shows its source and scope, with Update, Disable/Enable, Move and Remove controls. Source updates show added, changed and removed files before approval. Installed skills are excluded from automatic learning edits and automatic archiving.

Chat tools include `skill_list`, `skill_inspect`, `skill_update_from_source`, `skill_disable`, `skill_move` and `skill_remove`. Updates, scope moves and removal ask for confirmation. User-scoped skills are available in every project; project skills stay in that project. Both use Ramu’s existing managed export for Claude Code, Codex, OpenCode, Cursor and Antigravity, including approved reference files. Disabling/removing a skill updates the catalog and exports; the next provider session sees the new list.

Node.js and `npx` are required only for finding, staging and source updates. If they are missing, the tool and Settings link to [Node.js installation](https://nodejs.org/en/download). Existing skills and the rest of Ramu continue working.
