# Learning and context efficiency

Ramu shares durable memories and reusable procedures across providers. Memory stays in the existing local SQLite store; generated procedures are managed separately from installed skills.

## Response styles

Choose a global style in **Settings → Chats → Response style**, or override it from a chat's composer: Default, Concise, Detailed, ADHD-friendly, Caveman, or Custom. Custom accepts presentation instructions and an optional installed skill name, resolved in the chat's scope. A missing skill is skipped; custom text still applies.

ADHD-friendly leads with the action or answer, keeps steps short, and avoids tangents. Caveman uses telegraphic prose. Exact code, commands, paths, structured output, material failures, and uncertainty must remain intact. Explicit user requests take precedence. Styles guide generation rather than shortening the answer after tokens have already been spent. Changes take effect on the next turn.

## Automatic learning

**Settings → Memory & skills → Learning & skills** offers Off, Review first, and Automatic (default). Save changes before running maintenance. Review-first still uses model tokens to prepare proposals; it waits for you to apply them.

After a substantive turn finishes successfully, Ramu queues an idle review. Eligibility checks tool activity in that completed turn, rather than earlier turns. Greetings, acknowledgements, and connectivity tests with only an incidental tool call are skipped. Cancelled or failed turns are excluded. Background reviews wait for foreground chats and memory cleanup, have a one-minute settling delay, and share a rolling daily review limit (default five). **Run learning maintenance** bypasses the settling delay, while respecting activity and daily limits. Choose a maintenance model from your saved model steps, or use the source chat's model. The selected maintenance model also applies to memory cleanup; the review count limits learning reviews, while memory cleanup retains its existing daily schedule.

The model proposes durable memories, reusable skills, updates/consolidations of existing skills, and a session checkpoint. Proposals include their source chat and event boundary. A checkpoint records chat-local progress and unfinished verification; it does not declare the whole task complete. Reviews can leave the checkpoint empty when there is no meaningful progress to preserve. Durable preferences and reusable procedures belong in memories and skills. Saved checkpoints are available from **Session checkpoint** in the chat header, with their timestamp and event boundary; Settings retains pending checkpoint text for approval and the durable learning review history. Current user instructions and live evidence take precedence when memories or checkpoints disagree. Review the proposed text, apply it, dismiss it, or retry a failed/outdated review. Jobs survive service restarts and an already-applied job cannot write twice. Off pauses learning; existing memory cleanup has its own switch.

Only Ramu-generated, self-contained Markdown skills are automatically maintained. Ramu does not rewrite installed provider/plugin/user skills or their scripts. Managed skills appear in the chat's skill picker. Every provider loads them through its own skill system: Ramu keeps a per-scope export folder under the profile's `skills/export/` (global skills, plus the project's when a chat has one; the project's wins on a name clash) with each skill named `ramu-<name>`, and points the provider at it for that chat only. Claude Code loads it as the `ramu-managed` plugin, Codex adds it as a skill root of its own app server, and OpenCode lists it in its inline `skills` setting. Nothing is written to your own skill folders or provider config. Only active skills in the chat's scope are exported; disabled and archived ones disappear from the folder right away and from running providers when they next rescan skills, which is at the latest the next chat.

**Cursor and Antigravity** cannot be pointed at another folder for one chat, and only scan fixed skill folders, so Ramu symlinks (a junction on Windows) each exported `ramu-<name>` folder into the folder the provider scans in the chat's working directory: `<cwd>/.cursor/skills` for Cursor and `<cwd>/.gemini/skills` for Antigravity. Project and global skills both appear there, as in the export. For a chat without a project the directory is Ramu's own, and links are never written under your home folder. The links are created when a chat starts and updated whenever a skill changes, and stale ones are removed the same way. In a Git repository the entries are added to `.git/info/exclude` (never `.gitignore`), so the project shows no changes and tracked files are never touched. Ramu only creates or removes links whose name starts with `ramu-` and whose target is inside its export folder; a real file or folder, or a link pointing anywhere else, is left alone and logged. Links are not followed when removed, and a folder that is itself a link is never written through. Links and the `.cursor`/`.gemini` folder Ramu had to create stay behind when a project is removed from Ramu or Ramu is uninstalled; they are harmless but dangling, and cleaning them up is a follow-up. Provider-native loading does not report reads, so no provider records skill reads. Pin, disable, archive, restore, and inspect/restore revisions in Settings → Memory & skills. Unpinned skills are archived once they have gone the configured number of days without an update (Ramu cannot see when a provider loads a skill), so pin skills you rely on that rarely change. Consolidations require a surviving skill in the same scope and reject concurrent edits. Copies of generated `SKILL.md` files live under the profile's `skills/<id>/` directory; database revisions remain authoritative.

Reviews never spend tokens on input they have already seen. Before building a prompt, Ramu fingerprints the turn's trace, the chat's checkpoint, the memories and skills in scope, and the maintenance model. A review with nothing to read, or with the same fingerprint as the chat's last successful one, is marked dismissed with "Skipped: nothing to review" or "Skipped: nothing changed", does not use a daily review, and is remembered across restarts. A failed review records nothing and retries. **Retry** always asks the model again. Memory cleanup applies the same rule per scope: an automatic pass skips scopes whose notes and model are unchanged since the last pass, while **Run now** always asks.

Model-generated learning can be wrong. Review-first makes changes inspectable before they affect later work. Memory cleanup and learning cannot rewrite or archive user-confirmed or essential memories. Conflicting evidence must be recorded separately. The Memory page compares earlier text with the current note and restores a revision as a new user-confirmed edit.

## What Ramu learned

Reading every saved memory and skill one by one does not scale, so Ramu can write a short summary of what automatic learning did. It is an AI-written, **read-only** account, grouped by theme in plain language: new memories, new skills, merged and cleaned up, archived, and anything **worth a look**.

**Settings → Memory & skills → What Ramu learned** sets how often it is written (Off, Daily or Weekly, default Weekly), whether memories and skills are included, whether the latest summary shows on Home, and a **Run now** button. The history of summaries is listed below the controls. Save changes before running. It uses the same background model as learning (**Background model**) and the same rules: it waits for foreground chats, learning reviews and memory cleanup, and a one-minute settling delay applies to scheduled runs. **Run now** skips the delay and the interval but still waits for foreground chats.

**What is summarized.** The change log comes from history Ramu already keeps: memory revision history, skill revisions and learning jobs since the previous summary. Nothing new is tracked, except that skill revisions now record who made them (learning, cleanup, you, or a review chat). When nothing was learned in the period, the run is skipped before any prompt is built, so it costs nothing, even for Run now, which then says "Nothing new since <date>". Scheduled runs also use the shared background input gate: if the change log and the settings that shape the summary (included kinds and model) match the last successful summary, no model is called. Run now forces a run when there is something to summarize, and a failed run records nothing, so it retries. Changes you made yourself are only counted in a short "changed by you" line, never reported as learned, and the model never sees the text of notes you wrote or confirmed. The summary is data for you to read; links to items and the theme headings come from the change log, not from the model.

**Reading a summary.** Home shows the latest one with an unread dot, and a notification appears when a new one is ready. Opening it shows the summary, the linked memories and skills (a click opens them in Settings → Memory & skills), and the review chats started from it under **Discussed in chat**. **Looks good** marks it dismissed when nothing needs changing; it stays in the history list.

**Discussing it.** Typing in the box at the bottom and sending starts a regular chat with no project, shown under Chats with a small **Review** label. The chat is seeded with the summary text and item ids (as data, not instructions) and linked back from the summary. A summary can have several discussions. The chat runs in the most restrictive access mode and its Ramu connection exposes only memory and skill tools: no file, shell, Git, schedule or other Ramu tools. For Claude Code the built-in tools are also turned off; other providers rely on their own sandbox for the same guarantee, so keep that in mind when choosing a provider for review chats.

The chat can read any memory (`memory_search`, `memory_read`) and managed skill (`skill_inspect`), and edit them with `memory_update`, `memory_archive`, `memory_restore`, `memory_merge`, `skill_update`, `skill_archive` and `skill_restore`. Edits apply immediately and each one is a normal revision you can restore from the Memory page or the skill history. The usual protection applies by default: memories you wrote (user-confirmed) or marked essential, pinned skills, and installed provider, plugin or user skills are left alone by the AI. These protections are the default, not absolute: when your own latest message in the chat explicitly asks to change a protected item, the AI may do it by calling the tool with `userRequested` and a short quote of your words in `userRequest`. It must never set this on its own initiative or because the summary suggested it; without the flag, a protected item is refused and the chat tells you to edit it yourself or asks you. A protected memory stays protected after such an edit, and a pinned skill stays pinned. Installed skills can be rewritten this way (not archived): the previous `SKILL.md` text is kept as a revision, and `skill_restore` writes it back (keeping a copy of what it replaces). The transcript marks these rows "Protected item changed at your request" with your quoted words. Edits made in review chats are counted separately in the next summary.

## Ramu tool search

With **Settings → Chats → Ramu tool search** enabled, essential conversation controls remain directly exposed. Optional Ramu tools are discovered using `tool_search`, then called using `tool_invoke` with the returned schema. This searches only tools exposed by Ramu, including newly registered capabilities. It uses lexical matching and aliases, with no embeddings or vector database. It does not search provider-native tools or external MCP catalogs.

Invocation validates the original schema and runs the original scope checks. Tool exposure mode is fixed for a provider connection; changing the preference applies to new connections. The portable search/invocation interface works without native provider deferred-tool support.

## Input compression and continuity

**Settings → Chats → Input compression** offers Off, Balanced (default), and Aggressive. It compacts large textual results from Ramu tools before the provider receives them. Omitted content is marked, and `tool_result_read` retrieves exact character ranges from the original result within the same chat. Error results pass through intact. Stored originals remain available for the lifetime of the chat.

The composer shows a character-based estimate of tokens avoided for compacted Ramu output. It excludes detail rereads, provider cache effects, and provider-native operations; provider usage remains the billing observation.

Memory supports concise search followed by `memory_read` for full text and sources. Approved session checkpoints can reduce older tool output in same-chat provider handoffs while retaining original user requirements and recent events. `session_recall` retrieves original events by sequence number when a checkpoint omits necessary evidence. Files should still be inspected live with the provider's ordinary tools.

The optional **RTK command tool** requires RTK installed on the server's PATH. It exposes `rtk_run` only to full-access chats, runs argument arrays without a shell in the chat working directory, and reports exit status/errors. RTK itself filters the underlying command output. Ramu does not install global hooks or alter native provider shell tools. Native provider history compaction also remains controlled by the provider.

## Validation

`pnpm check` covers shared contracts, queue persistence, review budgets, stale revisions, protected memory, exact output recovery, tool invocation validation, and provider guidance. `pnpm test:learning` runs an isolated Electron journey with simulated providers, screenshots, settings persistence, approval, pinned skills, memory revision restoration, and restart checks. `pnpm test:e2e` covers the wider desktop journey. Real-provider quality and token savings need opt-in live evaluations; simulated tests establish application behavior.
