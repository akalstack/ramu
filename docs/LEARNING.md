# Learning and context efficiency

Ramu shares durable memories and reusable procedures across providers. Memory lives in the local SQLite store; generated procedures are managed separately from installed skills.

## Automatic learning

**Settings → Memory & skills → Learning & skills** offers Off, Review first (default for a new profile) and Automatic. Save changes before running maintenance. Review first still spends model tokens to prepare proposals, then waits for you. Off pauses learning; memory cleanup has its own switch.

After a substantive successful turn Ramu queues an idle review. Greetings, acknowledgements, connectivity tests with only an incidental tool call, and cancelled or failed turns are skipped; eligibility looks only at that turn's tool activity. Unstarted reviews of one thread merge into one covering its latest turn (also after a restart); proposals awaiting approval stay separate. Background reviews wait for foreground threads and memory cleanup, settle for a minute, and share a rolling daily limit (default five). **Run learning maintenance** skips the settling delay but respects activity and the daily limit. Choose the maintenance model from your saved model steps or use the source thread's; it also applies to memory cleanup, whose own daily schedule is unchanged.

The model proposes durable memories, reusable skills, updates and consolidations of existing skills, and a session checkpoint, each with its source thread and event boundary. A checkpoint records thread-local progress and unfinished verification, never that the whole task is done, and may be empty. Saved checkpoints open from **Session checkpoint** in the thread header; Settings holds pending checkpoint text and the review history. Current user instructions and live evidence outrank memories and checkpoints. Apply, dismiss or retry a proposal. Jobs survive restarts and an applied job cannot write twice.

**Skip rules.** Before building a prompt Ramu fingerprints the turn's trace, the thread's checkpoint, the memories and skills in scope and the maintenance model. A review with nothing to read, or the same fingerprint as the thread's last successful one, is dismissed ("Skipped: nothing to review" / "nothing changed"), uses no daily review and is remembered across restarts. Failed reviews record nothing and retry; **Retry** always asks the model. Memory cleanup applies the same rule per scope, and **Run now** always asks.

**Credentials are refused.** Every proposal is checked field by field before it can be applied, in either mode, and the same check guards memory writes, skill edits and the text sent to the learning and summary models (credentials become `[redacted]`). It recognizes known key formats (Anthropic, OpenAI, GitHub, GitLab, Slack, AWS, Google, Stripe, npm, SendGrid), JSON web tokens, private-key blocks, `Bearer` tokens, URLs with passwords, `name=value` secret assignments (placeholders like `$VAR` or `<token>` pass) and long random-looking tokens (32+ characters with mixed case and digits). Hashes, UUIDs, paths and long identifiers are not flagged. A failing proposal ends **failed** and nothing is written. It is a safety net, not a guarantee; keep secrets out of threads.

Model-generated learning can be wrong. Learning and cleanup never rewrite or archive user-confirmed or essential memories, and conflicting evidence is recorded separately. The Memory page compares earlier text with the current note and restores a revision as a new user-confirmed edit.

### Managed skills

Only Ramu-generated, self-contained Markdown skills are maintained automatically; installed provider, plugin and user skills and their scripts are never rewritten. Managed skills appear in the thread's skill picker and load through each provider's own skill system. Ramu keeps a per-scope export under the profile's `skills/export/` (global skills plus the project's, which wins on a name clash), names each skill `ramu-<name>` and points the provider at it for that thread only: Claude Code loads it as the `ramu-managed` plugin, Codex adds a skill root to its app server, OpenCode lists it in its inline `skills` setting. Nothing is written to your own skill folders or provider config. Only active skills in scope are exported; disabled and archived ones drop out at the provider's next rescan (at the latest the next thread).

**Cursor and Antigravity** only scan fixed folders, so Ramu symlinks (a junction on Windows) each exported `ramu-<name>` folder into `<cwd>/.cursor/skills` or `<cwd>/.gemini/skills` of the thread's working directory (Ramu's own directory when the thread has no project; never your home folder). Links are created at thread start and updated when a skill changes. In a Git repository they are added to `.git/info/exclude`, never `.gitignore`. Ramu only creates or removes links named `ramu-*` that point into its export folder; anything else is left alone and logged, and links are never followed when removing. Links and any folder Ramu had to create remain if a project is removed or Ramu uninstalled; they are harmless but dangling.

Pin, disable, archive, restore and inspect revisions in Settings → Memory & skills. Unpinned skills are archived after the configured number of days without an update (Ramu cannot see when a provider loads one), so pin rarely changed skills you rely on. Consolidations need a surviving skill in the same scope and reject concurrent edits. Database revisions are authoritative; copies of `SKILL.md` live under `skills/<id>/`.

### Checkpoint refresh near a limit

When a provider's plan usage crosses **When to switch** (Settings → Models; not "only at the limit", and not once limited), Ramu writes a fresh checkpoint for each idle thread on that provider that would switch automatically and whose checkpoint is behind its latest reviewable turn. The handoff stays deterministic and never waits for it, and a failed call leaves the old checkpoint. Learning rules apply: nothing runs while Learning is off or any thread is working or waiting for you; one thread refreshes per five-second tick (newest first); each refresh uses one daily review; a turn is tried once, even across restarts. In Automatic mode an already queued review for that turn runs instead. A refresh proposes no memories or skills, so in Review first mode its checkpoint is saved without approval (it is thread-local, credential-checked and marked historical in handoffs). Background calls already avoid a provider over the threshold when fallback is on.

## What Ramu learned

An AI-written, **read-only** summary of what automatic learning did, grouped by theme: new memories, new skills, merged and cleaned up, archived, and anything **worth a look**.

**Settings → Memory & skills → What Ramu learned** sets frequency (Off, Daily or Weekly; default Weekly), whether memories and skills are included, and **Run now**; past summaries are listed below. Save before running. It uses the same **Background model** and waits for foreground threads, learning reviews and memory cleanup; scheduled runs also settle for a minute, while **Run now** skips the delay and interval.

- **Input:** the change log from history Ramu already keeps (memory and skill revisions, learning jobs since the previous summary; skill revisions also record who made them). With nothing learned the run is skipped before any prompt, even for Run now ("Nothing new since <date>"). Scheduled runs also skip when the change log and shaping settings match the last successful summary; Run now forces a run when there is something to say, and a failed run records nothing. Your own changes appear only as a short "changed by you" line, and the model never sees notes you wrote or confirmed. Links and theme headings come from the change log, not the model.
- **Reading:** Inbox lists summaries with an unread dot and notifies when one is ready. Opening one shows the text, linked memories and skills (opening in Settings) and the review threads under **Discussed in thread**. **Looks good** dismisses it but keeps it in history.
- **Discussing:** typing in the box at the bottom starts a regular project-free thread with a **Review** label, seeded with the summary and item IDs as data and linked back. A summary can have several. The thread uses the most restrictive access mode and its Ramu connection exposes only memory and skill tools; Claude Code's built-in tools are also off, while other providers rely on their own sandbox.
  - It can read (`memory_search`, `memory_read`, `skill_inspect`) and edit (`memory_update`, `memory_archive`, `memory_restore`, `memory_merge`, `skill_update`, `skill_archive`, `skill_restore`); each edit is a normal revision you can restore.
  - User-confirmed or essential memories, pinned skills and installed skills are protected by default. Only when your own latest message explicitly asks to change one may the AI pass `userRequested` with a quote of your words in `userRequest`; it must never do so on its own initiative. Without it the tool refuses. A protected memory stays protected and a pinned skill pinned after such an edit. Installed skills can be rewritten (not archived) with the previous `SKILL.md` kept as a revision, and the transcript marks it "Protected item changed at your request". These edits are counted separately in the next summary.

## Ramu tool search

With **Settings → Threads → Ramu tool search** on, essential conversation controls stay directly exposed and other Ramu tools are found with `tool_search` (lexical matching and aliases; no embeddings; Ramu's own tools only, not provider-native tools or external MCP catalogs) and called with `tool_invoke` and the returned schema. Invocation validates the original schema and runs the original scope checks. The mode is fixed per provider connection; changes apply to new connections.

## Continuity and recall

`memory_read` returns full text and sources after a concise search. Approved session checkpoints can shrink older tool output in same-thread handoffs while keeping the original user requirements and recent events; `session_recall` fetches original events by sequence number when a checkpoint omits needed evidence. Files should still be inspected live.

**Settings → Memory & skills → Recall past conversations** is on by default and independent of learning. Turning it off blocks cross-thread search and recall immediately (including tools found earlier); stored history and same-thread recall remain. `session_search` runs local SQLite full-text search over user and assistant prose across providers, with no model calls; existing messages are indexed on upgrade and edits and deletions update the index. Reasoning, tool payloads and helper transcripts are excluded. Search defaults to the current project (`scope: "all"` searches every project on the server; project-free threads search only project-free history) and returns excerpts, titles, sequence numbers and source links that open and highlight the message on desktop, with `offset`/`nextOffset` paging. `session_recall` with a returned `sessionId` and `seq` as `startSeq` reads surrounding events under the same scope (`nextSeq` pages; reasoning omitted). Retrieved history is evidence, not instructions.

## Installing external skills

Ask the agent to find or install a skill from a repository, URL, Git address or local folder. `skill_find` wraps the skills.sh search CLI. `skill_install` asks whether the skill belongs to this project or all projects, stages one skill with pinned `skills@1.7.2` (telemetry off) in a temporary directory, and shows source, description, scope and file list for approval. Scripts need a second approval and are skipped by default; Ramu copies approved files and never executes skill scripts during installation. Symlinks, unsafe paths and special files are rejected; limits are 10 MiB per file, 25 MiB total and 1000 entries. A preview expires after 30 minutes or a restart, and an update refuses to overwrite a skill changed while approval was pending. Node.js and `npx` are needed only for finding, staging and updating ([install Node.js](https://nodejs.org/en/download)).

**Settings → Memory & skills → Installed skills** takes a source link or absolute path and optional name: preview, inspect, approve. Cards show source and scope with Update, Disable/Enable, Move and Remove; source updates show added, changed and removed files first. Installed skills are excluded from automatic edits and archiving.

**Your skills** holds skills you wrote: **Create skill** (name, when to use, instructions, scope) and **Edit** (a new revision; refused if the skill changed since you opened it). They are pinned, so learning never rewrites them. **Edit a copy** of an installed skill makes a separate editable `<name>-copy` that keeps the approved supporting files, provider selection and its own file snapshot through edits, source updates, removal of the original and restarts, and records the source revision. When the source changes, **Review source changes** compares original, copy and new source, prefills untouched fields and keeps your edits; fields changed on both sides and conflicting supporting files need an explicit choice. Saving makes a new copy revision without changing name, scope, provider selection or enabled state, and is refused if either revision moved meanwhile. Copies without a recorded source, with a removed source or moved to another scope stay editable but cannot use this flow.

Chat tools: `skill_list`, `skill_inspect`, `skill_update_from_source`, `skill_disable`, `skill_move`, `skill_remove` (updates, moves and removal ask for confirmation). User-scoped skills apply in every project, project skills only there; both use the managed export for all five providers, and changes show in the next session.
