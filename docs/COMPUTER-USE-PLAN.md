# Computer use and remote screen viewing

Implementation proposal, 2026-10-19. This planning change does not install a computer-use runtime or implement screen viewing. Follow [Architecture](ARCHITECTURE.md), [UI](UI.md) and the [root planning guidance](../AGENTS.md#planning-docs). Remove work as it ships, document lasting behavior in feature guides and delete this plan when acceptance is finished.

## Already in place

- Shared control-lease rules (`packages/shared/src/control/lease.ts`) and the server session/service/tools (`apps/server/src/computer/`): one controller at a time, observation-gated agent actions, takeover that drops queued agent work, pause on controller disconnect, viewer grants per device. Covered by `apps/server/test/computer*.test.ts`.
- App-scoped grants through Open Computer Use (`computer/ocu.ts`, MIT, installed by **Settings → Browser → Computer use → Install**, which runs a pinned `open-computer-use@1.1.2` into `~/.ramu/tools` and verifies the version; checked with a real install on 2026-10-22): the agent or a viewing device acts on one named app through the Accessibility tree, in the background, without moving the person's cursor. Checked through the real desktop app on 2026-10-22: Calculator was granted by name, a bogus app name was refused, and `125*8+42` produced 1.042 with the real cursor unmoved. Scrolling uses Page Up/Down and horizontal scrolling is unsupported; a drag is posted to the app, so window moves and text selection do not work; capture is the app's key window only.
- Smooth video of the main display: a ScreenCaptureKit helper (`apps/server/native/ramu-capture.swift`, built with the Xcode toolchain on first use) encodes hardware H.264, the host answers a viewer's WebRTC offer (werift) and the desktop viewer plays it with the browser's own decoder; the phone uses `react-native-webrtc`, which exists only in an EAS development or production build. Checked on 2026-10-22 through the real desktop app: about 29 fps at 1600×900 and about 185 KB/s while the screen changed. Image frames remain the fallback for Expo Go, app targets and failed connections. The phone path is untested.
- While a thread has computer access the host holds the Mac awake (`caffeinate -i`); the screen may still turn off. A display that is asleep or locked has nothing to capture, and macOS blocks input at the lock screen; app-scoped control through Open Computer Use's `agent_display` and its Locked Use component are not set up.
- A local macOS backend (`computer/macos.ts`) using `screencapture` for the main display and Quartz events through `osascript` for input. It is a stand-in for the Cua Driver below and cannot confine capture or input to one app.
- `computer.*` IPC handlers, the agent tool family (registered only while **Settings → Browser → Computer use** is on), a per-thread **Computer** tray with approve, take control, give control back, stop and revoke, and a polling viewer dialog with click, text and key input.

- A mobile viewer (`apps/mobile/src/components/ComputerActivity.tsx`) and a desktop control for sharing a thread's screen with a paired device (watch or control); viewing another host's computer from desktop works through the same host-qualified calls.

Checked on a development macOS 27 build through the real desktop app (2026-10-22): a 1600×900 JPEG frame of about 200 KB in about 0.5 s, and input at frame coordinates landed on the matching screen points. Still to check: a packaged build's own Screen Recording and Accessibility identity, Retina/external-display variations, IME text entry and the phone.

Not yet in place: an enrolled broker for a runtime owner that is not the execution host, a push frame subscription (viewers poll and share one capture at most four times a second), and per-provider image delivery checks.

## Human need and delivery

A person asks their existing Ramu agent to complete a task in a native application on a selected computer. From a phone, they can watch that computer's current screen, take control with touch and keyboard, return control to the agent, answer requests and return later to the same thread. From desktop Ramu, they watch the actual application directly when using that same computer; when controlling another computer, Ramu shows its screen inside the thread.

**Easier for the person:** The person watches and steps in from wherever they are, instead of walking back to the computer to unblock the agent.

Deliver one complete macOS flow first: explicit runtime setup and OS permissions, scoped agent actions, local activity/stop controls, and an authenticated screen viewer on mobile and on a different desktop. Viewing and human takeover on both mobile and desktop are part of the first usable delivery. Include touch/pointer input, text entry, essential keys and explicit human/agent handoff. Preserve existing drafts, navigation and provider selection.

## Framework decision and evidence

Choose **Cua Driver's MIT components** as the initial automation backend, wrapped by Ramu's server-owned authorization and lifecycle. Ramu's existing agent remains responsible for the conversation and task; installing another autonomous agent loop is unnecessary. This is a fit-based engineering decision pending the prototype and acceptance below, not a claim that Cua has the highest benchmark score.

Repository popularity checked through GitHub's repository API on 2026-10-19, rounded below. Stars describe each whole repository, including unrelated capabilities, and do not establish reliability or mobile-viewer support. Expanded shortlist, in descending star order:

- [Open Interpreter](https://github.com/openinterpreter/openinterpreter), approximately **68.6k**, Apache-2.0: general local code execution/agent tooling. Its current repository redirects from `open-interpreter`. Replacing Ramu's agent runtime would add overlap; it does not establish the required shared screen/control contract.
- [UI-TARS Desktop / Agent TARS](https://github.com/bytedance/UI-TARS-desktop), approximately **39.3k**, Apache-2.0: a strong alternative with local/remote computer operators and reusable agent infrastructure. Retain as the fallback candidate if Cua fails the native integration gate; adopting its application or agent loop is additional scope.
- [Cua](https://github.com/trycua/cua), approximately **30.1k**: MIT drivers/SDK, native automation and MCP/application integration fit Ramu's existing providers. Its background interaction is useful, but support must be checked per platform and application. Select its driver, not the entire product stack.
- [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL), approximately **20.1k**, Apache-2.0 repository: a model family with an official [computer-use cookbook](https://github.com/QwenLM/Qwen3-VL/blob/main/cookbooks/computer_use.ipynb), rather than a complete remote-desktop integration. [Qwen-Agent](https://github.com/QwenLM/Qwen-Agent), approximately **17.2k**, Apache-2.0, provides agent/tool infrastructure. Either can inform later model compatibility; neither removes Ramu's capture, authorization and viewer work. Check exact model-weight terms independently of repository licensing.
- [Agent S / S3](https://github.com/simular-ai/Agent-S), approximately **12.6k**, Apache-2.0: specialized GUI-agent planning/grounding research. Benchmark results do not validate Ramu's host routing or phone viewing; defer adding its separate model/agent pipeline.
- [E2B Open Computer Use](https://github.com/e2b-dev/open-computer-use), approximately **2.4k**, Apache-2.0: its documented setup requires an E2B API key and provides a sandbox display stream. Better suited to a later isolated cloud computer than controlling the user's existing desktop. Do not treat this repository as an official Qwen project or assume local-host support.
- [OS-Copilot](https://github.com/OS-Copilot/OS-Copilot), approximately **1.8k**, MIT: broader OS-agent research; additional agent orchestration would overlap Ramu.
- [qwen3_computer_use](https://github.com/SeungyounShin/qwen3_computer_use), **43** stars: a community Qwen driver using vLLM, PyAutoGUI and mss, distinct from official Qwen repositories. Useful minimal reference, without evidence for the production host/viewer requirements.
- [OpenComputer](https://github.com/andykr1k/OpenComputer), **17** stars, MIT: local VLM/API application; upstream describes several platforms as experimental. Less evidence of adoption than the shortlisted alternatives.

Inspect Cua at pinned revision [`b286bea824eef1a3a1c154ab140223a7b97e0048`](https://github.com/trycua/cua/tree/b286bea824eef1a3a1c154ab140223a7b97e0048). Its [Driver integration documentation](https://github.com/trycua/cua/blob/b286bea824eef1a3a1c154ab140223a7b97e0048/libs/cua-driver/README.md) describes MCP and application SDK entry points and macOS launch/permission identity requirements. Prototype the supported embedded host or standalone app path; do not rely on a raw helper process acquiring permissions accidentally through a terminal.

The [licensing map](https://github.com/trycua/cua/blob/b286bea824eef1a3a1c154ab140223a7b97e0048/LICENSING.md) distinguishes MIT Driver/SDK components from FSL-1.1-MIT Spaces/viewer/media components. Build the first Ramu viewer from authorized captures and Ramu-owned transport/UI. Do not copy the Spaces viewer/streaming code or install optional non-MIT perception packages as an implicit dependency. Pin the actual release, audit transitive native artifacts and record notices before distribution. The root MIT badge alone is insufficient.

## Product behavior

- Add **Computer** within existing thread tools/activity, alongside the separately planned **Browser**. Use browser tools for web tasks where sufficient; computer tools can operate native apps. Browser access does not grant access to the whole desktop.
- Resolve the **computer runtime owner** separately from the thread's execution host and the viewing device. Show the computer name and capture target on activity and viewer surfaces. Compare stable enrolled machine identities, never hostname, address, selected project host or thread execution host alone.
- **Phone/tablet:** show a compact current-screen preview in the thread with **View computer** opening a full-screen viewer. Include computer/app or display identity, agent/human ownership, connection state, capture time, **Take control / Give control to agent** and **Stop computer use**. In human control, offer touch-to-pointer input, scroll, drag, native text entry and essential keys; distinguish zoom/pan gestures from remote input. Allow landscape, zoom and pan without stealing transcript scrolling.
- **Desktop using its own computer:** show the activity, target, **Take control / Give control to agent** and stop action without a mirrored-screen pane. Taking control pauses agent input so the person can use their physical mouse and keyboard directly. The real application is already visible. Do not force a screen preview when automation begins.
- **Desktop using another computer:** show a resizable computer viewer in the existing thread pane, with the same target, freshness, connection, takeover and stop controls as mobile. Human control forwards mouse, scroll, drag, keyboard and text input to the owning computer through the authorized broker. Compare against runtime ownership even when the agent runs on a third machine. Unknown identity must not be treated as local; show the remote view when available and explain unresolved identity.
- Keep all execution on the owning computer when the user switches viewing devices. Hiding/closing an observation-only viewer stops frame delivery, not the task. Closing/backgrounding a viewer with human control cancels pending human input and pauses the session until explicit resume or handoff; stopping computer use revokes its input lease without claiming to undo earlier actions. Thread Stop cancels the run and all computer operations. Distinguish computer-only stop from thread stop in copy.
- Configure **Settings → Computer use** on the selected host: explicit Enable/setup, runtime readiness/version, granted app/display scope, OS permission status and revoke. Keep install, host administration and permission grants on the owning desktop; pairing a phone is not permission to enable whole-computer access. No automatic credential/session import.
- Localize copy and expose textual activity/status for VoiceOver/TalkBack, large text and keyboard use. Compose app controls outside upstream-owned `components/ui/`. Do not add a fifth mobile tab.

## Runtime and authorization boundaries

Extend `packages/shared/src/api.ts`, shared domain types, validated IPC handlers and `packages/contracts` capabilities. Add a focused server computer service; reuse `agent/toolRegistry.ts`, request-scoped tool registration, existing thread events, provider adapters and the authenticated host transport. Host-qualified session IDs and query/event keys must survive device switches without crossing into another host's cache.

The execution server owns session policy and task state. A native broker on the runtime owner owns OS capture/input and device permission prompts; the server must not import Electron. For a local desktop this broker uses the supported Cua macOS host identity. For another computer, connect only through an explicitly enrolled, authenticated broker bridge; a selected remote server must never silently control the viewing desktop. Headless hosts without an attached graphical runtime report **Computer unavailable**. Define server-to-broker command/result, registration, cancellation and disconnect messages explicitly; ordinary client RPC is not that reverse channel.

Expose a narrow Ramu computer tool family: capabilities/status, open a granted target, observe/screenshot, click, type, key, scroll, drag and close session. Server-derived host/thread/run identity, target grant, ownership generation and fresh observation IDs authorize every action. Route both direct and deferred tools through that service; do not expose unrestricted upstream MCP tools that bypass Ramu's checks. Probe image delivery and action compatibility for each provider; unsupported providers get a specific setup/compatibility message. Existing CLI/MCP configuration remains untouched.

Use one mutation queue and one agent input lease per target desktop/session. Helpers do not inherit control implicitly, and upstream multi-cursor support does not justify concurrent writers. Observe target dimensions, scale and generation; invalidate stale coordinates after resizing, display/app switching or ownership change. Cancel queued actions on Stop, permission revocation, session lock, broker loss or run exit. After an uncertain action result, observe before deciding whether to retry; never replay clicks or typed text on reconnect.

Grant observation and input separately to the agent and each viewing device, bound to the exact runtime/target/session. Enforce device roles and explicit grants in `remote/access.ts` and in the frame endpoint, not just UI visibility; existing viewer roles gain no computer visibility/input implicitly. Target changes require a new matching grant. Revocation terminates viewers and leases promptly. Capture only the approved app/window or display and tell the user what the selected mode exposes. If the backend cannot enforce window-only input/capture, require an explicit display-scoped grant or report unsupported instead of claiming confinement.

OS security prompts and secure input remain under OS control. Report Screen Recording/Accessibility denial, locked screen, sleeping/offline computer, protected content and unsupported applications with recovery actions. Keep credentials and driver endpoints on the owner; desktop content remains untrusted task data. Do not add shell execution to this toolset; Ramu already has scoped terminal/file services.

## Screen delivery and recovery

Use a dedicated authenticated, bounded frame subscription over the existing host connection or a narrowly authenticated companion endpoint. Do not place a video feed in durable transcript events or normal JSON RPC responses. Start with JPEG/WebP current-screen frames, aiming for two frames per second while visible, plus refresh after actions. Verify capture cost before fixing the default. This is a live state viewer, not a promise of video-rate streaming.

Frames carry session/target ID, monotonically increasing sequence, capture time, dimensions, scale and ownership generation. Drop superseded frames; bound payload sizes, memory, concurrent subscribers and capture frequency. Share capture work across viewers where safe. Refresh after foreground/reconnect, apply backpressure and stop subscription/capture work when no viewer or agent needs observations. Retain no screen history by default; screenshots used as agent evidence must follow explicit retention rules and stay out of notifications and generic logs.

Do not put long-lived bearer tokens in URLs or expose VNC/CDP/driver ports publicly. Authenticate every subscription and re-check revocation/expiry throughout its lifetime. Keep browser/Interactive Content origins and credentials separate. Bind any short-lived stream grant to device, host, target and session.

Show **Connecting**, **Live**, **Last frame · time**, **Disconnected** and **Computer locked** accurately. Mark a frame stale after five seconds without an update while subscribed, disable future remote input against stale observations and retain a frozen frame only while the current authorized viewer remains open. On app backgrounding or revocation, clear sensitive frames from UI/cache and app-switcher previews where the platform permits. Offline reopen shows status rather than a cached desktop screenshot. Losing an observation-only viewer does not pause the agent. Losing the human-controlling viewer pauses input; reconnect requires observation and an explicit resume, with no queued input replay.

## Ordered implementation and acceptance

Native prerequisite (2026-10-21): `command -v cua-driver` found no installed Driver, so the shipped backend is the macOS-native stand-in above. Packaged identity, Screen Recording and Accessibility grants and a representative capture and action still need explicit acceptance on a real machine.

1. **Prove the backend boundary.** On the supported macOS version, use a pinned Cua Driver build through a supported grant-owning host. Verify app/window capture, bounded actions, image delivery through one existing provider, cancellation and packaged identity/permissions. Confirm that the authorized capture supports mobile-friendly refresh without FSL dependencies. If this fails, evaluate UI-TARS operator components against the same gates and update the decision before expanding architecture.
2. **Ship the complete first flow.** Implement contracts, broker/service, thread tools/activity, explicit setup/grants, mobile viewer and remote-desktop pane with human takeover together. Unit/integration checks cover roles/grants, cross-host denial, local-versus-remote identity, unsupported/old hosts/providers, stale observations, frame bounds, human/agent ownership, Stop/revocation and reconnect. Use fake brokers/providers for deterministic checks.
3. **Validate a representative task.** Ask the agent to open Calculator on computer A and calculate `(125 * 8) + 42`, then verify `1042`. Watch current state and Stop from a phone and desktop B; verify desktop A shows activity without a mirrored pane. Repeat with the agent on host C and runtime on A to catch incorrect execution-host routing. Switch threads/hosts, background/reopen mobile, disconnect, lock A, deny permissions and stop during a queued action. Record failures and capture age/CPU/memory on actual iOS/Android and packaged macOS; do not claim acceptance from source inspection.
4. **Gate the first delivery on takeover acceptance.** Verify explicit **Take control / Give control to agent**, touch-to-pointer mapping, keyboard/IME and desktop input. Taking control advances generation, cancels queued agent mutations and waits for in-flight work to settle before enabling human input. Enforce one human controller at a time across phone, remote desktop and local desktop. A second device must request an explicit handoff; local takeover can revoke a remote lease immediately and reports the interruption on that device. Local physical interaction must pause conflicting agent work through supported broker detection; if detection is unreliable, require explicit takeover and state that limitation before enabling automation. While a remote controller owns input, local takeover takes priority. Release held keys/buttons on cancellation, ownership change or connection loss. Agent observations continue only within granted visibility. Agent mutations remain blocked until release and a fresh observation. Disconnect never hands control back automatically. Test takeover and return on phone, desktop B and local desktop A, including orientation/scaling, keyboard/IME, external keyboards, second-device conflicts, stale frames and non-idempotent input recovery. Human input never targets the phone or viewing desktop by accident. Keep control UI available while zoomed and provide accessible alternatives to gestures. If frame latency prevents accurate clicking/dragging, improve frame delivery before passing takeover acceptance.
5. **Expand verified platforms.** Add Windows and Linux only after native capture/input, session permissions, signing/packaging and host acceptance pass. Distinguish X11/Wayland and elevated-window limitations. Additional displays, isolated VMs/cloud desktops, high-frame-rate transport and optional local Qwen/UI-TARS grounding follow demonstrated need; do not expose settings for unimplemented backends.

For implementation changes, run focused tests and typechecks in affected shared/contracts, server, mobile and web packages. Desktop-facing implementation also requires `pnpm build` followed by `pnpm test:desktop-smoke`, never rebuilding during smoke. Keep `scripts/smoke/desktop-smoke.mjs` as the single desktop startup check; do not introduce a second desktop e2e/performance suite. This documentation-only change requires formatting and link checks, not desktop smoke.
