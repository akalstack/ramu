# MCP management and Shared MCP

## Smallest usable delivery

A person connects one supported external service on the intended host, enables it for a project and two compatible providers, then uses an authorized tool from each thread with the expected service account. Deliver one verified service/transport path through Settings, authentication, authorization and invocation before broadening compatibility. Keep raw command/environment fields and the full provider matrix in advanced/details views. The next action should say Connect, Sign in or Enable for this project; users need not understand gateways or MCP namespaces. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

## Goal and scope

Add **Settings → Agent setup → MCP servers** to manage external MCP servers, authentication, accounts, availability and diagnostics across Ramu's providers. Call the cross-provider feature **Shared MCP**: connect a server through Ramu once and make its permitted tools available to compatible provider sessions on the same workspace host. Follow the [Agent setup plan](AGENT-SETUP-PLAN.md) for Ramu-native Settings integration, existing skill management, shared rules, provenance, scope conventions and effective-session inspection. Keep MCP lifecycle and authorization in the boundaries defined here.

The motivating case is a user who can access Atlassian in Codex but cannot access it in a Claude thread. Offer to connect the same underlying MCP server through Ramu, authenticate when needed, and enable it for both providers. This is a configuration/access gap example, not a claim that Atlassian is exclusive to Codex. Atlassian documents multiple compatible clients; organization policy and client authorization can still prevent a connection.

Sharing an MCP connection does not transfer a provider subscription, copy another application's OAuth tokens, grant access to another account, or turn a provider-private connector into an exportable server. Show these distinctions before setup. Do not silently delegate the task to Codex or change the thread's provider to hide missing tool access.

This document contains unfinished work only. Update feature guides as implementation lands, remove completed work here, and delete the plan when complete.

## Existing boundaries

- `apps/server/src/index.ts` exposes Ramu's session-authenticated MCP endpoint and registers app-owned tools. Provider runners already inject that connection through Claude options, Codex configuration, OpenCode inline configuration, Cursor SDK options and ACP session setup.
- `apps/server/src/agent/toolRegistry.ts` currently discovers and invokes only Ramu-owned tools. It explicitly excludes external MCP catalogs. Preserve that contract while introducing an external catalog with its own authorization boundary.
- `apps/server/src/agent/permissions.ts` trusts the `mcp__ramu__` namespace in Auto and restricted review sessions. External calls must never inherit that trust by entering through an app-owned wrapper or discovery tool. Audit equivalent paths in every runner and in background/restricted sessions before exposure.
- Provider account sign-in in [Providers](PROVIDERS.md) is separate from MCP service authentication. Share the secure credential-store work planned in [Git hosting integrations](GIT-INTEGRATIONS-PLAN.md#architecture-and-credentials), rather than inventing another token vault. Neither feature may assume that store already exists.

## User experience

- Add a host-scoped **MCP servers** group under **Agent setup**, using Ramu's existing Settings patterns, with searchable server rows, **Add server**, **Discover existing**, account identity, source, transport, connection/authentication status, last check and provider availability. Keep provider login controls in Providers; cross-link relevant MCP rows from provider settings and missing-tool messages.
- Support a remote server URL and local stdio command with argument array, working directory and environment-secret references. Adding or importing configuration previews the destination host, endpoint or executable, requested access and provider/project scope before explicit Save/Connect. Discovery and editing do not launch commands, install packages or execute untrusted configuration.
- Provide **Connect**, **Check connection**, **Reconnect**, **Change account**, **Enable/Disable**, **Edit**, **Disconnect** and **Remove** as applicable. Disconnect removes Ramu-owned authorization; disable stops new use but preserves configuration. Remove explains credential cleanup and affected scopes. Do not log out an external CLI or alter its configuration.
- Separate connection health, authentication, scope and provider compatibility. Distinguish disabled, not connected, connecting, connected, sign-in required, expired/revoked, insufficient permission, organization blocked, offline, process failed and unsupported capability. Show the next useful action; a successful handshake does not prove every tool is authorized.
- Let users choose enabled providers, project scope and service account. New connections default to the current project and selected provider; extending sharing is explicit. Host-wide availability is an explicit choice. Each thread can narrow its allowed connections; it cannot broaden host/project policy. No-project chats receive only explicitly applicable host-wide connections.
- Show a provider availability matrix with **Shared**, **Native only**, **Sign-in required**, **Disabled** or **Unsupported**, plus a reason. A connected upstream may still be unusable from a runtime without the required MCP transport. Avoid promises of universal parity.
- In a thread, expose available connections, effective service account and source, pending changes and setup links. Authentication requests use the existing input/Inbox flow with cancellation and return to the originating thread. Expired login pauses the affected tool operation, not unrelated thread work; reconnect never silently repeats a write.
- Use composed app controls outside `components/ui`, semantic tokens, keyboard/focus support, narrow layouts and English/Indonesian strings. Mobile shows the paired host's status and supported actions; initial credential provisioning follows the host's administration policy.

## Shared MCP architecture

Introduce a host-owned connection service under `apps/server/src/mcp/` with persisted non-secret definitions, a secret-store boundary, upstream MCP clients, lifecycle/health management and a separately authorized external catalog. Shared contracts describe connection/account IDs, host/project scope, enabled providers, capability/status reasons and configuration revisions. Keep secret input out of generic settings methods and read models.

Ramu acts as an MCP client to each upstream and exposes selected capabilities to provider sessions through an isolated external-tool gateway. Reuse existing runner injection where practical, but preserve external provenance and authorize on the server even if the provider automatically approves the gateway. Prefer a separate MCP namespace where supported; a shared discovery/invoke entry point must enforce the same external policy before dispatch. Do not add external handlers to the trusted Ramu tool registry without changing its explicit contract and every trust path.

Use stable connection/tool identities, including account and host scope, with deterministic provider-safe names and collision handling. Never merge two servers because they use the same display name. Resolve tools from the authorized catalog for the requesting session; forged names or IDs cannot select arbitrary upstream methods. Preserve supported input/output schemas, structured content, error flags and content blocks; bound oversized outputs and explain unsupported schemas or content rather than silently changing semantics.

Start with tools over Streamable HTTP and local stdio. Determine legacy SSE support from discovered configurations and tested SDK support; label unsupported transports clearly. Negotiate capabilities and protocol versions. Resources, prompts, subscriptions, sampling, roots and elicitation require explicit capability decisions: forward only implemented, scoped features, and report the rest accurately. Never advertise arbitrary filesystem roots or provider sampling access by default.

External tool discovery must respect context budgets and the same per-session visibility as invocation. Support catalog changes, pagination, invalidation and deterministic naming. Bind approvals and calls to a configuration/catalog revision; changed endpoint, executable, account, tool schema or policy invalidates stale authorizations.

Pool only where upstream session semantics permit it. Key isolation by host, connection, account, project/workspace and any session state that must remain private. Enforce bounded process lifetimes, concurrency, output, timeouts, cancellation and reconnect backoff. Stdio runs on the workspace host with a constrained environment and a documented sandbox/trust decision; never run imported commands through a shell or resolve them on the viewing device.

## Authentication and authorization

- Support unauthenticated servers, explicitly entered API keys/headers and negotiated OAuth for remote servers, plus scoped environment secrets for stdio. Keep provider runtime login and upstream service account selection independent. Multiple service accounts have stable IDs and explicit scope bindings; authentication failure never tries a different identity automatically.
- Implement the negotiated MCP authorization requirements, including protected-resource/authorization-server discovery, resource/audience binding, PKCE and state, validated callbacks, supported client registration and secure refresh handling. Validate actual upstream compatibility before claiming OAuth support. Separate the provider-to-Ramu credential from Ramu-to-upstream credentials; never pass a provider or gateway bearer token upstream.
- Store tokens, refresh tokens, headers and environment secrets only in a verified host-owned secret store. Ordinary settings/SQLite hold opaque references and safe metadata. Define locked/unavailable-store and headless provisioning behavior; do not fall back to plaintext. Refresh is single-flight per account; replacement is atomic and failed replacement preserves a working connection. Explain local disconnection versus upstream revocation.
- Remote/paired clients cannot gain secret administration merely because they can render Settings. Define write-only secret submission and administration capabilities within the existing authenticated RPC boundary. OAuth completion binds host, initiating client, connection, account and one-time transaction; callbacks cannot authenticate a different host or revive a cancelled request. Headless/remote flows need a verified callback path before shipping.
- Validate configured URLs, authorization metadata, redirects and resource links; prevent credential leakage across origins and unintended access to private endpoints. Explicitly configured private MCP servers remain possible under a host-admin policy. Redact errors, headers and command environments from logs, transcripts, memory, diagnostics and exports.
- Authentication grants service access; it does not approve every tool action. Enforce external tool policy at the gateway for all providers, access modes, restricted reviews, advisors, helpers and background jobs. Default restricted/background sessions to no external access unless their role explicitly permits it. Propagate session/project restrictions to children and provider fallback.
- Display actual server, account, tool and meaningful arguments in approvals. Treat upstream tool annotations as hints, not authority that an operation is read-only or safe. Deny or request approval according to the effective access policy; a wrapper name cannot bypass it. Record external provenance and outcome without credentials. Upstream content remains untrusted tool output.

## Discovery, migration and provider changes

1. Inventory each supported runtime's configuration scopes and read capabilities from installed versions. Read only known, user-approved configuration sources; show parse errors and unsupported entries. Deduplicate by explicit identity and scope, not hostname alone. Never scrape token stores, export provider-managed sessions or rewrite user configuration during discovery.
2. Classify each discovered item as an importable server definition, a native-only integration, or unsupported/unknown. Import a non-secret definition only after preview; request separate Ramu authentication when an existing login cannot legitimately be reused. A native-only connector shows why sharing is unavailable and links to supported setup alternatives.
3. Preserve native configurations and existing tool access. Detect when a shared server duplicates a native server; offer an explicit per-session choice without editing global files or serving both copies silently. Removing Shared MCP restores the prior native choice.
4. On provider/model/account switches, fallback, resume and helper launch, resolve the effective shared catalog for the destination session. Preserve service identity and project policy. Report lost capabilities in the handoff; do not call a different tool/account as a substitute. Apply configuration changes at a safe boundary and show when a runtime restart is required.
5. In-flight writes are not retried after lost responses, reconnects, provider switches or service restart unless the upstream supplies a verified idempotency/reconciliation mechanism. Record unknown outcomes distinctly and let the user inspect them. Read retries are bounded and follow known semantics rather than trusting annotations alone.

## Delivery and acceptance

1. Define connection/account/scope/capability contracts, authorization rules and the secure-storage dependency. Audit the existing trusted-tool paths and installed provider transport support. Publish a tested compatibility matrix; unsupported runtimes get actionable status.
2. Build host-owned HTTP/stdio clients, lifecycle management, separate external discovery/invocation and server-side approvals. Cover isolation and policy enforcement before exposing external tools to real sessions.
3. Deliver Settings management, authentication lifecycle, provider/project selection and thread setup recovery. Add discovery/import previews and native/shared duplicate handling without modifying provider configuration.
4. Verify provider switches, fallback, helpers, remote/headless hosts and mobile status. Deliver the Atlassian scenario through two providers with the same authorized Ramu connection, documenting runtime versions, supported capabilities and any organization/client restrictions.

Focused server/shared tests cover scope precedence and escalation attempts; account/host/project isolation; name collisions and forged invocation; wrapper trust bypasses; restricted/background sessions; malformed/changed schemas; catalog pagination/invalidation; process environment isolation; disconnect/cancellation; OAuth callback binding/refresh races; secret-store failure/redaction; redirect and metadata validation; import without execution or token extraction; duplicate native configurations; reconnect and unknown write outcomes. Use fake MCP servers and temporary stdio fixtures for real protocol boundaries.

Web/mobile tests cover meaningful connection states, explicit save/cancel, failed credential replacement, effective account/scope, host switching and stale responses, setup deep links, provider availability, native-only explanations and supported administration actions. Manual acceptance covers keyboard/screen reader use, light/dark and narrow layouts, multiple accounts, restart/reconnect, locked/headless storage and remote OAuth completion. Live acceptance requires explicit test accounts and permission for paid calls or service writes; mocked authentication does not establish production compatibility.

Run scoped tests and typechecks for affected packages during implementation. Desktop-facing implementation requires `pnpm build` followed by the existing `pnpm test:desktop-smoke`. Documentation-only planning needs local link and diff checks, with no desktop smoke run.
