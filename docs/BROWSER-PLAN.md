# Integrated and provider browsers

Remaining integrated/provider browser delivery, originally planned 2026-10-18. Remove work as it lands, document shipped behavior in the feature guides, and delete this plan when implementation and acceptance are finished.

## Current implementation and remaining scope

Current local behavior and its limits are documented in [UI](UI.md#integrated-browser). The local desktop broker, root-run tools, host routing preferences and collaborative pane are implemented in the working tree; their new checks are deliberately deferred until all implementation code is complete. This is not evidence of packaged/native or live-provider acceptance.

Remaining implementation includes remote runtime/viewer and mobile control. Optional session import is implemented for Chrome, Edge and Firefox on macOS and Linux (see [UI](UI.md#integrated-browser)); packaged-app, real-keychain and Linux keyring acceptance and further sources remain. Local scoped upload/download workflows, conservative existing-install migration, adapter capability reporting, explicit Ramu-helper/non-Full-access approvals and link context-menu destinations now have working-tree implementations. Native transfer acceptance and live-provider suppression/negotiation acceptance remain unverified. Native helpers that share their parent MCP identity cannot receive independent app-owned browser grants; Ramu-managed helpers have separate approvals and tab sets. Local named profiles, sign-in/clear/delete controls, screenshot/select/press/scroll/wait/diagnostic/dialog tools, background-tab discovery and explicit viewing now have working-tree implementation and written regressions; these are not yet validated. Finish the applicable workflow and then perform the ordered acceptance below; do not claim unsupported providers or native imports from source inspection.

## Delivery

A person asks an agent to check a local page, sees the correct browser and machine, takes control to interact or sign in, then returns control and receives the result in the same thread. Deliver the local desktop runtime, minimal pane, routing and ownership together as one usable increment; internal contract/runtime steps alone are not a user release. Keep provider overrides and profile administration in Settings/details. Session import, remote runtime and mobile control follow independently after this flow works. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

**Easier for the person:** The person no longer copies pages, logins or results between a browser and the thread; handoff to and from the agent is one action.

## Product decisions and defaults

Treat **which browser agents control** and **where the user's clicked links open** as independent settings. A provider is a runtime such as Claude Code or Codex; a browser profile is a website login identity such as Work or Personal. Neither should be coupled to provider account rotation.

| Setting                    | Recommended default                                                      | Behavior                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent browser              | **Ramu integrated browser** for new setups once runtime readiness passes | One tool contract and visible browser across supported providers; uses a clean Ramu-owned profile.                                            |
| Provider override          | **Use default**                                                          | Each provider can select **Ramu integrated browser** or **Provider browser setup** explicitly.                                                |
| Open clicked links in      | **System browser**                                                       | Preserves the user's normal reading/login workflow; **Ramu integrated browser** is the other choice.                                          |
| Default integrated profile | **Default**, empty and persistent                                        | User can create named profiles or select Temporary; credentials stay on the browser's owning machine.                                         |
| Import signed-in sessions  | **Off; user starts import**                                              | One-time copy of supported cookies into a new profile; no automatic import or ongoing synchronization.                                        |
| Show agent browser | **Task-aware, background by default** | Agents explicitly request foreground for a demonstration, visual review or control handoff, and keep routine work hidden. Foreground never switches host/thread. Restored or empty panes never navigate on their own. |

Migrate existing installations with an existing provider browser configuration to **Provider browser setup** for that provider; do not silently replace their tools. Preserve existing system-link behavior. Missing runtime installation is a visible setup state, not permission to silently switch to a provider browser. The user can choose the provider setup from that state. Keep current runs on their resolved browser until they finish; settings changes apply on the next run.

## Ramu starting point

- Desktop is Electron. `apps/desktop/src/main/index.ts` prevents workspace navigation and opens HTTP(S) new-window requests through `shell.openExternal`. Keep workspace navigation isolation; route approved external navigation to a separate browser surface.
- `apps/server/src/index.ts` creates request-scoped MCP tools through `agent/toolRegistry.ts`. Register browser tools through the same direct/deferred registry, retaining session scope, authorization and discoverability.
- Provider adapters/runners already own launch-specific behavior. Extend their capability reporting and per-session tool configuration rather than edit users' global CLI/MCP configuration files.
- The web workspace has per-host state, task panes and tools. Device UI preferences use `deviceStorage`; host execution settings use host preferences. Use those boundaries for link destination versus agent routing.
- [Interactive Content](INTERACTIVE-CONTENT.md) runs saved documents with its own isolation and bridge. Browser tabs load arbitrary websites and authenticated sessions. Keep their origins, profiles, privileges and lifecycle separate.

## Settings and thread UI

Add **Settings → Browser**, searchable by browser, preview, links, sessions, profile and import. Use three groups:

1. **Agent browser**: default choice, status of the selected host's runtime, then provider rows with **Use default / Ramu integrated browser / Provider browser setup**. Provider rows show ready, needs setup, or unsupported with a specific reason and existing setup action. Explain provider setup in plain language: **Use this provider's existing browser tools and sessions. Ramu cannot show or import them here.**
2. **Links & viewing**: **Open clicked links in** (system/integrated) and task-aware foreground/background presentation plus explicit Browser activity/tab actions. Link destination is local to this device; agent-browser choices belong to the execution host. Display those scopes and do not fan device preferences out to paired hosts. Mobile uses its system browser until a remote integrated viewer ships; show that limitation next to an unavailable choice.
3. **Browser profiles**: Default, Temporary, named profiles, default-profile selection and **Add profile**. A profile row shows owning machine and last import time when applicable; actions are rename, sign in, import into a new profile, clear website data and delete. Default/Temporary cannot be deleted. Deleting a selected custom profile restores Default explicitly and closes its tabs after review of affected tabs. Clearing/deleting website data is user initiated and explains that it signs out affected sites.

In each thread, add **Browser** to its existing tools/pane actions. Open a resizable browser pane with tabs, back/forward/reload, address, profile selector, connection/runtime location, **Open in system browser**, **Take control / Give control to agent**, and close. Closing the pane hides it; closing a tab destroys the page; stopping a run cancels automation but leaves user-opened tabs. Display agent activity in the thread's existing activity surface. Use reusable app controls outside `components/ui/` with the shared theme tokens and accessibility APIs.

New automation tabs belong to `(hostId, threadId, runId)`; user-opened tabs initially have human control. An agent can act only after explicit release to that thread. Profile selection affects a new tab; changing an existing tab's profile recreates its context after informing the user, never silently logs it into another identity. Persistent profiles intentionally share website login state across their tabs, even when tabs belong to different threads; show **Shared profile** and offer Temporary for isolation. Do not claim tab ownership isolates shared cookies/storage.

## Routing and tool contract

Resolution is provider override → host default. Browser profile choice is independent and resolved on the runtime owner. Persist the resolved backend/profile with a run so a fallback to another provider preserves the integrated session where permitted. A fallback to a provider-specific setup cannot transfer that provider's private browser state; explain that difference and require new setup/sign-in as needed.

Add adapter capability metadata for integrated MCP support, configurable native browser tools and provider-browser availability. Register only the selected Ramu browser toolset. Suppress conflicting native browser tools only where supported through scoped provider launch configuration. Where native tools cannot be disabled, report that limitation and guide the provider toward the selected toolset; do not claim an exclusive guarantee. Mark a provider unsupported if it cannot use the integration reliably. Never overwrite external MCP settings.

Proposed Ramu tool family (final schemas belong in shared types): status/capabilities, open, snapshot, navigate, click, type, select, press, scroll, wait, screenshot, console/network diagnostics, upload, download status, dialog handling and close. Keep human input bridge private. Tools accept opaque tab IDs, scoped file handles and snapshot-bound locators; status returns host/runtime/profile metadata without secrets. Each action has bounds, cancellation and typed errors such as unavailable, human-controlled, wrong-thread, stale-snapshot and tab-closed. Retrying a non-idempotent click, form submission or upload requires observing the resulting page first; never blindly replay after reconnect.

Agent tool calls must carry server-derived thread/run identity, not caller-provided identity alone. Keep CDP/debugging private to the desktop broker or authenticated local channel; no public unauthenticated debug port. Browser JavaScript evaluation, if needed, executes only in the selected guest page under the same ownership rules; it cannot invoke shell IPC or read host files. Ordinary page text and scripts never become instructions authorizing privileged actions.

## Runtime, ownership and lifecycle

Define `BrowserRuntime` in shared/server contracts with a desktop broker implementation first. Follow [Architecture](ARCHITECTURE.md) and [UI](UI.md): domain methods use the existing shared API, validated handlers, registry/dispatcher and host-qualified queries/events; wire capabilities belong in `packages/contracts`. Desktop main owns isolated guest contents, partition creation, navigation, permissions, downloads and automation. The server dispatches bounded browser operations over the existing authenticated host connection with request/run/tab identity and cancellation. Define explicit broker registration, operation/result messages, capability grants and disconnect cleanup within that transport; ordinary client-to-server RPC does not by itself provide a server-to-desktop command channel. Keep an opaque broker interface in the server without importing Electron or reaching through the workspace renderer. The workspace renderer receives presentation state and approved user input APIs, never raw Electron objects or debugger access.

Serialize mutations per tab. Taking human control advances an ownership generation, cancels queued agent work, waits for an in-flight action to settle, then enables human input. Agent observations may continue only where the user has granted tab visibility. Releasing control advances generation again and requires a fresh snapshot. A second device cannot take over an already human-owned tab without an explicit handoff. On a controller disconnect, pause input and show **Control disconnected**; do not hand control to the agent automatically. A run stop/restart revokes its leases and pending operations.

Persistent named profiles survive restarts; Temporary uses a separate in-memory context per thread/run and is destroyed when its tabs/run end. Store only safe tab metadata for recovery; restart requires reopening pages and fresh snapshots, never replaying navigation or clicks. Do not restore Temporary cookies. Bound active pages, idle lifetime, downloads, screenshots and streamed frames; suspend hidden rendering and dispose idle empty contexts without deleting persistent login state.

The workspace shell and generated Interactive Content must never share browser partitions or privileged preload APIs. Validate navigation/popup/redirect schemes at the main-process boundary; support HTTP(S), keep internal app/file schemes inaccessible to websites, and handle explicit OS protocols separately. Downloads/uploads use scoped user-selected or workspace-authorized file handles, bounded transfer and cancellation, not arbitrary page-supplied filesystem paths. Website camera/microphone/clipboard/location permissions are origin/profile scoped and denied until explicitly granted. Preserve Chromium's sandbox.

## Session import

Import means **copy supported sign-in cookies once**, not passwords, payment data, bookmarks, history, extensions, passkeys, OS keychain exports or an entire live browser directory. LocalStorage/IndexedDB-only logins and device-bound authentication may need manual sign-in. Never write back to the source browser. Never synchronize session cookies across hosts/devices or into cloud settings, logs, transcripts or backups by default.

Wizard: choose installed browser → source profile → inspect supported website domains and select domains (none preselected) → name the new Ramu profile → review destination machine and selected websites → **Import sessions** → results showing imported/skipped/failed counts and reasons. Domain selection must preserve cookie domain/host-only/path/security flags; it cannot widen credentials to sibling domains. Warn that agents granted access to the imported profile can use those website sessions. Keep cookie values out of renderer responses and tool results.

Discovery returns installed-but-unsupported browsers with reasons, rather than hiding them in **No browsers found**. Source paths are discovered and revalidated in the privileged process; do not accept arbitrary renderer filesystem paths. Require closing a source browser if needed and offer Retry/Sign in manually. Use standard OS keychain grants; do not attempt to bypass app-bound encryption. Decrypted values stay in privileged memory only as long as needed.

Stage imports into a new unexposed destination profile. On cancellation/fatal failure remove the staged profile/data; on partial success show exact outcomes and allow Keep profile or Discard before making it available to agents. Re-import creates another staged profile rather than silently merging over an active login. Flush cookie writes before reporting success and do not call it successful when persistence fails.

Start with verified macOS sources and Firefox where supported, then Linux adapters (implemented, awaiting native acceptance) and additional sources with fixtures/native acceptance. T3's guide documents Safari permission requirements, Windows Chromium app-bound encryption and skipped partitioned cookies; these require explicit capability reasons in Ramu too. Until an adapter is verified, list it as unsupported and offer manual sign-in. Do not advertise universal Chrome/Safari/Windows import support from source inspection alone.

## Remote hosts and mobile

Native application control and computer screen viewing follow the separate [computer-use plan](COMPUTER-USE-PLAN.md). Reuse host identity, ownership and authenticated transport conventions where they fit, but keep browser and whole-computer grants distinct. Computer screens appear on mobile and on desktops viewing another computer; a desktop using its own computer needs only activity/stop controls.

Separate the thread's **execution host** from the **browser runtime owner**. In the first desktop milestone the integrated browser lives on the viewing desktop; remotely running agents need an explicitly authorized desktop-browser bridge. Its localhost means that desktop, not the remote project host. Without a bridge, return unavailable and offer provider setup; never navigate to a wrong machine's localhost silently. Show both machines in the pane and settings.

Follow with a host-managed Chromium implementation for headless/remote hosts. It uses the same tool/ownership contract, isolated persistent profiles and an authenticated viewer stream. Provision the runtime only through an explicit setup action, expose readiness/install failures, and do not disable the sandbox to make setup pass. Remote-host profiles begin clean; importing a local desktop session into a remote host is deferred to a separately reviewed credential-transfer flow.

Mobile now exposes metadata-only browser status/activity and **Open in system browser** for eligible public URLs; native and paired-host acceptance remain. A later full-screen remote viewer adds address/profile identity, take/release control, keyboard/touch and disconnect recovery. It views the owning host's browser; a phone WebView is not a substitute runtime and cannot import Safari/Chrome sessions from the phone. Loopback/private URLs need a host-mediated view, not phone-side opening. Gate controls on explicit host capabilities and remote-device grants; pairing alone must not grant browser import/admin privileges.

## Ordered implementation and acceptance

1. **Contracts, migration and capability audit.** Add browser preference/runtime/profile/tab/control types, IPC validation, device/host scopes and schema defaults. Audit each supported provider's actual tool configuration. Unit-test resolution, existing-install migration, invalid profile IDs, unsupported providers and old hosts before exposing enabled choices.
2. **Local desktop runtime and minimal pane.** Implement isolated contents/partitions, basic tabs/navigation, snapshot/input/screenshot and lifecycle. Add the private server broker and read-only readiness diagnostics. Unit/integration-test guest isolation, profile persistence versus Temporary, popup/redirect routing, bounded commands and crash cleanup.
3. **Agent routing and collaborative control.** Register tools through `ToolRegistry`, wire provider/session launches, ownership generations, cancellation and visible status. Verify two threads/helpers, user takeover mid-action, run stop, disconnect, stale locators and a provider fallback on a local test page. Include conflicting native-tool capability cases.
4. **Settings, links and profile management.** Compose reusable controls, provider overrides, local/host scope labels and browser pane actions. Centralize markdown/terminal/preview link dispatch; context menus always allow the other destination for that click. Test system/integrated targets, modifier actions, popups, unsupported schemes, older/mobile clients, reset/delete and profile isolation. Authentication/provider sign-in callbacks keep their dedicated flow and are not hijacked by generic link settings.
5. **Optional session import.** Ship discovery, domain selection, staged import and structured results for individually verified source/OS pairs. Test locked databases, revoked keychain grants, unsupported encryption, host-only/security flags, skipped partitioned cookies, flush failure, cancellation/cleanup and secret-free logs. Accept with disposable source-browser profiles and test accounts, never developers' personal credentials.
6. **Remote runtime and mobile viewer.** Add provisioning/readiness, host-owned Chromium and bounded authenticated streaming, then mobile control. Test routing/local-host identity, role grants, reconnection without replay, controller contention, file transfers and background resource cleanup. Keep cookie transfer out of scope.

After meaningful code changes run tests/types for every touched package. For desktop-facing increments run `pnpm build` then `pnpm test:desktop-smoke` with simulated providers; extend focused unit/integration coverage rather than add a second desktop startup/end-to-end suite. This documentation-only change needs no desktop smoke.

Release acceptance must include packaged macOS, the supported Linux desktop/runtime path and an explicit Windows capability matrix; native import tests cannot be replaced by mocked cookie fixtures. Verify keyboard/focus, screen readers, light/dark, large text, touch, human login/takeover, renderer crash, app restart and two paired hosts. Claim improvements over T3 only after matched task evidence, recording environment, outcome and failures.
