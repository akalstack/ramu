# Git hosting integrations in Settings

Unfinished implementation plan, 2026-10-18. Add account setup and repository-host capabilities to **Settings → Git**, using Ramu's existing design and server architecture. Implement GitHub only for now. Show GitLab, Bitbucket Cloud and Azure DevOps Services as **Coming soon**; their integrations are deferred beyond this plan’s current implementation scope. This is a deliberately limited mainstream set, not a provider marketplace or a claim about measured market share.

## Delivery

A person opens an existing repository, sees which GitHub identity it uses, resolves missing access through Settings and returns to the existing PR/issue workflow. First preserve detected CLI sign-ins and deliver connection status/setup with verified credential handling; clone/publish is a later usable increment. Keep account/source/access diagnostics in details and advanced account overrides contextual. Coming soon rows remain informational. Validate one complete repository-to-setup-to-PR flow, including failed authentication, before expanding the adapter boundary. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

**Easier for the person:** Existing CLI sign-ins are reused and a missing permission is fixed in place, so the person does not repeat setup per repository.

## Starting point and reference

Ramu already has GitHub PR discovery/creation, checks, review feedback, issues and background watches through `gh` in `apps/server/src/workspace/forge.ts`, `ipc/handlers/forge.ts` and `background/pullRequestWatches.ts`. Shared `forge.*` methods, Source Control UI and `apps/server/test/forge.test.ts` are the migration boundary. `GitSettings.tsx` currently contains workspace, sync, PR and commit preferences but no account management. Preserve those working flows and existing CLI sign-ins.

[T3 Code's source-control guide](https://github.com/pingdotgg/t3code/blob/main/docs/user/source-control.md), checked on 2026-10-18, provides the reference: settings expose hosting connections, credentials belong to the server, and API access can differ from Git transport access. Adopt that discoverability and host ownership. Ramu's proposed improvements are explicit connection saves, visible credential selection, per-repository capability diagnostics and predictable recovery from incomplete operations. These are design goals, not a verified superiority claim.

## Already in place

Written, not yet exercised on a device, a packaged build or a live provider (see Remaining acceptance below):

- **Settings → Git → Hosting accounts.** GitHub shows detected `gh` sign-ins (read-only, never the token), saved tokens (**Connect**, **Check connection**, **Replace credential**, **Disable/Enable**, **Disconnect**, **Use by default**, per-CLI-account choice when several are signed in), the locked-credential-store state and host-only administration. GitLab, Bitbucket Cloud and Azure DevOps are informational **Coming soon** rows.
- **Host-owned credentials** in `workspace/forgeAccounts.ts` through `credentials/store.ts`, with origin binding, atomic replacement, redirect refusal and redaction. A saved token is used by `gh` calls, and by the direct API client in `workspace/githubApi.ts` when the host has no `gh` (pull request status with checks and reviews, create, issues, review threads, job logs, repository search, publish).
- **Per-repository access** (`forge.checkAccess`, `forge.repositoryAccount`, `forge.setRepositoryAccount`), shown in Source Control under **GitHub access** with the account choice, **Open GitHub settings** deep links for unavailable actions, and the resolved account in the Publish dialog.
- **Watches** record the account choice they were made under and end when it changes, poll each pull request once per round, and pause on rate limits. A lost reply to **Create pull request** is reconciled against the branch before an error is reported.
- **Enterprise repository search.** The clone dialog offers a **GitHub server** choice when the host has a saved token for an Enterprise origin; `forge.searchRepositories(search, origin)` lists with that token and keeps only clone addresses on that server.
- **Clone progress and cancel.** `folders.clone` takes an optional client `cloneId`; `folders.cloneProgress` reports Git's phase and percentage and `folders.cancelClone` stops it and removes the folder it was filling (a failed clone still keeps its folder). The desktop dialogs and the phone's host-folders screen show progress and **Cancel clone** on hosts that support it; an older host clones as before.
- **Phone status.** Settings → Git shows **GitHub on this host** (`apps/mobile/src/components/HostingStatus.tsx`): the detected sign-ins and saved tokens in words, the locked-store state and where to connect (the phone never holds a token), through the same wording as the desktop (`packages/shared/src/forgeStatus.ts`).
- **Clone** from the signed-in account's repositories or an exact `owner/name` in the host folder dialog (`forge.searchRepositories` then `folders.clone`).

## Settings and interaction

- Add a **Hosting accounts** group near the top of Settings → Git. Keep existing Git preferences below it. Show four compact provider rows. GitHub expands to its connection summary, account/server identity and relevant actions; an unconfigured GitHub row stays collapsed. GitLab, Bitbucket Cloud and Azure DevOps show a visible **Coming soon** label and have no expand, connect, credential-entry or setup actions. Keep their names readable and the status accessible without relying on color or disabled-control tooltips. These placeholders must not trigger discovery, network calls, CLI checks or background work.
- The expanded GitHub row shows configured servers/accounts, selected credential source, last verification time, enabled state and **Connect**, **Check connection**, **Replace credential** and **Disconnect** as applicable. Use explicit **Save connection** and **Cancel** for credentials; never save a partial token on blur. Actions save independently of the general Git-preferences draft, with dirty-state and pending-operation handling made clear.
- Distinguish not configured, checking, connected, expired/revoked, missing permission, rate limited, offline and unsupported server. A successful identity check does not prove repository access or push access. From a repository, **Check access** reports API reads, available writes and Git transport separately, without making a test commit or push.
- Allow multiple accounts per server and an explicit repository override. Bind selection to the Ramu workspace host, forge origin and account ID. Show the resolved account and its source; ambiguity asks for a choice. An action never silently switches identities after authorization failure.
- Deep-link unavailable Source Control actions to the relevant Settings row and return to the originating repository afterward. Show the server's terminology: pull request or merge request. Missing capabilities offer an explanation and **Open on host** where useful.
- Follow `SettingsRow`, `SettingsLabel`, `SettingsGroupTitle`, app-composed buttons/inputs, shared dialogs and semantic theme tokens. Compose reusable hosting rows outside `components/ui`; do not edit shadcn primitives, copy T3's layout or introduce feature-local visual variants. Preserve keyboard navigation, focus restoration, accessible status text and narrow layouts. Add English/Indonesian copy.

## Provider scope: GitHub now, others coming soon

1. **GitHub first:** github.com and explicitly configured GitHub Enterprise origins. Detect existing `gh` authentication and support a directly configured token for API operations without requiring `gh`. Preserve PR creation, issues, checks, feedback and watches. Prefer fine-grained repository access where compatible; explain feature-specific scope or organization-approval gaps rather than requesting broad permissions up front. Browser/device sign-in may follow only after the application-registration and callback design is validated.
2. **GitLab — Coming soon:** reserve the Settings row for gitlab.com and self-managed GitLab. Authentication, merge requests, pipelines, review feedback and issues require a separately scoped future implementation.
3. **Bitbucket Cloud — Coming soon:** reserve the Settings row for workspace/repository connections. Authentication, PRs, build status and review feedback are deferred.
4. **Azure DevOps Services — Coming soon:** reserve the Settings row for organization/project/repository connections. Authentication, PRs, policy/build status and review feedback are deferred.

Verify GitHub API versions, authentication options, required permissions, pagination, rate-limit handling and supported Enterprise/CLI versions before implementation; publish the tested GitHub support matrix. Other providers get presentation metadata only: no adapters, credentials, API methods, persistence migrations or simulated support. Future implementation must recheck each provider’s current APIs and authentication requirements. Keep the shared boundary extensible without implementing speculative provider-specific contracts.

Bitbucket Data Center and Azure DevOps Server are also deferred. Defer Gitea, Forgejo, GitCafe and other hosts until concrete user demand justifies them. Ordinary Git operations on arbitrary remotes continue to work without a hosting integration.

## Architecture and credentials

- Evolve the existing forge implementation into a small server-side adapter boundary with only GitHub implemented under `workspace/forge/`, retaining a facade while callers migrate. Keep Git execution in `workspace/git.ts`. Hosting adapters are separate from AI `ProviderAdapter` and model/account fallback. Avoid a general plugin framework.
- Put typed connection summaries, repository identities, capability results and provider-neutral review data in `packages/shared`. Treat provider-native IDs as opaque; do not assume every issue or review has a globally meaningful numeric ID. Capabilities cover discovery, creation, checks/policies, feedback, issues and watches independently. Unknown or unavailable check/review data must not become a passing status.
- Extend named `forge.*` methods and validated handlers through the existing API table, registry and dispatcher. Query through `invokeOn` and host-keyed IPC queries. Add explicit authorization for account mutations to local and paired-client allowlists; do not accidentally expose them to agent tools or read-only viewers. Server code must remain independent of Electron.
- Resolve HTTPS, SSH and scp-style remotes, ports, GitHub Enterprise API bases, upstream branches and fork/base repositories. Persist explicit provider/origin mappings for custom servers rather than guessing from arbitrary names. Account credentials are bound to an approved origin; reject embedded credentials and prevent credential-bearing cross-origin redirects. Validate user-configured enterprise origins without blocking intentionally configured private servers.
- Use the server-owned `credentials/store.ts` abstraction introduced for Shared MCP; do not add a separate forge-token vault. Verify its OS-backed native store in packaged desktop and headless Git hosting flows. Persist only opaque references and non-secret metadata in ordinary settings/SQLite. Define locked/unavailable-store behavior and secure headless provisioning before saved-token support ships; never quietly fall back to plaintext or import Electron into the server.
- Support explicit saved-credential or detected-CLI selection; environment credentials may be offered as a clearly labelled source bound to an origin. Existing users retain their current CLI behavior until they choose otherwise. Disabled connections stay disabled regardless of available environment variables. Credential changes invalidate affected caches and outstanding verification results.
- Secrets enter through a dedicated write-only request over the existing authenticated transport, never through generic preferences. Never return saved values, include them in process arguments/remote URLs, or copy them into client persistence, traces, transcripts, agent context, memory, diagnostics or exports. Redact provider errors and request logging at the boundary. Replacement is atomic; failed validation preserves the previous working connection.
- The workspace host owns authentication and API calls. A paired host does not inherit the local computer's token. Remote settings name the receiving host explicitly; offline hosts cannot save. Mobile uses the paired server's capabilities without storing its forge credentials. Initial account provisioning follows the existing local-host administration boundary; remote credential entry requires a deliberate authorization extension, not merely a rendered form.
- Keep API connection and Git SSH/HTTPS credentials separate. Connecting never rewrites Git's global configuration, remote URLs, credential helpers or SSH keys. Disconnect removes only Ramu-owned credentials/references, disables dependent watches and invalidates caches; it does not log out an external CLI. Explain when revocation must also happen on the provider's website.

## Repository flows and recovery

Migrate existing Source Control, issue-to-thread and watch flows before adding new surfaces. Carry forge/account/repository identity into persisted links, cache keys and watches; migrate existing GitHub records without losing linked issues or active watches. Refresh after account changes and reject stale responses after host/repository switches.

Route existing GitHub watches through the adapter boundary with host/account/repository deduplication, bounded polling, conditional reads where supported and provider retry guidance. Rate limits pause; revoked access requires reconnection; unavailable or unsupported feedback never looks like success. Preserve Ramu's existing thread feedback behavior rather than importing another app's agent-wakeup policy.

Cancellation and timeouts must distinguish failed from unknown outcomes. After a create request loses its response, reconcile against the intended repository and branch before offering retry; do not duplicate a PR or retry through another account. Preserve partial push/create/watch outcomes and existing Git locks. Enforce capabilities and authorization on the server as well as in UI.

**Publish to GitHub.** A repository with no remote publishes through `forge.publishRepository` (private by default, `gh repo create --source --push`, or the API plus Git push without `gh`); a repository with a remote or no commits explains the next step, and a created-but-unpushed repository is finished by the ordinary Publish branch rather than recreated. The dialog names the account. Remaining: an optional remote picker when several remotes have none named `origin`.

Clone from GitHub and publish use the existing project/host-folder flow; the pasted Git URL stays available. Clone destinations belong to the workspace host; cancelled/failed clones preserve inspectable state. Publishing previews account, destination, visibility (private by default), remote name and push scope before executing; a partial publish must be reconcilable without recreating the repository. Full review/merge dashboards, automatic merging, stacks, webhooks and cross-host credential brokering are deferred.

## Remaining and acceptance

Unwritten: the `workspace/forge/` adapter directory (the facade in `workspace/forge.ts` and `githubApi.ts` is the boundary today; split it only when a second provider is built). Everything else here is written and awaits acceptance below. Coming soon rows stay informational and their implementation is not an acceptance requirement.

Focused shared/server tests cover remote parsing and identity collisions; capability normalization; selected-account precedence and ambiguity; disabled connections; scope failures; pagination; rate-limit/offline errors; secret redaction and storage failure; atomic replacement; redirects; paired-client authorization; stale responses; watch migration/deduplication; and lost acknowledgements after remote writes. Use the existing forge/watch suites and temporary Git repositories where a real boundary matters, with fake HTTP/CLI adapters for external services.

Web/mobile tests cover meaningful connection states, independent save/cancel, failed replacement, account switching, host isolation, Settings search/deep links, unsupported actions, informational **Coming soon** rows with no setup/backend activity, and keyboard/focus behavior. Manual acceptance includes light/dark appearance, narrow/large-text layouts, screen readers, multiple accounts, enterprise hosts, forks, API access with broken SSH, working Git with no API access, restart/reconnect and a locked headless secret store. Live-provider checks use disposable repositories and never commit real tokens or assume a mocked permission result proves production support.

Run scoped tests and types for packages changed during implementation. Desktop-facing implementation requires `pnpm build` followed by the single `pnpm test:desktop-smoke`; do not add a desktop e2e suite. This plan is documentation only and needs formatting/link checks, not a build or smoke run.
