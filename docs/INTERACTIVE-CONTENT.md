# Interactive Content

Ramu can create self-contained interactive explanations, diagrams, data explorers, playgrounds, UI prototypes, calculators, simulations and small tools for any subject; the authoring guide favors development work that uses the conversation's real code and data. Controls run locally without another model call. This is an output format, not a separate agent or a collection of subject-specific demos.

## Authoring and publication

Eligible conversation sessions expose `preview_interactive`, `publish_interactive`, `interactive_list` and `interactive_read`. Deferred tool catalogs discover these through `tool_search` and call them through `tool_invoke`. Review-only library conversations do not gain these tools.

Submit a title, a readable summary, up to 12 accessible control checks and either one `html` document or a small project as `files` (up to 40 relative paths, 512 KB in total, binary assets as base64, entry `index.html` unless `entry` names another HTML file) to `preview_interactive`. A project is bundled into one document before preview: relative stylesheets, CSS `@import`/`url()`, classic `<script src>` files and `src`/`href`/`poster` assets become inline content or data URIs. Module scripts compile local JS/TS/TSX, JSON, CSS and imported assets through a virtual project boundary. The pinned browser library set is React/React DOM 19.3.0, Chart.js 4.6.1 and Dagre 2.0.4; use Chart.js for interactive charts and Dagre with accessible SVG for flow diagrams. No author-controlled package installs or host-file imports run. Missing files, paths outside the project and unapproved library imports fail explicitly. Classic scripts remain supported. Markup inside JavaScript strings is not rewritten, so JavaScript assets must use imports or embedded data rather than bare file-path strings. The exact files are saved beside the bundle and returned by `interactive_read` for revisions. Checks click, fill (including range sliders), select or check a labelled control, then look for expected visible text. A temporary browser with an isolated profile produces dark screenshots at 390 and 900 pixels and a light screenshot at 390 pixels, observes script errors, returns bounded `console.log`/`info`/`warn` output and remote loads that failed or returned an error status, and measures document width/height and horizontal overflow at 320, 390, 768 and 900 pixels, including light-mode diagnostics. Only declared HTTPS subresources load in new previews; failed remote loads are reported without blocking publication, while script errors and failed checks do block it. Overflow is reported as diagnostics for the author; it does not establish factual accuracy or native usability. This validates the specified behavior, not the factual accuracy of generated content or native-device usability.

On first use, the execution host downloads the Chromium version matched to Playwright and reuses its managed browser cache. Concurrent previews share the download; stopping a preview stops its wait without cancelling another preview’s installation. The browser uses a temporary isolated profile, separate from integrated browser tabs and saved sign-ins. Set `RAMU_INTERACTIVE_BROWSER` to an existing Chromium executable for an administered installation. Download failures report a retry/setup error; content cannot silently bypass preview. At most two preview browsers run concurrently, each with a bounded lifetime. Source input is limited to 512 KB and compiled documents to 1.5 MB; previews expire after 30 minutes and are capped at 20 per session.

Publish the returned preview ID with a stable request ID. Publication saves the exact tested compiled bytes, source input, library versions and network permissions; a stored artifact digest detects mismatches without recompiling; failed, expired or mismatched previews cannot publish. Repeating the same request recovers the same version; reusing that request for different content fails. `previous: {id, version}` creates an immutable revision only when that version is still latest. Old turns keep their original version.

Publication creates a dedicated `interactive` conversation event carrying metadata, never executable bytes. Ordinary HTML/tool text cannot publish content. The saved version and its event commit in one database transaction; retries and restarts do not duplicate or resurrect deliberately rewound events. Retrieval and revision are scoped to the authenticated session and selected host.

## Document contract

Use accessible labels, keyboard controls and responsive layouts. Respect reduced motion. Leave the page and outermost element without a background or outer card; the document sits on the thread's background. Viewport height units (`vh`, `svh`, `lvh`, `dvh`) in stylesheets or style attributes fail preview, because the frame grows to fit its content.

### Network access

New documents are **offline by default**. Optional `network: { resources: ["https://images.example.com"], connect: ["https://data.example.com"] }` allows exact HTTPS origins separately for resources and API connections. Paths, credentials, wildcards, IP literals and local hostnames are rejected. These permissions are saved per immutable version and applied by its CSP on desktop, mobile and exported HTML. New documents have no `eval`/`new Function` permission. Bundle libraries and assets rather than depending on CDNs. Existing versions without a network declaration retain their original HTTPS/evaluation policy for compatibility. Frames, plugins, forms, plain HTTP, navigation, local files and app commands remain blocked. Preview requests use the server's vetted public-address DNS lookup at connection time, omit cookies and authorization, and bound remote response sizes. Client-side CSP limits origins; it is not a general-purpose network proxy or a guarantee about external domains' future DNS ownership.

Remote resources load live every time a card is viewed: the reader's device contacts those servers, and a cached document reopened offline runs without them. The authoring guide asks agents to pin exact library versions so published versions keep working, and to prefer the built-in kit and icons, which are stored in the document, for app-styled interface parts.

### Theme tokens

Documents receive the app's live palette as CSS custom properties, updated when the user changes theme or light/dark mode on desktop and mobile: `--background`, `--foreground`, `--muted` (secondary text), `--primary` (brand accent), `--surface` (cards), `--surface-raised` (buttons and inputs), `--border`, `--code-background`, `--button`/`--button-foreground` (solid actions), `--success`, `--warning`, `--danger`, `--chart-1` to `--chart-6`, `--radius`, `--font-sans` and `--font-mono`. Before the host sends its palette, and in exports, the defaults follow the operating system's light/dark preference.

### Built-in kit and icons

Ramu provides offline building blocks that preview and publication inline into the stored document, so app-styled interfaces need no network. Published versions therefore never change when the kit is updated, and the kit and icons work offline.

- `<link rel="stylesheet" href="ramu:kit">` adds app-styled defaults (headings, inputs, focus rings) and the classes `.card`, `.btn` (`data-variant` `primary`, `ghost`, `danger`; `data-size` `sm`, `icon`), `.badge`, `.callout`, `.dot`, `.bar > span` (`data-tone` `primary`, `success`, `warning`, `danger`), `.stat` with `.stat-label`/`.stat-value`/`.stat-delta`, `.table` (`td.num` right-aligns), `[role=tablist]`/`[role=tab][aria-selected]`, `.field`, `.stack`, `.row`, `.grid`, `.muted`, `.small`, `.mono` and `.num`. Every rule has zero specificity, so the document's own CSS always wins.
- `<svg data-icon="chevron-right"></svg>` becomes the matching [Lucide](https://lucide.dev) icon (ISC license), sized `1em` and drawn in `currentColor`. Icons without `aria-label`, `aria-labelledby` or `role` are hidden from assistive technology. Unknown names fail preview with suggestions. Icons inside `<template>` are resolved too, so scripts can clone them.

Other `ramu:` references fail preview. Text inside scripts, styles, textareas and comments is never rewritten.

Standard input/select/textarea values restore automatically, except passwords, files and hidden inputs. For canvas state, selected steps or other custom scenarios:

```js
window.ramuContent.onRestore(state => {
  // Rebuild the visible scenario from this JSON-compatible value.
})
window.ramuContent.setState({ step: 2 })
window.ramuContent.onActive(active => {
  // Pause animation when inactive.
})
```

Animations should save elapsed playback time and play/pause state alongside the selected chapter, and restore them after initialization without overwriting them with startup defaults. A chapter number alone cannot resume within a chapter after an offscreen unload.

Declared state is user-controlled data, not an instruction or permission. The combined state is limited to 32 KiB and 200 controls. Reset clears the version's local scenario. State is not synced between devices. To intentionally preserve the same control keys and custom JSON meaning across revisions, authors may declare an identical `stateSchema` identifier during preview. Only those matching declarations enable the native **Copy saved scenario** action between versions of the same document and session; copying always requires a user action. Missing or changed declarations never infer compatibility.

## Scenarios and revisions

**Versions** in the card menu groups this document's immutable revisions. Choosing another revision opens a separate, closable viewer; the historical card and its title/version stay unchanged. Offline browsing offers only revisions already cached on the device. Current scenarios remain separate for every host and version.

**Saved scenarios** keeps independent named copies of a captured scenario, with up to six per version and 20 per host. Saving an existing name updates that copy. Reaching either limit reports a failure rather than silently removing other named copies. Restore changes the current local scenario; Reset clears only that current scenario. Named copies live in persistent device storage and remain independent of evictable document bundles.

**Choose values** captures the scenario and lets the user select individual labelled controls or explicitly include custom state. **Add to message** attaches only those captured values with the exact source reference. Captures stay labelled historical if the live controls change afterward; no selection sends a message automatically.

## Viewing

Desktop opens the document automatically while its card is on screen; the saved preview screenshot stands in while it loads. The card header holds the title, version, **Reset**, a width switch (**Fit to width**, **Tablet (768 px)**, **Phone (390 px)**), **Expand** and a menu with **Ask about this**, **Choose values…**, **Saved scenarios…**, **Versions** and exports. Projects add a **Preview**/**Code** switch that lists each saved file. Up to three documents run together; the oldest stops first and offers **Run again**. A script error is reported without stopping the document. It loads the document through a dedicated ephemeral `ramu-content:` origin with a restrictive response policy and sandboxed frame. The workspace retains its own stricter script policy. Generated frames cannot navigate to external destinations and have no preload/host invocation API. The width switch reflows the same live frame at that width so you can check phone and tablet layouts. **Expand** enlarges the card over the conversation without reloading it, preserving state; **Esc**, the backdrop or **Collapse** returns it. Hiding the desktop app sends an inactive signal without reloading the frame; returning resumes the same in-memory scenario. Scrolling far offscreen still unloads it; returning restores declared state. Refetching the same document and network policy preserves its live frame. HTML export captures the current scenario and includes the saved source with the isolated runtime, drawn in the palette you were viewing. **Export source** downloads the saved source unchanged inside a page that adds only the theme tokens and base styles it is written against (in the palette you were viewing), so it looks the same when opened on its own; it adds no runtime code or scenario data. Agents read the exact saved bytes with `interactive_read`; for projects, **Export bundled source** downloads the bundled document and the **Code** view shows the exact files.

Native mobile also opens visible cards automatically, without Open/Pause controls. Its compact header offers Code/Preview, Expand and Content actions; the actions sheet keeps reset, follow-up, selected values, scenarios, versions and sharing together. Code displays each exact project source as inert, copyable text and labels binary assets without showing their base64 bytes. Expand uses the existing full-screen sheet with native safe areas. Native mobile has a separate incognito WebView renderer with network policy, navigation restrictions, disabled file access and a bounded state/height bridge. It is separate from the terminal. Expand/close remounts from declared state; offscreen rows, screen blur and app backgrounding stop it, and returning restores the latest declared scenario. Renderer failure or eviction waits for an explicit Reload instead of restarting repeatedly. State and termination callbacks from a removed frame cannot update its replacement. The browser companion keeps a static viewing fallback until it has a dedicated document origin. Native **Share HTML** and **Share source** use the platform share sheet for runnable or source HTML respectively; project Share source still shares the bundled document, while Code exposes the individual files. The browser companion downloads those files. Native sharing needs the matching Expo build with `expo-sharing` (the dependency uses the current SDK pin).

Up to three generated documents run at once per desktop or native mobile renderer; the oldest live card is evicted when another claims the budget. This bounds live frames, not CPU or memory use. Device-local caches retain up to four document bundles (3 million serialized characters total) and 30 current scenarios per host, plus up to 20 explicitly named copies. State writes do not rewrite document bundles. Previously cached bundles can reopen offline; uncached content needs its host. **Ask about this** adds a chip for the content to the thread's message box, like review comments; nothing is sent until the user writes and sends a message. The message then carries the exact content ID, version, digest, summary and latest saved scenario as hidden context, and the sent message shows the content's title and version. Asking again about the same version replaces its chip with the newer capture; **×** removes it. Native mobile still stages this context as draft text.

## Verification limits

Unit/integration tests cover ownership, immutable revisions, retries, atomic publication rollback, state bounds, host/version cache separation, named-copy limits, explicit compatibility declarations, styled source exports, share failure/concurrency recovery, selected-value drafts, transcript replay and browser interaction/layout diagnostics. A disposable built-desktop check also exercised scenario restore, a separate revision viewer, compatible copying and draft staging without sending. The existing desktop startup smoke remains the only desktop smoke suite.

Native iOS/Android gesture, accessibility, navigation/egress, file sharing and lifecycle acceptance still needs device evidence. Remaining platform and comparative acceptance is tracked in [the roadmap](ROADMAP.md#interactive-content-acceptance). Chromium previews and typechecks are not native-device validation, and no comparative superiority is claimed.

Tool groups keep their outputs, images and earlier reasoning inside the disclosure. Their compact headline follows the newest running step; failed steps remain identified. The latest desktop thinking stays in its separate live slot. Inputs and full output remain available in Details.
