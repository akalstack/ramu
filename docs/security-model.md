# Security model

What Ramu can reach, and how it limits that. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## What Ramu can do

Agents run with your user permissions: they can read files, edit code and run commands. Providers receive the context you send them, including attached files and unsaved editor content. Closing the window leaves background agents and schedules running. Stop them in Ramu when needed.

An [ability call](guide/working-with-agents.md#abilities) sends another of your signed-in providers only the calling agent's prompt and the inputs it names: images or files inside the thread's folder, or attachments the thread already holds. It never sends the conversation, other files, memory or credentials. The run has no shell, file, Git or MCP tools. Codex runs read-only in an empty folder with every MCP server its login configures switched off, and Claude runs with no settings files or MCP servers. The thread's row shows what was sent, **Ask before using another provider** turns each call into an approval, and **Off** in Settings → Models → Abilities refuses one. Ramu's own web search sends only the query, to DuckDuckGo. An image or search ability mapped to a Shared MCP tool sends that tool only the prompt or query, through the thread's own Shared MCP access: the tool must be approved for the thread's provider login and project, and its approval rules apply as when the agent calls it. A video, speech, music or sound ability on a media account (Google Gemini or ElevenLabs) sends that service only the prompt or the words to say, with the person's API key: the key is checked against the service before it is kept, lives in the host's OS credential store, is added and removed only on the host, and goes only to that service's API (`x-goog-api-key` or `xi-api-key`). A video Gemini returns as an address is downloaded only from Gemini's own API host. The file it returns is kept as an attachment of the thread.

## Ramu account

The account at `account.akalstack.com` is optional. Signing in grants nothing on its own: a device signed in to the account reaches only hosts the person listed there, and a listed host pairs it without asking only when the person chose that on the host (**Connect devices on my Ramu account** with **Ask me first** off, in Settings → Devices & access, which a paired device cannot change). Otherwise the request ends with the person approving it on the host, with the same six-digit check as a nearby request. Choosing to connect the account's devices makes the account's sign-in (GitHub, Google or a passkey) a way into that host, so a host that holds anything sensitive should turn on **Ask me first** or **Connect them view-only**.

- **What the service stores:** name, email and avatar from GitHub or Google, linked sign-ins and passkeys, sessions per device, sealed backups (ciphertext, size and time), the backup key sealed under the recovery code, key requests and relayed pairing messages for at most ten minutes, and each listed host's name, id and last-seen time. Identity providers' access tokens are not kept after sign-in. **Delete account** removes every row for the person at once.
- **Backups are sealed on the device** with XChaCha20-Poly1305 under a random 256-bit backup key kept in the host's credential store (the phone's secure store on a phone), with the slot bound as associated data. A slot's name is sealed the same way. The service never receives the key. A backup carries the portable settings export only. Credentials never leave the host, sealed or not.
- **Getting the key to a new device:** the new device commits to an X25519 key, the approving device sends its own, the new device reveals its key, and both derive the six-digit number and a sealing key from the exchange. The backup key is sent sealed under it only after the person approves. The service relays envelopes it cannot open and deletes them on delivery or after ten minutes. The recovery code is 160 random bits. The copy of the key sealed under it is useless without the code.
- **Your hosts:** a listed host's addresses never reach the service. A relayed pairing runs the nearby exchange through the service. The host seals its addresses to that exchange in its approval, and the device checks the host's identity on each address. Only devices signed in to the same account reach a listed host, and the host also refuses a relayed message the service names as coming from another account. A pairing the host made on its own is announced at the host each time with **Remove**, and once that device is removed (in Devices & access, with `ramu devices revoke`, or by expiry) the same device's next request asks the person at the host. Five requests wait per host at most and one device sends one a minute.
- **What a compromised service could do:** withhold or delete backups, see sign-in metadata, backup sizes and times and listed hosts' names, and delay or drop requests. It could not read settings, learn a host's address, open a backup without a device's key or the recovery code, or pair a device without the person's approval on the host.

## Remote access

A device paired with **full access** can read workspace data, run agents and terminals, edit files and use the host's provider credentials. Pair only devices you trust.

A **viewer** can read conversations and answer approval and question requests. Approving a request can authorize the agent to act on it, so use viewers for trusted reviewers, not public sharing. The host enforces the viewer role with a method allowlist (`viewerMayInvoke`, `packages/shared/src/viewerAccess.ts`). New methods are denied to viewers by default. Disabled controls in the apps are a convenience, not the boundary.

- **Pairing:** `ramu pair` creates a full-access code and `ramu pair --role viewer` a viewer code. The role belongs to the single-use code. A device cannot ask for more. Failed attempts are rate limited per peer with exponential backoff.
- **Device permissions:** a full-access device also needs a permission for each of computer use, the browser, terminals, changing settings and agents (reading status and settings stays open). New devices get all but Agents; a host that saved its own set before keeps it, shown under Devices in Settings → Devices & access. A device holding less than a new one is marked **Limited** there. A viewer gets none. The host grants, extends or removes each one per device: **This time** (until that device's last connection closes), **For 1 hour**, **For 1 day** or **Always**. A device can request a missing permission. Only a person at the host can allow it (Settings → Devices & access or `ramu devices allow`). **Never** removes it and declines that device's further requests for it until the host allows it again itself. The server refuses the call otherwise, whatever the client shows.
- **Pairing by request:** while the host is Discoverable (or a pairing offer is open), a nearby device can ask instead of typing a code. The device commits to an X25519 key before the host sends its own, then reveals it. Both derive a six-digit number and the device token from the exchange, so the token never crosses the network and a relay cannot make the numbers agree except by a one-in-a-million chance per attempt that a person must also approve. A request appears at the host only after a valid reveal, and only a person can allow it and choose its access, at the host or on a device allowed to [manage devices](#remote-access) (it reads the six-digit number from the host's list): the desktop app asks in a dialog (or a system notification when it is in the background or closed), and a headless server prints the request for `ramu pair --approve <request>` or `--deny`. Requests are refused when the host is neither Discoverable nor has an offer open, or when they arrive through a tunnel address, limited to one per address and four in total, expire after two minutes, and failures count toward the same back-off. A declined address waits a minute before it can ask again. While an offer is open the host also advertises itself nearby, even when Discoverable is off.
- **Host pairings:** a person at host A can let its agents use host B. With a desktop pairing to B, turning on B under **Linked hosts** in Settings → Devices & access on A requests **Agents**. Once a person at B grants it, A pairs itself with a one-time code that lasts a minute and can only become a host pairing, and that pairing ends with the grant. Agents is off for every device until a person at B grants it to that one. Without a desktop pairing, `ramu hosts add <address> <code>` uses a code from `ramu pair` on B. A pairs with B as a `host` device that B limits to six calls: start a thread, check, message or stop threads that pairing started, list project names, aliases and descriptions (no folder paths), and offer A's tools for review on B. Checking a thread returns its state and its latest reply, so A's agent sees what those threads report and nothing else. It holds no device permissions and receives no events, so it cannot read files, paths, Git, terminals, settings, the browser or any other thread. Every thread it starts gets at most B's **Most access for its threads** for that pairing (default Allow edits), B's own depth limit (two levels of agent-started threads) and an hourly limit of 8 threads and 20 messages. B checks all of these itself, whatever A sends. A asks the person before every start on another host and never sends uncommitted changes. A keeps the token in the OS credential store and renews it before it expires. **Forget** on A stops using it, and revoking the device on B ends it immediately. Hosts never sync settings or credentials.
- **Devices:** `ramu devices` lists them and `ramu devices revoke <id>` (or `all`) revokes, as does **Remove** in Settings → Devices & access. Revocation is immediate and closes open event streams.
- **Managing devices from another device:** a full-access device with the settings changes permission may list the devices, rename one, remove one (itself included) or every other phone and computer, make a pairing code (full access or view only) and answer nearby pairing requests (`DEVICE_MANAGEMENT_METHODS` in `packages/shared/src/devicePermissions.ts`). Viewers and host pairings are refused. It names a device by its exact id, never `all` or a prefix, and cannot remove a linked host or the host's own desktop, which is no paired device. It follows and withdraws only the codes it made. It cannot change any device's permissions or lifetime, the defaults, or how the host is reached. Each change is kept on the host (`device-changes.json`), shown there as a notification and under **Changes from other devices**, and printed by a headless host. The trade-off: a stolen full-access device with that permission could remove the other devices or pair a new one. It could already do that with a terminal on the host (`ramu pair`, `ramu devices revoke`), and the host shows each change. Set a device's settings changes permission to **Ask first** or **Blocked** to keep it from managing devices.
- **Credentials:** a device token expires after 30 days of inactivity (set `RAMU_DEVICE_TOKEN_DAYS` to a number of days or `never`). Paired clients renew the token weekly with `POST /renew`. The host retires the old token two minutes after the new one is first used. A token is also bound to a key the device holds: the desktop app and the phone each make an Ed25519 key once, keep the secret in the OS credential store (Keychain or Keystore on a phone), and name the public half when they renew. From that token's first use on, the host accepts it only with a proof signed by that key, fresh to within five minutes of the host's clock and usable once, for the connection, a renewal or a plain request. A token copied from a backup, a log or a relay is then useless on its own, and it cannot renew or swap the key either. A device paired before this keeps working with its token alone and binds at its next renewal, which the apps ask for within a day of updating; a device whose clock is far off reads the host's clock and tries again. Through a tunnel or Ramu Link the proof travels as a request header like the token. A host pairing made for agents (`ramu hosts add`) is not key-bound.
- **Browsers:** cross-origin browser access is off. `RAMU_BROWSER_ORIGINS` takes a comma-separated list of exact trusted HTTP(S) origins. Origin checks supplement bearer authentication.
- **Network:** expose the server only on a trusted LAN or VPN, or behind authenticated HTTPS such as your own tunnel. Plain HTTP sends bearer tokens and workspace data unencrypted. A tunnel address must be `https://`. Ramu can run Cloudflare's quick tunnel, Tailscale Funnel or ngrok itself with the person's own tool and account. It only reads the address the tool prints. While a tunnel address is set, a request from loopback (where a tunnel on this computer delivers) is limited by the visitor address the tunnel reports: `CF-Connecting-IP` behind Ramu Link or a quick tunnel, whose Cloudflare edge sets it, and otherwise only the last `X-Forwarded-For` entry, which the proxy appends. Those headers are ignored from any other address. Pairing by request is refused through a tunnel, so a device outside the network pairs with a code or through the Ramu account. The tunnel's provider terminates HTTPS and can read the traffic. The mobile app does not pin TLS certificates, so use a trusted HTTPS certificate or your own authenticated VPN.
- **Dev servers on the phone:** **Open on this phone** for a page on the host's loopback asks the host for a forward. Only a full-access phone with the browser permission can ask. The forward is a separate listener on a fresh port of the address that phone's connection arrived on. It drops connections from any other address and answers only requests carrying the cookie set when the phone opens its one-time address, and that address works once. It reaches only the requested http port on the host's loopback (never Ramu's own), with the request addressed to `localhost` and the forward's cookie removed. A phone that reaches the host through a tunnel or its own loopback gets no forward. A forward closes when its viewer closes, after 30 minutes, or when the device is revoked or becomes a viewer, and a phone holds at most three. The forward is plain HTTP on that network, so use it on a network you trust, as with the dev server itself.
- **Live Activities through Ramu Link:** a host with no Apple key of its own (every host but one built with `RAMU_APNS_*`) hands its paired iPhones' Live Activity pushes to Ramu Link, which holds the Ramu app's Apple key. The host signs in with its Ramu account, and Link checks that session with the account service and allows 60 pushes a minute per account. A push carries the activity's token and its counts, state, language and times, never a thread's title or text. Thread titles on the Lock Screen come only from the phone's own updates, made from what Ramu already shows there. Link builds every field Apple receives itself, so a host can only update or end Ramu's own work activity, never send any other notification. The host keeps the tokens in its data folder (`mobile-live-activities.json`, readable only by the user), and revoking the phone drops them. Hosts never start an activity: a phone takes back the start token an earlier version handed over, and the host deletes any it kept.
- **Webhook schedules:** a webhook schedule's address holds a random 24-byte token, and full-access devices are the only ones that can read it or its secret. Viewers see neither. Requests are checked against the schedule's signature (HMAC-SHA256 over the exact body, Vercel's HMAC-SHA1, Netlify's HS256 token whose claim is the body's SHA-256, or GitLab's token header) with a constant-time comparison, limited to 256 KB and 30 a minute per address, and logged with their outcome. What reaches the agent is the schedule's prompt plus the chosen fields, fenced as untrusted data with an instruction not to follow it. The run uses the schedule's own permission level. A GitHub webhook Ramu creates uses the repository's existing account, and a `gh` call receives the secret through a private temporary file, never its arguments.

See [Headless server](guide/remote-hosts.md) for running a host.

Continue on another host is a person's action from an owner device: the device calls both hosts directly, viewer devices are refused, and paired hosts cannot reach the package, clone or start methods. The redacted conversation leaves the host, and can quote code and uncommitted content. Files do not.

Any process running as your OS user can reach the host's local socket with owner access, and Ramu cannot tell which tool called it. `ramu thread` commands are therefore trusted like you: they are labelled with the name given by `--as` and default to **Allow edits**, but are not a security boundary.

### Host pairing

A host paired with another as `host` may call only `hostThreads.start`, `status`, `message`, `stop` and `projects` and `hostTools.offer`, over calls-only sockets. Retries and operation keys pass the same check. A person at the asking host approves each start. Nobody at this host approves individual starts, and these choices follow from that:

- **Access ceiling.** Threads a pairing starts default to **Allow edits**. Raising the ceiling shows a warning, because the other host's agent writes the prompt and, if compromised, could run commands here at Auto or Full access.
- **What `projects` names.** `hostThreads.projects` answers with each project's id, name, aliases, description and Git author email, and this host's platform and architecture (such as `darwin` and `arm64`) so the asking agent can pick a host that can build the task, never folders, hostnames or hardware.
- **What comes back.** `hostThreads.status` returns the latest reply of threads that pairing started, so those threads can pass file contents back, plus their count of tool calls and their latest tool call's summary (secrets redacted, at most 200 characters), never tool input or output. The asking host reads it every five seconds while such a thread runs as one of its agent's helpers. `hostThreads.stop` interrupts only a thread that pairing started. The thread and its work stay here. Their reports reach the asking agent labelled as not coming from the person.
- **Limits.** 2 levels of depth, 8 threads and 20 messages per hour per pairing. The message count is kept in memory and resets when this host restarts.
- **Labels.** A thread shows this host's own name for the pairing. The other host's name for itself and its thread title are context only.
- **Revocation.** Revoking a pairing stops new calls at once. Threads it already started keep running, visible with their origin label, until stopped here.
- **Transport and tokens.** The token is in the OS credential store on the asking host and hashed here. Plain HTTP needs `--private-network`. On a headless host without an unlocked credential store, `ramu hosts add` fails with a message to unlock it, and nothing is stored in plain text.
- **Offered tools.** `hostTools.offer` carries the setup of the tools the asking host keeps on other hosts (sources, commits, server addresses, which tools are on) and the ones it removed, never keys. This host keeps only what is meant for it as items to review in Customize or `ramu tools`. Nothing installs or is removed until a person here does it. The answer is this host's own name and tool-sync id, not its identities, projects or tools. It is refused when **Agents** is off for that pairing.
- **Agents permission.** A device granted **Agents** may pair its own computer here without a code from a person. That code is one-time, lasts a minute, only becomes a host pairing, and the pairing ends with the grant.

Test devices give agents fixed operations on simulators and emulators, not a shell: every command is a fixed program with checked arguments, app files must resolve inside the thread's workspace, logs are filtered to the launched app with known secrets removed, and a device belongs to one thread at a time.

## Deploys

- **Uptime checks:** the host sends one `GET` every five minutes to the live address saved in the Live app sheet (or the lasting address of an app run on this computer), on the health path from `ramu.json`, which can only name a path on that same origin. It sends no credentials or cookies, reads no body, stops after 10 seconds and follows redirects only on the same host name. When the address gives no answer at all, one `HEAD` request to github.com tells whether the host itself is offline. The incident thread is told where to find the latest deploy. Reading logs or rolling back goes through `platform_cli` and its cards.
- **Apps published from this computer:** **Run on this computer** runs the app in a Docker container with no host network, `no-new-privileges`, none of Ramu's environment, and only its port published to `127.0.0.1` on a random port. Its tunnel is a separate process pointed at exactly that port, of the kind pages opened to anyone use, so the app gets a hostname of its own that shares no origin with Ramu's address. Tailscale Funnel and a fixed ngrok domain are refused. Ramu refuses to publish without Docker, since a process running as the person's user could reach Ramu's local socket. Stopping removes the tunnel before the container. Of the host's saved variables, the container gets only those the app's code reads, passed by name to `docker run` with their values in that one process's environment, never on a command line. Without Docker, only when the person chooses **Run without Docker** after the sheet says it has their permissions, a Node app's own scripts run as a program in its own process group with the project's variables and none of Ramu's environment, listening on loopback. It can read what the person can, so it is meant for code they trust. A lasting address uses a named Cloudflare Tunnel whose ingress names only the app's hostname and one loopback port, ending in a catch-all 404. Ramu's own port and wildcard hostnames are refused, the person's Cloudflare token and the tunnel's token stay in the OS credential store, and the tunnel token reaches `cloudflared` through its environment, not its command line.
- **Identities and moving settings:** an identity holds only references to accounts already connected on its host, so no credential is copied or moved. Identities, their pins and account assignments are host settings that a paired device edits only with its settings changes permission. **Copy settings**, **Export settings** and **Import settings** carry only the portable groups (preferences, model sets, rules for every project or an identity, identities' Git author and rules, and everywhere notes when chosen), never executable paths, credentials, account tokens, workspace state or device permissions. An identity's accounts travel as their kind and sign-in email and are matched on the receiving host, never as ids. The guardrail's **Continue as ‹other›** allows one action for ten minutes on the host itself.
- **Plugins:** a plugin is installed only after the person's review of everything it adds, at a pinned commit. A source from an index that names a signing key installs only a commit `git verify-commit` accepts against that key alone, and the default index's commits must carry Akalstack's key, which ships in Ramu. Clones are shallow, never run hooks or submodules, and accept only https, ssh or local paths (no `ext::` transports). A plugin's code runs only as an MCP server (with Shared MCP's approvals) or as its CLI through `platform_cli`. Hooks and other parts Claude Code or Codex run are listed and never run, and skill scripts are copied only with their own approval and never run by Ramu. Credentials are pasted or signed in only on the host, kept in its OS credential store, and reach only that plugin's MCP servers (as environment or headers), CLI (in its token variable, never as an argument) and data sources. Every occurrence in CLI output is replaced before the agent reads it. `platform_cli` refuses sign-in commands and token arguments, runs with an environment limited to the path, user, locale and shell variables and a home folder of Ramu's own, and runs only the plugin's declared read-only prefixes without asking. Every other command asks the person with a card, in every access mode. A data source calls one https origin fixed in the manifest or taken from the credential's address field, with the fields the manifest declares (others are refused), bounded in time and size. A POST must be declared read-only and is reviewed when the plugin is listed. An update that changes an MCP command, a credential, a read-only prefix or a script asks for approval again. An agent's `plugin_install` shows the same review as a card the agent cannot answer.
- **Deploys:** agents deploy only through `platform_cli` with a plugin's CLI. A command the plugin marks as a preview deploy runs without a card. One it marks as production asks the person with a card in every access mode, with **Allow production deploys in this thread** as the widest choice (there is no lasting allow), and runs the project's migrations first against the production database address saved on the host. That address is entered only on the host's own computer, kept in its OS credential store and never sent back to a client. Migration output is redacted before the agent reads it.

## CI

- **Set up CI** commits one generated workflow file on a new branch from a temporary worktree, with the repository's Git hooks switched off, and opens a pull request. Nothing reaches the default branch until the person merges it. Generated workflows pin actions to a major version and grant the job read access to the repository only.
- **Branch protection:** requiring CI before merge is a person's choice in Set up CI, made with the repository's existing GitHub account. Agents have no tool for it. Existing rules are only added to, never replaced.
- **Push watches:** a failing check on a pushed default branch is handed to the thread as external feedback, with its log tail redacted and an instruction not to follow commands in it.

## Isolated content

- **Theme preview:** the Code/Diff preview in the theme editor runs bundled Monaco code on its own `ramu-theme:` origin. It serves only the preview entry and bundled assets, cannot read workspace files, call the native bridge or reach the parent window, and accepts only validated palette and view messages.
- **Interactive content and artifacts:** agent-generated documents run in a separate `ramu-content:` origin with a restrictive content policy and cannot use the theme origin or any host API. See [Artifacts](guide/artifacts.md).
- **Artifact capabilities:** an artifact's page reaches records, AI, photos, notifications, a project folder or a thread only through messages its viewer forwards to the host, which checks that the page declared the capability, that the person allowed it, and its limits (records 10,000 and 20 MB per page, a daily model and notification budget, bounded run steps, writes and time). The page never receives credentials or another page's data. An image a page's AI asks for (`ai.image`) needs the AI grant, counts against its daily budget and sends only the prompt to a signed-in provider with image generation, never through a Shared MCP tool. Page runs use only the page's own tools. Records, fetched pages and tool results are passed to the model as data, deleting records needs the person's **Allow** in Ramu's own toolbar (not page code), and every run's record changes can be undone together. A project folder grant is read-only and confined to that folder after resolving links. Ramu data a page may read is read-only and limited to token activity totals, thread titles and states, and pull request summaries, each source allowed separately, never transcripts, files, credentials or settings. A page's plugin data source queries run on the host with the plugin's saved credential, only for data sources the page declared and the person allowed one by one, through the same request a dashboard makes, never from a share link. The page receives rows, never the token. Photos are stored without JPEG location metadata. A motion's music, sound effects and recorded voices are audio files a media account or a mapped Shared MCP tool returned, kept with the version and mixed on the host. A motion's narration is spoken on the host by its own speech command (`say` on macOS, `espeak-ng` on Linux), run as an argument list with the words in a temporary file, and never sent anywhere.
- **Docs, decks, dashboards, designs and motions:** these are drawn on the host into HTML with no script, network or capability, and exported (PDF, PowerPoint, Word, images and video) by the host's own offline preview browser. A dashboard's live table reads only its own project: its deployments, usage, uptime, thread titles and states or pull request summaries, or one CSV or JSON file inside the project folder, resolved like a project folder grant (links followed, `.git` refused) and never written, or the records of an App artifact in the same project, read only. An ability mapped to a Shared MCP tool sends it only the prompt, and for a long read the named files' text or for an image edit the named images, through the thread's own Shared MCP access and approvals. A table from a Shared MCP server calls only a tool the server marks read-only, through the gateway bound to the dashboard's project, so only servers and tools approved for that project in Shared MCP are reachable. No confirmation is asked for these reads. A table from a **plugin's data source** (such as Grafana, Amplitude or Salesforce) reads only for a kept dashboard you allowed to read that source, one grant per dashboard and source, given on the dashboard (**Allow**) and taken back in its menu. A dashboard naming a source it was not allowed shows the table empty. The request is the one the plugin declares (see **Plugins** above), at most 5,000 rows of the columns the table names, each cell cut to 500 characters. A sign-in slot (Salesforce's) runs OAuth with PKCE through the person's own client: the browser on the host returns to a loopback-only listener on port 7417 that Ramu opens just for that sign-in, checks the `state` it sent, and exchanges the code with the verifier. The tokens are kept like a hosting token and renewed at the plugin's token endpoint. The host's agent activity totals (turns, cost and tokens per provider and day) can be read by any dashboard, never transcripts. A dashboard in no project reads only those totals and records of an App in no project. An artifact file filled from an attachment can only name an image attachment its own thread holds. **Present** may ask to know the displays (the browser's window management permission, granted only to Ramu's own window) and opens one blank presenter window that Ramu fills with text. That window cannot navigate or open others.
- **Artifact share links and webhooks:** a share link is an unguessable token for devices already paired with the host. Viewer-role devices may open it and, when the link allows, add records or (for a link that names its editor, on a doc, diagram or deck) save the text as that person, merged like any edit, with each version naming them, and take part in live typing on that one artifact, nothing else. Links expire after 30 days unless renewed and can be revoked. An artifact webhook is an unguessable address accepting records for one declared collection, checked against its fields and limited to 30 requests a minute.
- **Pages open to anyone:** a page opened to people without Ramu runs on its own loopback listener on a random port, reached through its own tunnel process, so it has a hostname that shares no origin, port or cookie with Ramu's API. The listener answers only `GET /` (and `HEAD`) with that page's exported bytes under the page's content policy plus `sandbox allow-scripts`, `nosniff`, `no-referrer`, `X-Frame-Options: DENY` and `no-store`. Every other path is 404 and every other method 405. Only a page that declares no capability can be opened, and one whose newer version declares any answers 410. Tailscale Funnel and a fixed ngrok domain are refused, since they would serve the page under the host's own name. Closing it stops the tunnel and the listener.
- **Publishing artifacts:** a page with records or AI cannot be published. A static deploy sends only the page's exported HTML to the platform the person chose, on their own account: GitHub Pages through the saved Git hosting login, and Cloudflare Pages by running `wrangler pages deploy` through the Cloudflare CLI plugin, as `platform_cli` runs it (its token in the environment, a home folder of Ramu's own, the token replaced in any output shown). Platform error bodies from GitHub are not shown, since they can echo request details.
- **Artifact runs beyond the artifact:** web search sends only the query, to DuckDuckGo, through the same vetted DNS as page fetches. Shared MCP servers are offered to a page run only when the person allowed that server for that page, through a gateway bound to the page's model login and project, and every call is confirmed in Ramu's own toolbar, except tools the server marks read-only (MCP's `readOnlyHint`) on a server the person separately allowed to read without asking for that page. The hint is the server's own claim, so the choice is per server and off by default. Runs nobody started from a device load the page on the host offline, in the sandboxed preview browser, where it can only read its own records.
