# Thread state visibility

Status: partially implemented. Remaining summaries, recovery checks and acceptance work are listed below. Source inspection and synthetic/browser checks do not establish live-provider or native-device acceptance.

## Human need and delivery

A person can identify what a thread is doing through its indicator and status information, with short visible labels on mobile and per-thread popover details on desktop. Keep Ramu's dots, spinners, clocks, row layouts, navigation and existing accurate labels. T3 is a reference, not a requirement to copy its sidebar or vocabulary. No desktop or mobile sidebar redesign is needed.

**Easier for the person:** A glance or hover answers what a thread is doing without opening it.

Start with one shared presentation mapping and platform-specific presentation. Desktop keeps its existing dots, spinners, clocks and quiet age rows, with no permanent text label added to each row. Expose a thread details popover from the individual thread row/indicator, reachable by hover and keyboard focus, with click/keyboard activation for interaction. Include a short status label inside the popover alongside useful branch and checkout context. Thread status must not require hovering the project. Mobile keeps its icons and adds a short visible label in existing row metadata where useful, because hover is unavailable. Reuse existing text when it matches the meaning; shorten only for space. Keep titles readable, preserve actions and leave full request/goal details in their existing surfaces. Do not add a display-mode setting for this first delivery.

## Comparison and evidence

T3's [current sidebar](https://github.com/pingdotgg/t3code/blob/3ff5b3c82a62baddc0c2b1b227e9d3a06190c426/apps/web/src/components/Sidebar.tsx#L1664) explicitly labels working threads **Goal** when their goal is active and **Working** otherwise. It also presents Waiting, Approval, Input, Limited, Failed and unread Done. Those labels explain otherwise similar indicators; they do not require Ramu to adopt the same wording or organization.

T3's [native goal integration](https://github.com/pingdotgg/t3code/pull/15592) uses provider-owned Codex/Claude goals and tracks automatic continuation. Its [goal contract](https://github.com/pingdotgg/t3code/blob/3ff5b3c82a62baddc0c2b1b227e9d3a06190c426/packages/contracts/src/orchestrationV2.ts#L838) distinguishes active, paused, blocked, usage-limited, budget-limited and complete, with optional usage data. Ramu already has its own persistent [Goals](GOALS.md), evidence checks, verification commands, continuation limits and pause/limit distinction. A provider token budget and Ramu's continuation-turn cap are different controls; do not rename one to imply the other.

The gaps in Ramu are presentation and summary coverage:

- Desktop [`TaskStateIcon`](../apps/web/src/sidebar/projects/TaskStateIcon.tsx) shows a spinner, input/error/unread dot, limit clock or age. Its accessible labels already include **Agent working**, **Waiting for your input**, **Agent failed** and **Finished, not viewed yet**. Retain this compact model and existing meanings; make richer information available through each thread indicator's popover instead of adding persistent desktop labels.
- Mobile [`ChatRow`](../apps/mobile/src/components/ChatRow.tsx) retains icons, title, age and a preview. It now shares visible lifecycle labels and includes the full status and offline qualifier in its accessible name; remaining device acceptance is tracked below. Preserve this layout and improve its status text and accessible description.
- [`threadActivity`](../packages/shared/src/chat/threadActivity.ts) already combines connection, input, provider wait, parent work, helpers, goals, advisor and queue inside an open thread. Mobile preserves turn-limit and verification states; audit remaining desktop callers and the generic working entry that can lead while a goal is active. List rows lack that richer context.
- [`Task`](../packages/shared/src/types/workspace.ts) now exposes compact goal context and the latest root execution outcome, and [`hostInboxInput`](../packages/shared/src/hostOverview.ts) carries it into Inbox. [`syncTaskStatus`](../apps/server/src/agent/sessionRecorder.ts) considers running sessions/helpers but not active goals between turns or verification claims. [`HomeAgents`](../apps/web/src/HomeAgents.tsx) now retains active and held goals in their appropriate groups. Remaining aggregate helper and revision context belongs in these existing projections.
- [`agentNotifier`](../apps/desktop/src/main/agentNotifier.ts) already suppresses finished notices for continuing/blocked goals. Preserve that protection and audit consistency with list grouping and mobile notices; do not assume notification behavior is wholly missing.

## Proposed state and copy mapping

The full status descriptions below retain existing Ramu copy: **Working toward goal** already exists in the goal bar, and **Agent working** names the ordinary working indicator. Desktop shows a short status label inside the thread details popover, with these full descriptions as supporting context and accessible names; mobile can use the same short text beside its existing icon while retaining the full meaning in details and accessible descriptions. No copy changes are needed solely for T3 parity.

This table describes the semantic mapping and full status wording, not permanent desktop row labels or new persisted `TaskStatus` values. Higher-priority input or a provider hold can coexist with a goal; keep that goal available in existing details. An offline marker qualifies last-known state rather than claiming fresh activity.

## Desktop thread details popover

Keep desktop rows compact with the current dot/spinner/clock. Hovering a thread reveals its own context card; keyboard users can focus and activate the same information. The **short status label belongs inside this card too**, using the mapping above. The existing project hover remains a project overview; it cannot substitute for a thread's actual checkout.

Present enough context to answer “What is happening, where is it working, and do I need to act?” in this order:

- **Thread title and short status:** show the full title and a label such as Working, Goal, Approval, Needs input, Limit reached, Failed or Stopped beside its indicator. Retain existing accurate wording when it fits. Add one concise explanation only when the label needs context; do not repeat the same status in several lines.
- **Checkout and branch:** show Current checkout or Worktree using existing Ramu wording, the workspace name when applicable, and the actual branch for each bound repository. A current-checkout thread follows that checkout's current branch; never substitute the project's default branch or an old launch branch. Show detached HEAD, no commits or a plain folder truthfully instead of inventing a branch. A reused worktree keeps its actual binding and may say Shared workspace when another thread uses it.
- **Location:** show project/repository and a readable working-folder path, plus the host name for remote or ambiguous contexts. Resolve the exact thread binding, not whichever workspace happens to be open. Long paths remain selectable/copyable in details without forcing an oversized card. For several repositories, show a compact repository/branch summary and an existing details route for the rest.
- **Action context, only when applicable:** a bounded goal objective, the required input/approval and source, a failure/stall reason, a pending/failed verification, or the expected limit reset and whether auto-resume is on. Link to the exact existing request, goal, error or verification detail. A paused goal explains that it needs explicit Resume.
- **Activity context, only when it helps:** current provider/model, active helper count or queued messages when relevant to where work runs or why it is waiting. Use reported/current configuration and distinguish a queued provider change. Do not list completed helper history, token counters or the full transcript.
- **Freshness and recovery:** show offline/last-known context or workspace setup failure when relevant. Use the existing last-activity meaning; do not call it completion time. Missing context should say unavailable or loading, never imply Current checkout, no goal or a successful run.

Keep one primary route such as Open thread or Review request; use existing thread/workspace details for deeper inspection. Hovering is read-only: it must not switch branches, create a worktree, resume work, refresh every repository or mark the thread read. Do not duplicate the full sidebar action menu or add branch editing here. The card stays open while moving the pointer into it, supports focus and Escape dismissal, stays within the window and closes on drag/rename or switching its host/thread. Ordinary row click still opens the thread; activation of card controls must not also trigger that row click.

Reuse [`ProjectHoverCard`](../apps/web/src/sidebar/projects/ProjectHoverCard.tsx) interaction and visual conventions through app-level composition, alongside existing [`RepositoryBinding`](../packages/shared/src/types/workspace.ts), `tasks.bindings`, workspace stores and Git status queries. Reuse cached host/task/repository-qualified values and fetch missing branch/location details only while the card is open, with bounded queries and cancellation/stale-response protection. Changing the current checkout's branch must update the card. Do not preload Git status or every transcript for all sidebar rows, add another poller or expose one host's cached branch under another host's thread.

## Priority and coexistence

Keep the current activity model's priority of pending input, provider hold and live work, qualified by connection freshness. Within pending input, approvals precede questions for the compact primary label; details retain every request. When parent work is active, an active goal specializes its working label. Active goals remain unfinished between turns and while verification is pending.

After live work, show actionable goal holds, then latest stopped/failed outcomes, then finished/unread or quiet idle state. Failure must remain discoverable when the same error blocked a goal; display Agent failed with the goal's reason in details rather than losing the error behind generic blocked copy. User pause/stop prevents future continuation; a still-finishing turn is not silently declared stopped. Keep other meaningful states as secondary detail in the existing activity surface, not a row full of badges.

Unread, pinned, marked done and archived are independent organization/read properties. Mark done is not Stop, and a finished turn is not a completed goal. Maintain existing organization behavior without hiding independently running work. Advisor activity and a long-running development server alone are not evidence that the user's task is unfinished. Unknown native dependencies remain generic rather than inferred from assistant prose.

## Architecture and existing services to extend

Follow [Architecture](ARCHITECTURE.md), [UI](UI.md) and the [root product guidance](../AGENTS.md#product-design-and-architecture). Extend existing types, summaries and pure event folds; do not introduce a parallel lifecycle store or expand the persisted task enum just to style rows.

The execution server owns current goal/request/provider/helper facts and revision-safe summaries. Extend existing agent/task overview methods behind the typed API, with additive optional fields for older hosts. Reuse `GoalManager`, `SessionStore`, `SessionRecorder`, provider-wait, helper ownership/capabilities and existing snapshots. Fold once through shared pure helpers, then reuse the same meaning in desktop sidebar/Home/Inbox, cross-host summaries, mobile Threads/Inbox and open-thread activity. Keep device connection freshness, unread state, drafts and uncertain outbox delivery on the device.

Summary reads must not require opening every transcript or making a per-row goal/request RPC. Include host/task/session identity and enough revision/currentness information to reject late snapshots. Reconnect and rewind replace discarded state; old progress cannot resurrect stopped or completed work. Missing fields from an older host mean unknown context, not no goal/no request. Show existing generic status with an accessible explanation until authoritative details are available.

Compose reusable status presentation outside `apps/web/src/components/ui/`; reuse existing dot/spinner/clock primitives, popover components and semantic tokens. Desktop keeps indicator-only rows: the thread row/indicator exposes the thread details popover specified above, including its short status label, branch/checkout/location and relevant action context. Hover/focus reveals information; click/keyboard activation keeps interactive content operable. Preserve a reachable trigger when row actions appear, avoid nested buttons inside a row button, and opening the popover must not accidentally navigate or mark a thread read. Keep project hover information; thread information must also be independently reachable. On mobile, reuse `ChatRow` metadata space for short labels and native controls/details for explanations. Keep row actions, swipe behavior and the current navigation hierarchy.

## Acceptance and validation

Representative task: scan concurrent threads for a login change pursuing a goal, an ordinary documentation edit, an approval, a question, a provider limit, a user pause, a stalled goal, a turn-capped goal, a failed run, a stopped run and a finished unread result. On mobile, identify which needs action and which will continue from icons and short labels. On desktop, inspect the same information from each thread indicator popover without opening the conversation or relying on project hover. Open the correct request, answer once, return and observe the updated indicator/text. Let the goal pass between turns and await verification; it must never appear finished during those gaps. Read the finished result and verify that its unread dot clears without marking the objective complete or moving an unrelated thread.

Desktop context acceptance: compare two threads in the same project, one on Current checkout and one on an isolated worktree, plus a reused worktree, plain folder, detached checkout and remote host. Hover/focus each row and identify its short status label, exact branch and working location without opening it. Change the current checkout branch and verify the card updates while the isolated worktree retains its own branch. Cover missing bindings, setup failure, multiple repositories, offline cached data and a late response after moving to another thread/host. Card actions and keyboard dismissal preserve row navigation and unread state.

Use existing shared/server/web/mobile test directories. Add focused behavior tests for priority/coexistence, idle versus goal continuation, pending/failed verification, stopped versus failed, active children after parent idle, advisor exclusion, pause/stop races, server queue versus uncertain outbox, mark-done independence, missing summary fields, stale snapshots and host ID collisions. Reuse current goal, provider-wait, helper, hostInbox and notifier tests. Add integration coverage where the overview/API boundary changes; do not create another e2e suite.

Run tests and typechecks for each affected package. Desktop-facing implementation requires `pnpm build` followed by `pnpm test:desktop-smoke`, with no rebuild during smoke. Validate existing layout with long titles/translations, narrow sidebar/phone widths, popover hover/focus/activation/dismissal, row actions, keyboard focus, VoiceOver/TalkBack, large text, light/dark and reduced motion. Documentation changes require formatting and link checks.
