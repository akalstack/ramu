# Microphone input and composer suggestions

Proposal, 2026-10-18. All implementation and acceptance below remain unfinished. Add speech-to-text into Ramu's existing mobile and desktop composers, preserve native keyboard assistance, and improve the existing command/file/skill pickers where an audit finds gaps. Use T3 Code as a reference while keeping Ramu's architecture, navigation, controls and design tokens. Move shipped behavior into [UI](UI.md) and the [mobile guide](../apps/mobile/README.md), remove completed work, then delete this plan when finished.

## Delivery

A person taps the microphone in the existing composer, dictates, reviews the inserted text and sends through the normal action. Ship this complete flow on each verified local platform without waiting for every adapter or contextual-picker improvement. Keep system language/input defaults and contextual readiness/setup actions; model assets and input-device selection stay in details. Verify draft preservation and cancellation during a real composing task. Ordinary typing and system keyboard assistance remain usable when local recognition is unavailable. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

## What the autocomplete actually is

Without the exact screen/recording, the observed effect cannot be identified conclusively. Distinguish these cases:

| What appears | Owner and evidence | Ramu scope |
| --- | --- | --- |
| Word candidates above the iPhone keyboard, or gray inline word/phrase predictions accepted with Space | iOS predictive text, subject to keyboard settings and language support. See [Apple's predictive text guide](https://support.apple.com/en-gw/guide/iphone/iphd4ea90231/ios). | Preserve native text-input behavior. Do not build a model service to reproduce a keyboard feature. |
| Commands, skills or files after typing `/`, `$` or `@` | T3-owned contextual pickers, described in its [composer guide](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/docs/user/composer.md). | Ramu already has `/` commands/skills and `@` files on mobile and desktop. Audit parity and improve missing triggers, selection and availability instead of replacing the system. |
| An app-generated continuation of an ordinary sentence | No general model-generated prose completion is established by the inspected editor/voice sources. | Keep it out of this implementation unless a specific reference establishes the behavior and a separate product decision approves its latency, privacy and cost. |

T3's native iOS editor uses `UITextView` and exposes autocorrection/spellcheck controls. It explicitly avoids assigning an unchanged selection because that resets the keyboard's predictive/autocorrect context. This is source evidence of preserving OS assistance, not a bespoke text-prediction model. See the pinned [native editor](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/apps/mobile/modules/t3-composer-editor/ios/T3ComposerEditorView.swift).

## T3 Code microphone reference

Inspected `pingdotgg/t3code` at [`9c161462c94f7d9d6d9169da5c841457cbadf213`](https://github.com/pingdotgg/t3code/commit/9c161462c94f7d9d6d9169da5c841457cbadf213) on 2026-10-18. These are facts about that revision, not every released version. Review licensing before copying code.

- The [voice architecture](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/docs/internals/voice-input.md) treats transcription as a draft edit, with capture/transcription supplied by the client. It records draft ownership and revision before insertion. Its implementation documents supported local iOS transcription; environment-backed transcription is not implemented there.
- The [iOS binding](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/apps/mobile/src/native/voiceTranscription.ios.ts) probes Apple availability and locale, prepares the language model and discards aborted results. The generic [platform binding](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/apps/mobile/src/native/voiceTranscription.ts) returns unavailable.
- Its [shared controller](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/packages/client-runtime/src/voice-input/controller.ts), [transcription contract](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/packages/client-runtime/src/voice-input/transcription.ts) and [composer adapter](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/apps/mobile/src/features/voice-input/useVoiceInputController.ts) distinguish cancellation from actual native completion so cleanup does not race a still-running transcriber.
- The [composer guide](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/docs/user/composer.md) describes record/confirm, insertion at the original selection, a five-minute cap, local model preparation, temporary audio deletion and review before submission.

Ramu's proposed improvements are desktop support, an explicit speech-language choice, capability-based Android support, consistent draft protection across hosts/windows, and native keyboard regression coverage. These are intended outcomes, not claims of better recognition accuracy or shipped platform parity.

## Ramu architecture and existing pieces

- Mobile uses Expo/React Native. `apps/mobile/src/components/Composer.tsx` owns draft editing, selection, mentions, attachments, queue/steer, models and measured keyboard layout. Its main message input does not explicitly disable autocorrection; the `autoCorrect={false}` nearby belongs to the model-search field. Do not assume the current composer needs a global autocorrect switch flipped.
- `apps/mobile/src/components/ComposerSuggest.tsx` and `apps/web/src/composer/ComposerSuggestions.tsx` already fetch host-scoped files and skills and handle command/file completion. Preserve their scope, permission and loading/error behavior.
- Desktop is Electron around `apps/web`. Native device operations belong in Electron main/preload; server work uses named methods through the existing client runtime. A paired remote server is not the owner of the user's microphone.
- `packages/shared` holds pure cross-platform domain helpers. `packages/client-runtime` is currently a Node transport client, not a universal mobile/audio runtime. Put the platform-independent dictation state machine and insertion helpers under a new `packages/shared/voice/` export; do not copy T3's package placement or add native dependencies to shared code.
- Desktop device preferences use `deviceState`/`deviceStorage`; mobile device preferences use its local storage/settings model. Voice and keyboard choices belong to the input device, not host `AppPreferences`, provider account settings or the server settings fanout. Audio never enters the agent event log, normal attachments or offline outbox in this scope.

## Experience and defaults

Add one **Dictate message** microphone button to the existing composer action row on mobile and desktop, available in both New thread and an existing thread. Use mobile's existing icon/button/sheet and desktop's app-composed controls outside `components/ui/`; retain Ramu spacing, semantic colors, focus states, touch targets and reduced-motion behavior. At narrow widths reflow existing actions rather than cover the model, usage chip, activity/limit tray or Send.

The flow is **Start recording → Stop and transcribe → review/edit text → normal Send**. A second explicit **Cancel recording** action discards the take. Show a small recording status with elapsed time, microphone activity and labels; a waveform is optional and must not imply recognition progress. Transcribing uses a labelled busy state, not a fake percentage. Recording controls stay visible with the keyboard open; do not replace the main thread's Stop/Interrupt button with a microphone action.

Dictation may edit a draft while an agent is working, then use existing queue/steer submission. While recording/transcribing, block this draft's Send/Queue/Steer and temporarily freeze its editor to avoid ambiguous edits; independent stop/approval/navigation actions remain usable. Switching thread/host or leaving the recording screen cancels the take and keeps the old draft. A limit hold does not prevent preparing a draft, and recording does not resume a held agent. There is no hands-free mode, always-listening mode, automatic submission or spoken execution of commands.

Use an initial five-minute recording cap plus enforced byte/memory limits. At the cap, stop capture and show **Recording limit reached** with explicit **Transcribe** or **Discard**, never send. Calls, audio-route loss, app backgrounding, device lock or capture failure cancel safely and preserve existing text. The device stays awake only while actively recording, then releases that request. Denied/revoked permission produces a specific explanation and OS-settings action; never repeatedly prompt after denial.

Add a **Voice input** group to each client's existing composer/input settings section, searchable for microphone, dictation, speech and voice. Do not introduce a new navigation destination just for dictation.

| Device setting | Recommended default and behavior |
| --- | --- |
| Show microphone button | On when a supported local engine is ready; show a setup action when local capability can be installed. No permission request until the user starts setup/recording. |
| Speech language | **System language**, resolved against installed/downloadable engine languages, with explicit supported language choices. Test Indonesian, English and mixed technical speech; never silently force English. |
| Transcription | **On this device**. Use the native local engine when supported; otherwise offer an explicitly installed local engine. No automatic cloud fallback or remote audio upload. |
| Microphone | **System default**; desktop can select a permitted input device where supported. Do not enumerate/access microphones before OS authorization permits it. |
| Recording retention | Temporary only; no audio history or save-by-default option. Inserted text follows ordinary draft persistence. |

Language-model downloads require an explicit action with size/location/progress/cancel/delete information. Separate speech model assets from the agent's provider/model picker. Show a truthful readiness matrix: device unsupported, language unsupported, model needed, permission needed, ready, recording, transcribing and cleanup pending. Unsupported devices still support ordinary typing and any system keyboard dictation; local unavailability must not block the composer.

## Platform adapters

Define narrow `VoiceCapture` and `VoiceTranscriber` adapters with capability discovery, prepare, start/stop/cancel, final transcript and disposal. Prepare and bind the engine/language once per take. Report typed failures and separate **recognition unavailable** from **microphone denied** and **model download failed**.

**iOS:** prototype an Expo native-module adapter for Apple's on-device transcription, checking hardware/OS/language support rather than only an iOS version. Apple's [SpeechTranscriber documentation](https://developer.apple.com/documentation/speech/speechtranscriber) distinguishes available, installed and downloadable models. Evaluate a maintained dependency versus a small Ramu-owned module against Expo/RN compatibility and packaging; do not import T3's private native bindings blindly. Add only the usage descriptions/permissions required by the chosen APIs. Native functionality needs a development/production build, with a safe unavailable adapter in Expo Go and mobile web where necessary.

**Android:** use an explicitly on-device recognizer only when the device and requested language support it. Android exposes [on-device recognition discovery and creation](https://developer.android.com/reference/android/speech/SpeechRecognizer), with lifecycle cleanup requirements. Do not call the generic recognizer and advertise offline operation when it could use an OEM/cloud service. A streaming native implementation can feed final text into the same controller without forcing a temporary audio-file path. For unsupported languages/devices, offer the verified local-model adapter or an unavailable explanation; do not silently change privacy behavior.

**Desktop:** ship the same microphone UX, not just a hint to use OS dictation. Electron main owns permission checks, the operation lease, temporary files and the local recognition helper. A trusted shell capture adapter obtains audio only after the user's action; main validates the sender origin/window and a recording token. Browser tabs, Interactive Content, provider tools and remote hosts never inherit microphone permission from the shell. Follow [Electron microphone permission APIs](https://www.electronjs.org/docs/latest/api/system-preferences), packaged usage descriptions and platform entitlements as required.

Prototype a signed native Apple adapter on supported macOS and a bounded local helper based on [whisper.cpp](https://github.com/ggml-org/whisper.cpp) for supported desktop platforms/languages. Choose the actual engine/model after compatibility, licensing, memory, CPU and recognition checks on supported hardware. Use a managed/versioned executable and checksum-verified model download with cancellation; never download/execute arbitrary user-supplied helper commands. Run recognition outside the renderer/main event loop with timeout, bounded IPC and crash recovery. Linux and Windows require native capture/package acceptance and an explicit support matrix; they are not automatically supported because the UI renders. No claim that Electron's Web Speech API offers a reliable local backend.

Start with local iOS and macOS adapters, then Android and other supported desktop platforms behind capability checks. These remain acceptance obligations; do not declare cross-platform work complete after only an iPhone demo. Cloud/BYOK transcription, remote-host transcription, original-audio attachments, text-to-speech and automatic AI transcript rewriting are deferred product decisions outside this implementation.

## Shared state, insertion and resource ownership

Use one device-level active recording lease across composers; on desktop main arbitrates multiple windows. Bind each take to an opaque operation ID and `(device/window, host, draft owner, draft revision, selection)` rather than just a thread ID. New-thread drafts also need stable ownership. Capture the whole text revision and selected range before recording; mention/reference metadata must remain associated with that revision.

The pure controller models idle, preparing, recording, transcribing, cancelling/disposing and settled/error states. Cancellation immediately makes a result ineligible for insertion, but keeps resource ownership until native work has actually settled. Late callbacks cannot release another operation's lease or mutate another draft. If a native call cannot stop, discard its result and defer file cleanup until it stops using the file. Prevent a new conflicting take until capture/recognition resources can be reused safely.

On success insert once at the original selection, replacing only that selection and preserving surrounding whitespace/text, attachments and mention tokens. Use a single undoable edit; measure the composer's resulting multiline height even if it is not focused. Before applying, compare operation, owner, revision, text and selection validity. A cross-window edit, restored draft, host/thread change or accepted suggestion invalidates automatic insertion. If the original draft remains open but changed, hold a temporary **Transcript ready** preview with **Insert at current cursor / Copy / Discard**; never overwrite new text. On owner navigation/cancellation discard the take rather than offering to insert into another thread.

Recognized text is plain draft text. It cannot execute slash commands, answer approvals or invoke tools on arrival. Only the existing explicit suggestion selection and message submission paths can do so. Do not perform an extra model rewrite that changes commands, file paths or identifiers silently.

Stop capture and release OS audio resources on all exit paths. Delete temporary audio after transcription/cancellation and clean orphaned voice-specific temp files on next startup, scoped to an owned directory. No audio in logs, crash payloads, server attachments, provider requests or phone outbox; no retry that uploads a take elsewhere. Persist only the resulting accepted draft through normal mechanisms. Do not restore an interrupted recording or resume the microphone automatically after restart. A disconnected workspace host can still permit local transcription, but normal send/outbox behavior remains explicit.

## Keyboard predictions and app completion work

Preserve native iOS/Android predictions, autocorrect, replacement, selection and keyboard dictation in ordinary prose. Follow system keyboard controls; do not claim an app toggle can force predictions that the OS or third-party keyboard disables. Avoid resetting unchanged selection/text, remounting the editor on each keystroke or rebuilding attributed content in a way that loses marked text. Keep search/code-oriented inputs' existing autocorrect decisions separate. Audit the main controlled/styled `TextInput` and only consider a native editor extension if a reproduced platform bug requires it; do not replace the entire composer to imitate T3.

Ramu already has contextual autocomplete. Audit `/` commands/skills and `@` file menus in both New thread and existing threads. Add `$` as an explicit skill trigger if confirmed compatible with Ramu's provider/skill insertion contract; retain `/` skill discovery and never interpret normal currency/shell text as a command automatically. File/skill lookup remains scoped to the selected host/project/workspace with visible offline, empty and unsupported states. Reuse existing host methods; no per-keystroke full transcript or generic LLM prediction call.

Unify only pure trigger parsing, range replacement and choice identity under shared helpers where duplication actually causes drift; preserve platform UI adapters. Keep token boundaries/escaped syntax and multi-repository file identity intact. Avoid stale host results, repeated full catalog loads and an always-visible suggestion strip. Touch selection should not unexpectedly dismiss the keyboard or lose the caret; desktop supports Arrow keys, Enter/Tab and Escape without submitting a message while a choice is being accepted.

Native keyboard/IME composition wins over app pickers. While marked/composing text is active, suppress app acceptance/interception so Enter/Space first commits the OS candidate. A pasted or dictated `/`/`@`/`$` is text until intentionally used through the normal controls. Do not duplicate the OS word-candidate bar inside Ramu, and do not add an AI prose-completion toggle without demonstrated need.

## Implementation and verification

1. **Capability/permission spike and keyboard baseline.** Record current main-input behavior on actual iOS/Android and desktop. Choose capture/STT dependencies with hardware/language/build evidence, local-processing guarantees and license review. Document supported OS/device/language combinations, permission manifests and model packaging. Keep typing functional while dependencies are unavailable.
2. **Pure controller and device settings.** Add shared state/insertion/cancellation helpers and typed local adapter contracts. Integrate device-local preferences through existing desktop/mobile storage; do not fan them out to hosts. Implement lease, operation ownership, revision checks, bounded duration/data and cleanup contracts with fakes before native UI wiring.
3. **Mobile and desktop adapters.** Implement local iOS/macOS capture/transcription, narrow Electron main/preload APIs and safe capability fallbacks. Follow with verified Android/local-helper and other desktop adapters. Add signed/bundled helper/model lifecycle, language preparation, interruption/revocation handling, resource disposal and orphan-temp cleanup. No server API/audio transport is necessary for device-local transcription.
4. **Composer UI on both surfaces.** Compose the microphone, recording/cancel/transcribing states, readiness/settings actions and draft review into New thread and thread composers. Preserve queue/steer, limit/activity/usage rows, selection, undo, attachments, accessibility and keyboard measurements. Add English/Indonesian copy, focus restoration and configurable desktop shortcut through the existing shortcut system without claiming an untested global key binding.
5. **Contextual completion parity and keyboard fixes.** Reuse current suggestion components, add any verified missing `$`/first-message behavior and fix only reproduced caret/IME/prediction regressions. Keep OS predictions separate from app completion and avoid general AI typing suggestions.

Focused shared tests must cover draft revision/owner changes, selection replacement and token boundaries, empty results, one-time insertion/undo, cancel versus late native completion, lease contention, model/download/permission failures, time/data limits and cleanup after failures. Adapter integration tests cover process death, cancelled native calls, permission revocation, file lifecycle and a guest/remote sender failing to access desktop capture. No real recordings or private transcripts should be committed as fixtures.

Focused mobile/web tests cover New thread and existing-thread targets, keyboard focus/height after multiline insertion, microphone states, disabled submission, queue/steer after review, host navigation, stale transcript preview, language readiness and keyboard/picker precedence. Existing suggestion tests should be extended for IME, trigger ranges, async host switching and hardware keyboard acceptance rather than duplicating the implementation.

Run tests/types for touched shared/mobile/web/desktop packages. For desktop-facing changes run `pnpm build` followed by the existing single `pnpm test:desktop-smoke` using fake audio/transcribers/providers; do not require real microphone permission or a model download at startup, and do not add another desktop end-to-end suite. This documentation-only change needs no build/smoke.

Native acceptance on real supported iPhones, Android devices and packaged desktops must cover permission grant/denial/revocation, Bluetooth/wired/default-device changes, interruption/background/lock, locale/model preparation, offline use, five-minute cap and cleanup after crash/restart. Test English, Indonesian and mixed code/paths without asserting unverified language support or rewriting identifiers. Verify screen readers, large text, reduced motion, keyboard dictation, OS word/inline predictions, third-party keyboards, marked-text IMEs and hardware keyboards. Measure local STT latency, battery/CPU/memory and model storage on representative hardware; demonstrate transcript privacy and draft preservation before claiming an improvement over T3.
