# Ramu vs T3 Code v0.1.0

Compared on 2026-10-16 using the [T3 Code v0.1.0 release notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0), against Ramu at commit 8cf751b. Ramu's side comes from its docs and keyword searches of `apps/`; the UI items were not exercised in the running app.

**Verdict:** roughly even, with different strengths. Ramu should stay the simpler, integrated workspace and only take what fits that.

## Where Ramu is ahead
- Automatic provider fallback across usage limits, including waiting out a limit and resuming after a restart.
- Persistent goals across provider changes.
- Shared memory and learning (skills, lessons, "What Ramu learned" summary).
- Advisors and helpers, with routing to another provider and isolated checkouts.
- Integrated editor, terminals, Git and review with selective undo.
- GitHub issues and pull requests in the app (`PULL-REQUESTS.md`).
- Mobile Git controls and undo.
- English and Bahasa Indonesia.

## Where T3 is ahead
- Subagent lineage and a view of all running agents.
- PR watches that wake the agent on checks, reviews or conflicts.
- Signed, auto-updating releases.
- First-run onboarding.
- More providers, an app-driving MCP, fork and merge-back, webhook schedules, iPad and network discovery. Ramu does not plan these (see below).

## Providers
Ramu and T3 use the same transports: Claude on the Claude Agent SDK, Codex on its app-server, OpenCode 2 on its HTTP API, Cursor on its SDK. Ramu uses ACP only for Antigravity and OpenCode 1.x. Runners are listed in `apps/server/src/providers/runners.ts`. Cursor has not been tested against a real account.

## Plan

Ordered by value for the effort. Paths are starting points found by search; read them before changing anything.

### 0. Simplify first
Ramu should work for someone new to coding with agents and still serve professionals. The settings have about 190 controls, so remove or hide before adding.
- **Remove RTK.** Delete `apps/server/src/rtk.ts`, the `registerRtkTool` call in `apps/server/src/index.ts`, the `rtk` preference and its setting, and the `rtk_run` display case in `packages/shared/src/chat/ramuTools.ts` (keep the case for old transcripts). Update `docs/LEARNING.md`.
- **Remove response style.** The adaptive learning engine already carries the user's preferences. Delete `responseStyle`, `responseInstructions` and `responseSkill` from preferences, `AgentSettings.responseStyle` and its IPC schema, `responseInstructions` in `apps/server/src/intelligence.ts`, the session start and handoff code that uses it, and the settings rows. Saved preferences and old chats must still load: drop the unknown fields instead of failing.
- **Remove dead settings:** `defaultChatDockOpen` and `rotateAccounts`.
- **Hide expert settings under "Advanced":** tool-output compression, load tools on demand, background model, reviews per day, archive-skills-after days, custom turn limit, and the slow-command timer.
- **New chat screen:** default to the current project and hide the worktree picker until clicked.
- **README:** lead with "chat with an agent next to your editor, terminal and Git", then fallback, goals and memory.

### 1. Pull requests from the default branch
The PR section is hidden on `main` (`canCreate` in `apps/web/src/sidebar/scm/PullRequestSection.tsx`), and `pullRequestDraft` in `apps/server/src/workspace/forge.ts` refuses the base branch, so the PR flow looks missing.
- Commits ahead of `origin/main`: show **Create pull request**. The dialog adds a branch name pre-filled from the commits, creates the branch at HEAD, then opens the PR as today. Local `main` is left alone.
- Only uncommitted changes: show a hint that leads into the existing commit-to-new-branch flow (`apps/web/src/git/CommitBranchDialog.tsx`).
- Nothing to propose: show nothing.

### 2. PR watch that wakes the agent
Checks are polled only while the window is focused, and "Fix failing checks" always starts a new thread.
- Poll in the service (`apps/server/src/background/`) so it works with the window closed.
- When a thread's PR gets a failing check or requested changes, queue the feedback into that thread through the normal input queue. Pushing still needs the user.

### 3. Agents page and helper breadcrumb
Helper threads already record `parentId`.
- A breadcrumb above helper threads that opens the parent.
- An **Agents** page that lists every thread and helper across projects, grouped by status (waiting for input, running, waiting on a usage limit, done). Rows show the project, model and changed-file count, with open and stop actions. Waiting-for-input rows come first and can answer the pending request in place.
- A separate page keeps Home short. Home's **Running in the background** list links to it.

### 4. Onboarding and crash reporting
- First run detects installed provider CLIs (`providers/providerBinaries.ts`), signs in and picks a repository.
- Opt-in crash reporting (Electron `crashReporter` plus service errors), with no prompts or code in reports.

### 5. Install skills by chat
Today Ramu only keeps skills it wrote itself, and exports them to every provider as `ramu-<name>` (`docs/LEARNING.md`, `apps/server/src/memory/skillLinks.ts`). Installing someone else's skill means copying folders by hand. Add a Ramu tool so "install the X skill" works from chat.
- **Use the skills.sh CLI instead of writing our own fetcher.** `npx skills` (MIT, `vercel-labs/skills`) already resolves GitHub repos, URLs, git addresses and local paths, finds skills by keyword (`find`), and enforces download limits (10 MiB, 25 MiB extracted, 1000 files).
- **Tool:** `skill_install` takes a source (`owner/repo`, a URL or a local path), an optional skill name, and a scope: **user** (all projects) or **project**. It asks which scope when the user didn't say. A companion `skill_find` wraps `npx skills find` so "find me a skill for X" works.
- **Stage, then import.** Ramu runs the CLI in a temporary folder, never in the project or home: `npx skills@<pinned version> add <source> -s <skill> -a codex --copy -y`, with `DISABLE_TELEMETRY=1`. It then imports the resulting skill folder into Ramu's managed skills in the chosen scope. The existing export then reaches Claude Code, Codex, OpenCode, Cursor and Antigravity, so we do not let the CLI write each agent's own skill folders (`.claude/skills`, `~/.cursor/skills` and so on) and Ramu stays the single source of truth. Global (`-g`) mode is not used, because Ramu does not write into home folders.
- **Safety:** before importing, show the user the skill's name, description, file list and source, and wait for approval. Import only `SKILL.md` and its reference files. Scripts are listed and need a separate confirmation, and Ramu never runs them. Reject paths outside the skill folder and symlinks. Pin the CLI version, since `npx` runs downloaded code. Record the source so Update can re-run the same `add` into staging and show what changed.
- **Missing `npx`:** if Node isn't on the PATH, Settings and the tool say so and link to install instructions. Nothing else breaks.
- **Manage by chat:** the same chat can list, update, disable and remove installed skills (`skill_inspect`, `skill_update`, `skill_archive` already exist for managed skills; add list, update-from-source and remove).
- **Manage in Settings:** in Memory & skills, show installed skills with a source badge and scope, and add Install (paste a link), Update, Disable, Move between user and project, and Remove. Installed skills are never archived automatically.
- **Done when:** saying "install the X skill for this project" in chat makes the skill appear in Settings and in every provider's skill list on the next chat, and removing it from either place removes it everywhere.

### UI quick wins
- Render `mermaid` code blocks in `AssistantText.tsx` and `MarkdownPreview.tsx`, loaded lazily.
- Keep the thread pinned to the bottom when toggling tools or thinking.
- Pending requests wait until typing stops.

## Not planned
These add surface area without fitting Ramu's simple, integrated design. Revisit only if users ask for them.
- **ACP registry and more providers.** Each provider adds setup, fallback and support cost; five is enough.
- **An MCP that drives the app, and OAuth for outside agents.** A large permission surface for a small group of users.
- **Fork and merge-back.** Editing a message to rewind and isolated helpers cover most of it.
- **Webhook triggers for schedules.**
- **Usage and cost page.** The composer usage chip and Settings → Usage are enough for now.
- **Guided review and agent line notes.** People mostly chat with the agent; they rarely read a diff tour. Ramu's `review_add_note` tool was unused and has been removed (agents can still reply to your review threads).
- **Signed releases (for now).** Builds stay unsigned and auto-update stays off (`docs/RELEASING.md`).
- **Language servers in the editor.** Heavy to run per workspace, and agents already run type checks. T3 v0.1.0 has no LSP either; it has no built-in code editor and opens external IDEs.
- **Drag-to-reorder panel tabs, iPad layout, network discovery, PR comment filters, model renaming and favourites.**

## Taking ideas from T3
T3 Code is MIT licensed (Copyright (c) 2026 T3 Tools Inc.).
- **Features and flows:** ideas such as "wake the agent when checks fail" are not protected by copyright. Building the same behaviour in Ramu's own code and design is fine.
- **Code:** copying T3 source is allowed, but each copied file or substantial portion must keep T3's copyright and MIT notice. Prefer writing Ramu's own version.
- **Look and name:** do not copy T3's branding, logo, name or distinctive visual design. MIT covers code, not trademarks.

Keep Ramu's identity: the integrated workspace plus fallback, goals and memory.
