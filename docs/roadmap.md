# Roadmap

Unfinished work only. Completed items are removed; lasting behavior lives in the [guide](README.md#guide). Open an issue before starting anything here.

Every item needs scoped tests and typechecks for the packages it touches. Desktop-facing changes also run `pnpm build` then `pnpm test:desktop-smoke` ([contributing](../CONTRIBUTING.md#checks)). Checks that need a physical phone, a signed build, a live provider or a second host are listed under [Acceptance](#acceptance) and stay open until run; fake-provider tests do not close them.

## Release

- macOS signing and notarization in CI, and signed auto-update (`APP_AUTO_UPDATE` in `packages/shared/src/updates.ts` stays `false` until builds are signed). See [Releasing](contributing/releasing.md).
- Linux: the first release run builds x64 and arm64 `.deb`, `.rpm` and AppImage. Install the `.rpm` on Fedora and start the AppImage on Ubuntu 24.04 (its AppArmor user-namespace limit can block Electron's sandbox) by hand; only the `.deb` is smoke-tested in CI.
- Windows: the port is under way on the `windows-port` branch (CI on Windows, the local service over a named pipe). Next are the server's shell, terminal and path handling, packaging, and a hands-on run in a Windows 11 VM.
- Mobile distribution: the Expo project, app ID `com.akalstack.ramu` and Android push (FCM) are set up. EAS holds the Android upload keystore and the Play submission key (`play-submit@akalstack-ramu`). Remaining: upload the first production `.aab` to Play's internal track by hand (later releases use `eas:release:android`), and the Apple Developer Program (APNs key, TestFlight), which also unblocks macOS signing.

## Implementation

- **Transport:** bounded replay and snapshot recovery for every resource, and defined connection outcomes (current, synchronizing, disconnected, authorization rejected, outcome unknown) that keep drafts and queued messages; mutations that cannot be retried report an unknown outcome and reconcile. Start from measurements on real networks ([Architecture](contributing/architecture.md#transport)).
- **Background terminals:** native command handles for Claude, Codex, OpenCode and Cursor need verified owner-lifecycle contracts. The ACP client-terminal boundary is written but enabled for no provider until one is verified against a live runtime.
- **Agent setup:** per-adapter rule delivery (path-matched activation only where a runtime supports it).
- **Mobile parity with the desktop's open thread:** two things the desktop's thread header offers are missing on the phone. **Continue in new thread** (start a thread in the same checkout with the conversation as context, `useContinueInNewChat` on the desktop) belongs in the thread's menu beside Continue on another host. **Find in conversation** should search the loaded transcript, jump between matches and say how many there are, using the phone's existing search field. The thread header's **Low memory** marker could become an activity pill; the phone already offers Stop idle in Inbox. Inbox and Schedules match the desktop. Phone-only features stay (swipe actions, host filter, native keyboard input in viewers); desktop-only ones stay off the phone where they need the host's keyboard, screen or secrets (editor, shortcuts, environment variables, Reveal in Finder, connecting repositories).
- **Mobile:** IME composition checks on a device. Add a phone entry for a desktop setting only when it clearly helps someone away from the laptop.
- **Thread titles:** a provider verified to supply titles, checked on a live runtime.
- **Browser and computer use:** provider capability negotiation and more session-import sources. **Open on this phone** reaches only dev servers listening beyond the host's loopback; forwarding one loopback port to one paired phone (expiring, IP-bound, shown with its port) needs a security review first. Computer use on Windows and Linux waits for native capture, permissions and signing.
- **Provider compatibility:** compatibility rules for OpenCode's ACP runner, Cursor and Antigravity after protocol checks.
- **Host facts for agents:** `hostThreads.projects` could add each host's platform, architecture and description so `project_list` lets an agent recommend a host; it changes what a paired host learns, so it needs the same scrutiny as the rest of [host pairing](../SECURITY.md#host-pairing).
- **Activity tokens:** Claude and Codex turns record tokens; OpenCode, Cursor and ACP runtimes need a documented per-turn token count in their protocols first.
- **Helpers on another host:** `ramu_agent` with a `host` would mirror a helper's events into the parent live, which needs an event channel between hosts; a thread started there with its report covers the need until then.
- **From an idea to a deployed app:** the platforms' own databases and file storage, and a rewritten site. See [the plan](SHIP-AN-APP-PLAN.md).
- **Artifacts:** widened from Apps to every kind an agent makes (Doc, Slides, Design, Dashboard, Motion, App, Diagram, Live), each with in-place editing where it fits, host-side exports (PPTX, DOCX, PDF, MP4), design systems, live refresh, two-person editing, templates, named-service dashboards and Motion voice-over, connected to the shipping plan. See [the plan](ARTIFACTS-PLAN.md).
- **Abilities:** tools for vision, video and speech, abilities from Shared MCP servers, and music and sound effects for Motion. See [the plan](ABILITIES-PLAN.md).
- **Code quality:** push events are checked for channel and shape where they enter the phone and the desktop, and RPC results take each method's declared type; checking RPC results against runtime schemas is still to do. About 140 `react-hooks/exhaustive-deps` disables name the trigger they are keyed on and are mostly deliberate; convert one only when touching it, after checking it neither loops nor refetches.

## Decisions and deferred scope

- **Certificate pinning:** not built. It needs a native transport replacement that cannot be verified without device builds. Reopen with a concrete threat that HTTPS pairing and host-identity checks do not cover.
- **Preference sync:** hosts talk to each other only through host pairings for agent-started threads, so settings do not follow a person across hosts; credentials and workspace state stay out of any future sync.
- **Remote access:** devices reach a host over the LAN, a private network (Tailscale, NetBird, ZeroTier, WireGuard), SSH, or a tunnel: Cloudflare's quick tunnel, Tailscale Funnel or ngrok run by Ramu with the person's own tool, or one they run and name. A hosted relay and paid plans are deferred until there is a way to fund them; tunnels provisioned per host by a Ramu service are the cheapest option to revisit (free up to 1,000 tunnels).
- **Remote administration:** network access, pairing and device permissions are managed only at the host. A device's **Change settings** permission covers settings, not this; widening it needs reviewable changes and recovery first.
- **Codex call costs:** Ramu does not price Codex tokens from a table of its own. Published per-token prices change with each model release, and the lists outside OpenAI's own rate sheet disagree, so a built-in table would rank providers on figures that are wrong. Cost-aware Auto uses only costs a provider reports; a Codex API key, which reports tokens but no cost, ranks after subscriptions and after keys with a reported cost. Reopen if Codex starts reporting cost.
- **Cloudflare sign-in:** Cloudflare connects with an API token, not `wrangler login`: the CLI's sign-in is an hourly OAuth token, and every Cloudflare deploy runs in the repository's GitHub Actions, which cannot renew it.
- **Deferred:** a full mobile editor, dedicated mobile provider sign-in, chunked large-file upload, marketplaces for MCP, themes or skills, arbitrary plugin or hook execution, automatic provider-file or credential synchronization, AI conflict resolution, local grounding models and VMs for computer use, and vector retrieval for learning.
- **Agent tools from T3 Code left out:** browser recording needs a video encoder Ramu does not ship (an ffmpeg binary, or a JPEG decoder and GIF encoder), and step screenshots cover proof today; reopen it when people ask for change videos on pull requests. Also left out: running arbitrary page JavaScript (it bypasses snapshot-bound browser actions), agents editing queued messages or changing another thread's model, pin or archive state, deleting projects, and pairing hosts, which stay the person's actions.
- **Evidence rule:** claim an improvement over another application only with matched-task evidence, not source inspection or one demo.
