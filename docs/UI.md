# UI development

The renderer uses shadcn/ui with Base UI, Tailwind 4, and shared theme tokens. `components.json` defines paths and the `@` alias.

Add registry components with `pnpm ui:add <component>` and review generated changes. Treat existing components in `apps/web/src/components/ui/` as upstream-owned; do not edit or copy them for Ramu-specific styling or behavior. Compose reusable app components outside that directory, following `components/desktop-button.tsx`, and keep shared variants, tokens and interaction states there. Preserve accessibility, refs and composition APIs. Base UI triggers use `render`, not `asChild`; dialogs use `onOpenChange(open, details)`, `initialFocus`, and `finalFocus`.

`ui.css` maps colors and typography to Ramu's tokens. `styles.css` contains shared desktop sizing. Tailwind preflight is omitted because Monaco and xterm manage their own styles. Reuse shared components for menus, dialogs, list rows, and empty states. Respect reduced-motion preferences.

## Chat disclosures and motion

Desktop tool groups, individual tool output, thinking, helper groups, file changes and worked-for summaries ease between closed and measured content height. The scroll-to-latest control fades and moves into view, and scrolls smoothly when activated. System Reduce Motion and the desktop Reduce Motion preference disable these effects. A message being sent appears immediately as local sending feedback; the host's transcript or durable queue entry replaces it without a second copy. The composer draft clears only after acknowledgement, so a failed send remains recoverable. Sending restores scroll following immediately instead of jumping after provider preparation finishes.

Mobile uses shared height-and-opacity disclosure motion for grouped tools, tool output, plans, worked-for summaries, question options, completed goals and helpers. New non-text transcript blocks fade and rise into place; initial history, earlier-turn pagination and recycled rows do not replay arrival motion. Generated replies keep existing text stationary and give only newly received words a brief 120 ms fade, with no stagger or delayed typing queue, on desktop and mobile. System Reduce Motion reveals content immediately. Sending on mobile already uses the local outbox for immediate feedback; new outgoing bubbles arrive with a short native scroll animation, while streaming output continues following without a delayed animation queue. Consecutive tool calls share one expandable row, while each call retains separate input and output. Plans retain pending, running and completed states. Answered questions show the question and answer with their original options available on expansion, including typed answers and independent replies. Native sheets handle long logs, helper details and full-screen content; message actions remain available through long press.

## Workspace and terminals

Git status, branch lists, history, stashes and change counts are cached by host, repository and checkout path. Threads and hover cards using the same current checkout or worktree share the latest state, keeping it visible during background refreshes. Separate worktrees and hosts keep separate state.

Thread and workspace panes share a resizable split. Bottom terminals span both panes. Terminals in the workspace share the file tab strip; selecting a terminal group shows its shells in place of the file. Resize handles support dragging and arrow keys, Home, and End.

Terminal tabs contain groups of panes. Splitting keeps the shell in its group; moving a pane to a tab preserves it. Hidden groups keep running. Layout and grouping persist with workspace state.

Persistent commands Ramu launched for a thread (`term.background.*`) are owned by the host, not by a tab. The thread's activity dock shows a **Background terminals** count whenever any exist, including after the agent is idle. **Open output** attaches the existing terminal by identity without starting a shell; closing that tab leaves the command running. **Stop** asks the command's process group to end and shows *Stopping*; **Force stop** appears only then. Repeating a request, or stopping a command that already ended, is safe, and final output and exit code stay readable. The host persists command ownership and a bounded output tail in SQLite. After a restart, commands without a verified live handle show **Unknown**, with inspect-only saved output and no input/stop controls. Completed commands retain their known exit outcome. Restored records never replay a command or authorize control by a saved PID. Deleting a thread stops its reviewed live commands first; unknown records require explicit acknowledgement and retaining the checkout files.

Agents can discover `background_terminal_launch`, `background_terminal_list`, `background_terminal_inspect` and `background_terminal_stop` through the existing Ramu tool connection. Launch uses the authenticated session's checkout and thread; arguments cannot redirect it to another host or directory. Launch and stop require Full access, checked again on invocation. Other access modes use the provider's native command permission flow. Inspect returns the most recent bounded output with its cumulative cursor. Force stop requires a prior graceful request and host support. These tools manage Ramu-owned commands; commands started through native provider shells are not automatically registered. Launch records ownership before spawning. Streaming output is checkpointed about once per second and lifecycle changes flush it immediately, with the most recent 64,000 characters retained across restart; abrupt termination can lose the final uncheckpointed tail. Each thread retains its newest 100 records plus older active or uncertain records. Closing an output view retains the command record. Output views persist the exact background command ID and never open a substitute shell when it becomes unavailable. Automated archived-thread cleanup skips active or uncertain commands. Desktop and mobile deletion dialogs list unsettled managed commands before approval. The host rejects commands added after review and prevents new managed launches or shells during deletion. Graceful stop must finish within three seconds; otherwise the thread and output remain available for inspection and optional Force stop. No automatic force stop is performed. An unknown record cannot stop a process: the user can explicitly forget it while deleting only the thread, with checkout files kept. Worktree removal is blocked while command status is unknown, and shared worktrees remain protected. Failed worktree removal retains final command history for retry. Bulk archived deletion refuses unsettled commands and asks for individual review. Older clients cannot silently delete a thread with these commands; a host that predates reviewed deletion requires an update.

Markdown files open in **Preview**, a rendered view without editing. The file header offers **Source** (raw Markdown), **Edit** (rendered editing), and **Preview**. Settings → Editor → Default Markdown view changes the opening mode for newly opened files; switching a mode in one open file keeps its current buffer. Links to a source line or search match open Source so the requested location remains visible.

Editors, terminals, and attachments use native context menus. Keep clipboard and save-dialog operations in the main process.

## Usage limit state

A thread at a usage limit is idle, not failed, and every surface words it **Limit reached · resumes around 5:00 PM** (or **resuming automatically** when the time is a guess). **Paused** means only a goal you paused yourself. The sidebar clock, the Home and Inbox **Limit reached** group, the goal bar and the mobile transcript all read the thread's `provider-wait` event; the shared helpers in `packages/shared/src/chat/providerWait.ts` and `limitPolicy.ts` (`providerWaitState`, `effectiveAutoResume`, `limitTrayView`, `limitChoiceOf`) keep desktop and mobile in step.

- **Settings → Access & Fallback → When a usage limit is reached** is one choice: **Switch to another model**, **Wait on this model**, or **Stop and let me decide**. It writes both `defaultAutoFallback` and `fallback.autoResume` (`settings/LimitChoiceRow.tsx`). A stored switch-and-stop combination shows as a fourth item, **Switch, then stop if none has room**. **When to switch** and **Fallback order** apply only to the switching options. Across hosts the row reads **Mixed** when either value differs.
- **Tray row** (`models/ProviderWait.tsx`): clock, title, detail, then a button and the per-thread **Auto-resume** menu. **Try anyway** is quiet while a reset is known and ahead; **Try again** is primary when the time is unknown or guessed; **Resume** is primary when the limit has reset and auto-resume is off. All three call `agent.retryLimitNow`; a failed try reads **Still limited**. **Auto-resume** offers **Use default (on/off)**, **On** and **Off** through `agent.setAutoResume`, and the provider chip menu offers the same three items. The chip is always there when the thread has the control: near or at a limit it is the full chip, otherwise a quiet icon-only chip whose menu holds the three items and **Fallback settings…**. While held at a limit its menu also lists **Continue with <provider>** for every other provider not known to be limited (`models/continueWith.ts`); choosing one runs `agent.configure` then `agent.retryLimitNow`.
- **Composer** while at a limit: the placeholder says when the message is sent (or that it is queued until you resume), the send label is **Queue**, the empty-box play button becomes **Try again** or **Resume** when the tray makes that the main button, and the provider chip shows **Limit reached**. Stop is not shown because the thread is idle.
- A reset notice fires once per wait while auto-resume is off (desktop `agentNotifier`, mobile push).
- A **Context handoff** separator adds a line such as "Carried events 1–412 from Claude (compacted handoff, 3 old results shortened)" once the next launch has built the handoff (`views/agent/handoffLine.ts`). Returning native sessions say **new events only**. Full-history transfers say **compacted handoff** if content was shortened, omitted or replaced by a checkpoint (whose event boundary is shown); otherwise they say **full handoff**. Settings changes that resume the native conversation use **Settings changed**.

## Settings lists

Lists in Settings (memories, saved approvals, installed skills, learning reviews) use the compact `SettingsCard` from `apps/web/src/settings/cards.tsx`: a header row with the title, badges and small actions, one quiet meta line, no borders. Long lists page with `usePaged`: the first 20 items (10 for skills and reviews), then **Show more**. New Settings lists should use both.

## Command palette

The palette (`apps/web/src/palette/`) is a set of sources, each drawn as its own group. No prefix searches files, projects, threads and text inside project files; `>` runs commands only; `#` searches file contents only. Results stay in their group (never one flat ranking), show the first few with **Show more**, and render through `VirtualList`.

To add a source, write a `PaletteSource` (`palette/sources.ts`) and add it to the list in `Palette.tsx`:

- `id`, `label` (translated), `priority` (group order), `modes` (`all`, `commands`, `content`).
- `query(text, { signal, limit, mode })` returns a batch (synchronous), a Promise, or an AsyncIterable of batches. Each result carries its label, optional highlight offsets, detail, snippet and a `run` that opens it.
- `minLength`, `debounceMs`, `limit`, `initialShow`. Keep cheap sources at `debounceMs: 0`; anything that waits on the server needs a debounce and a minimum length, and should honour `signal`. A new keystroke aborts the old query and its late result is dropped. Set `scope` (for example the task id) so a running query survives rebuilds of the source list but not a project switch.

Content search reuses `files.search` (ripgrep, ignore files, binary and size limits, `SEARCH_RESULT_LIMIT`). The server has no cancellation, so a superseded search finishes in the background and is ignored. Tests for the pure parts are in `apps/web/test/palette*.test.ts`.

## New-thread model defaults

Settings → Providers → Model sets offers **Steps** and **Model then effort**. Steps walks the configured model/effort presets; Model then effort keeps the selected model while adjusting its actual supported efforts, with the existing model picker available separately. Changing the flow preserves the current provider/model/effort, composer, access/fallback policy and custom sets. Mobile exposes the same effective choice in the selected host’s Providers & models settings; older hosts omit the unsupported row. This is a host setting shared by its clients, not a global or phone-only preference.

Generated defaults group available providers in deterministic Codex, Claude, Antigravity, Cursor and OpenCode order. Codex uses the available Luna/Sol/Astra steps and prefers Sol Low when offered; a different Codex catalog uses its reported default model. Other providers use their reported default model with up to three actual supported efforts. Models with no effort setting have a single model choice. These groups are useful defaults, not a comparative quality ranking. Refresh and provider-configuration changes re-evaluate the generated set on the execution host. A saved generation fingerprint lets untouched sets follow catalog changes; edited sets and surviving explicit default steps remain unchanged. If an explicit default disappears, its set remains available for correction. Unmarked older sets are retained unless their untouched legacy shape is proven. Empty or failed catalogs never erase a known generated set. Before any usable catalog is known, the legacy placeholders remain subject to the existing pre-send availability checks.

The model picker follows the selected project's provider/model preferences after host catalog validation. Its compact notice names the source file or explains an unavailable preference; manual model selection and **Use host default** preserve the draft. **Use project default** restores model inheritance. Explicit choices retain the displayed access/fallback policy and stay qualified by host and draft scope. Revalidation happens before creating a thread or enqueuing a message; superseded or changed results require review. Offline mobile drafts without loaded host defaults require a reviewed choice. Existing sessions and queued settings are not replaced by configuration changes. See [Configuration files](CONFIGURATION.md#repository-configuration) for precedence and storage.

## Workspace defaults and branch names

Desktop new-thread drafts retain optional manual/generated branch candidates and their bounded naming request in the host/project workspace sidecar. Manual edits survive prompt changes; generated candidates are restored only for matching prompt/title/settings. Mode changes retain optional candidates, while choosing an existing workspace skips naming. Storage failures retain the complete in-memory choice for Retry, and a late Send acknowledgement cannot delete a newer branch edit. This metadata follows the existing 30-day automatic draft expiry.

On mobile, New thread → Workspace exposes optional branch-name details for supporting hosts. Manual candidates remain editable offline and survive prompt changes; generated candidates belong to the prompt and naming settings that produced them. Generate name and Preview worktrees never create a thread. Dismissal, edits and host/project switches cancel or discard pending results. A provisional preview shows each repository’s base commit, branch and path. **Keep these base commits** freezes its bases when the unchanged request is queued; names and paths remain advisory. Editing the request requires a new review. A confirmed moved-base rejection offers review and explicit retry from the pending message, preserving its request ID and naming inputs. An uncertain delivery cannot replace its plan. Before enqueue, reviewed previews last only for the mounted form; candidates remain in active and explicitly saved drafts.

Settings → Git → New threads & worktrees saves the execution host's default checkout mode and Git branch prefix. Current checkout remains the initial default. An untouched new-thread draft follows the host default; a manual choice or explicit existing workspace wins. Use default clears a manual override. Plain folders and repositories without commits visibly fall back to Current checkout when following a default; an explicit worktree request is blocked instead.

**Rename workspace…** in a desktop thread’s menu or the selected-workspace menu edits the shared workspace label. On mobile, select an existing workspace in New thread → Workspace, then choose **Rename workspace**. The label is shared by all threads using that workspace; thread titles, branch names and folder paths retain their existing identities. The host checks the original label before saving, so a concurrent change asks the person to reopen the editor and review it. Lost-acknowledgement retries are safe, offline saves are disabled, and older hosts show an update hint. Viewer grants cannot rename labels.

Desktop new-thread drafts retain a host/project-qualified workspace choice: Use default follows current host/repository defaults, a manual mode stays explicit, and an existing workspace keeps its exact ID. Explicit workspace-scoped entry points override the restored choice. An unavailable saved workspace requires another choice before creation. Failed persistence keeps the current session choice with Retry; unreadable or unsupported saved metadata requires a fresh workspace choice and leaves message text intact. A late send acknowledgement clears only the unchanged choice it sent. This active metadata expires after 30 days independently of explicit saved drafts.

Fixed names use `ramu/<title-slug>` by default, support an empty or nested namespace, and need no provider. The server owns allocation, includes pending database bindings when finding collisions, and stores the exact base commit for setup. A preview cannot authorize filesystem paths. A moved base with an explicit preview requires review. Creation request IDs deduplicate retries; setup refuses unowned branches and can retry partial failures. Settings also supports Semantic name and Custom instructions. These produce a complete branch name without adding the fixed prefix. Only the bounded opening message and naming instructions are sent to isolated analysis, with no tools, a 15-second deadline and no deferred provider-limit wait. Invalid output, unavailable providers and deadlines use `ramu/<title-slug>` and retain a visible “Used default branch name” notice on the thread.

Desktop worktree Details offers Generate name, Cancel and an editable branch name. Previews are provisional before generation; sending can generate automatically. Prompt/settings changes discard generated suggestions, manual edits win over late results, and abandoning generation asks the host to cancel it. Generated collisions get bounded suffixes; a manually entered name is used exactly or rejected if taken. Directory paths always come from the title. No generated result renames an already-created branch.

Naming runs outside the global allocation lock. In-flight creation request IDs coalesce generation; completed retries return the recorded allocation before contacting a model. Mobile freezes the strategy, instructions and bounded opening message with the resolved checkout mode and prefix in its outbox, and generates on the host at delivery. Mobile New thread offers existing isolated workspaces in its Workspace sheet. The host/project-qualified active draft retains default/manual/reused selection across reopening; changing checkout keeps the composer intact and resolves file references in the explicitly selected checkout. Existing-workspace IDs are frozen in the outbox and reused without branch generation or new-worktree planning; the server revalidates project membership and readiness before creating the thread. A missing workspace never silently becomes a new one. Hosts without workspace-default discovery can still accept an explicitly selected Current checkout. Explicit native generation/editing, desktop draft provenance, frozen preview bases and additional cross-host acceptance remain in the workspace plan.

## Plan usage detail

Desktop account details show each allowance window for other logins, with percentages explicitly labelled as used. The next-message provider chip checks the thread’s own login and previews another eligible account before another model. Account rotation preserves the selected model, reasoning effort and service tier. Five-hour capacity does not override a weekly or model-specific threshold.

Mobile Threads shows Plan usage under its title and through a header action. Its composer has a separate Usage target beside the model. These open one shared host/account detail sheet; Settings reuses the same reading rows. Measurements, notice-only holds, missing values and old readings stay distinct. A reset timestamp passing says it awaits an update. Refresh is labelled specifically for Claude; other providers continue reporting through their sessions. Account selection never substitutes another login's readings. Desktop detail also preserves monthly/quota windows and distinguishes a notice-derived hold from a measured quota. Routing and usage presentation share provider-aware model-scope rules, including versioned Claude models and Antigravity families; unknown scopes require an exact model identity. Mobile allowance labels and Cursor/Antigravity pool explanations use the selected language and the same scope rules as desktop. An open mobile detail sheet reloads account readings on host usage events, discards stale/out-of-order responses and releases subscriptions on dismissal. Unsupported account/refresh methods explain that the host needs updating while retaining last-known readings. Transient refresh failures keep refresh available, and reconnect reloads account readings without discarding the last-known data. Refresh remains labelled for Claude; Access & Fallback settings opens for the selected host.

## Mobile Explorer

Browse files on Threads/Home opens a registered-project picker. A thread's Explorer action opens its exact task checkout; project actions open the current checkout. Neither action creates a task or worktree. Direct and transcript file links share a scoped viewer for code, Markdown, images and diffs. Host, context, repository and relative path qualify resource identity.

Directories load lazily in pages of at most 2,000 entries. **Load more files** continues each visible folder on supporting hosts; older hosts retain the truncation notice. Continuations belong to the exact directory revision, and a changed directory requires Refresh. Late pages from another host or checkout are discarded; filename/path search uses the existing bounded quick-open index and shows at most 200 matches. Explorer reports unavailable/offline scopes instead of selecting another host. Project-free browsing only exposes an already-existing working folder. Home browsing offers Current checkout and the selected host/project’s existing isolated workspaces. The header identifies the project/workspace, and repository details show the branch and working path. Change checkout returns to scope selection; Collapse folders closes expanded tree rows. New thread also exposes Browse files for its selected checkout, and its existing file/skill context picker works before thread creation. File/skill suggestions qualify cached catalogs by host and checkout. Live file-change watchers are shared per checkout and leased by task: archiving or deleting the last task using a checkout stops watching it, and reopening the task resumes. Confirmed file management, device copy/reveal, complete localization and native accessibility/large-text checks remain unfinished.

File previews offer **Add to message** for their originating thread or New composer. From Home, **New thread with file** uses a separate draft for the selected checkout and preserves the ordinary Home draft. File references keep their repository identity; staged, unstaged and combined diffs remain distinct. **Add image reference** stores a path on its execution host, not image bytes or an uploaded attachment. Saving the reference precedes navigation; failed storage keeps the preview open and leaves the current draft editable. A changed checkout in a previously opened file draft requires review rather than a silent override. None of these actions sends, queues, starts a thread or creates a workspace.

A mounted composer reloads file references on return without replacing its text, quotes, attachments or mentions. A late Send acknowledgement clears only an unchanged composer snapshot. Messages with more than 30 combined mentions and context references are blocked for correction instead of silently dropping files.

**Show in Explorer** reveals the selected file in its exact host, checkout and repository, expands its ancestors and scrolls to the row. A missing path or one outside loaded entries is reported explicitly. Collapse remains in effect through refresh; an explicit reveal can expand the path again. Previews resolve read-only bindings before reading files, so opening an unstarted standalone thread never creates a working folder. Older hosts lacking this boundary explain that an update is needed. Plain folders offer file viewing without Git controls, and Markdown links with a line number open source for line navigation.

## Saved message drafts

Mobile's composer action sheet offers **Save draft** and **Saved drafts**. Saves are device-local, host-qualified snapshots; occupied restore offers **Save current and restore**. Quotes, captured file context, mentions, completed attachment references and explicit checkout intent are preserved. Saving/restoring never sends or starts work. See [Saved message drafts](MESSAGE-DRAFTS.md) for retention, failure handling, limits and attachment validation. **Use in this composer** offers reviewed same-host recovery when a save belongs elsewhere, including a deleted source. It keeps destination settings, converts source references and captured context into readable text, and rechecks retained attachments before sending. Desktop saved controls, mobile hardware-keyboard shortcuts and native acceptance remain in [the plan](MESSAGE-DRAFTS-PLAN.md).
