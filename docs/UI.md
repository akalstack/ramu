# UI development

The renderer uses shadcn/ui with Base UI, Tailwind 4, and shared theme tokens. `components.json` defines paths and the `@` alias.

Add registry components with `pnpm ui:add <component>` and review generated changes. Treat existing components in `apps/web/src/components/ui/` as upstream-owned; do not edit or copy them for Ramu-specific styling or behavior. Compose reusable app components outside that directory, following `components/desktop-button.tsx`, and keep shared variants, tokens and interaction states there. Preserve accessibility, refs and composition APIs. Base UI triggers use `render`, not `asChild`; dialogs use `onOpenChange(open, details)`, `initialFocus`, and `finalFocus`.

New desktop actions use `components/desktop-button.tsx`, including compact drag handles and inline Settings actions. `apps/web/test/sharedButtons.test.ts` rejects raw buttons outside the dedicated theme-recovery control. That native exception bypasses host field restrictions and uses a fixed palette, so a bad trial cannot remove the person’s way back. This guard does not replace review of specialized controls or visual overrides.

Reorder activators use `components/drag-handle.tsx` across queues, saved commands, model steps, fallbacks, provider accounts and model favorites. Pointer/keyboard sensor listeners, instruction attributes and activator refs stay on the button; busy or unavailable settings use its disabled behavior. Favorite reordering remains focusable during saves, while the shared button blocks pointer and keyboard activation. Image panning keeps its own gesture treatment. Sidebar host/section toggles use `sidebar-disclosure-button.tsx`, and worked-for disclosures compose the existing marker/collapsible with `summary-disclosure-button.tsx`. These app-owned controls centralize hover, focus and disabled styles while callers supply layout, labels and state.

`row-button.tsx` supplies selection, hover, focus and disabled states for discovery, Inbox, clone/folder and activity rows. Offline Inbox conversations remain focusable for their cached hover details while navigation is disabled. `inline-action.tsx` keeps host mutations field-aware and external destinations as links; local usage expansion clears the field restriction around its trigger so cached accounts stay readable.

Browser tab controls share selected, hover, focus and disabled styling, with Arrow/Home/End navigation that skips disabled or hidden tabs. Context menu and retained tab callbacks recheck busy state, readiness and host/thread identity; middle-click close retains the same guard, while Copy address stays device-local. Hosted tab selection also rechecks access before replacing an address draft.

The app button converts semantic font-size aliases into explicit length tokens before class merging, so choosing a text color cannot erase the device’s text-size preference.

`ui.css` maps colors and typography to Ramu's tokens. `styles.css` contains shared desktop sizing. Tailwind preflight is omitted because Monaco and xterm manage their own styles. Reuse shared components for menus, dialogs, list rows, and empty states. Respect reduced-motion preferences.

Settings → Appearance → Customize colors previews the candidate with the production message bubble, worked-for disclosure, question row, goal evidence, composer disclosure, limit row, input, switch, selectable rows, browser tabs, inline disclosure and buttons. Wide/Narrow changes only the sample layout; typing, toggling and expanding samples stays local and survives candidate changes. The preview scrolls within a bounded area so color fields remain reachable. Compact candidate thumbnails remain noninteractive. The Code/Diff preview runs the production Monaco core, Shiki grammars and workbench color mapping on a separate app-owned `ramu-theme:` origin. It offers code and inline/split diffs over fixed read-only samples; palette updates preserve selection and scroll, and switching modes restores each view. It has no workspace bridge, file operations or provider access, and does not change the workspace editor’s global theme. The full preview also includes read-only xterm ANSI output using the live terminal palette mapping and an interactive quantity chart on the same isolated document origin and sandboxed frame as transcript content. Candidate color edits update the chart through the production theme-message contract without rebuilding its controls. Preview documents share the live-frame budget, stop offscreen or when the app is hidden, retain their declared scenario on return, and release their native document URLs when closed. They do not open a shell, create a thread, publish content or change the selected theme.

## Workspace and terminals

Background terminal rows show whether the person or agent requested a stop. A human stop adds one transcript note per command, including after a retry or server restart, without submitting a message or waking an idle agent. Conversation handoffs retain that instruction: inspect current command state and do not relaunch without a new request. A stop request does not itself establish that the command has exited.

Git status, branch lists, history, stashes and change counts are cached by host, repository and checkout path. Threads and hover cards using the same current checkout or worktree share the latest state, keeping it visible during background refreshes. Separate worktrees and hosts keep separate state.

Thread and workspace panes share a resizable split. Bottom terminals span both panes. Terminals in the workspace share the file tab strip; selecting a terminal group shows its shells in place of the file. Resize handles support dragging and arrow keys, Home, and End.

Terminal tabs contain groups of panes. Splitting keeps the shell in its group; moving a pane to a tab preserves it. Hidden groups keep running. Layout and grouping persist with workspace state.

Persistent commands Ramu launched for a thread (`term.background.*`) are owned by the host, not by a tab. The thread's activity dock shows a **Background terminals** count whenever any exist, including after the agent is idle. **Open output** attaches the existing terminal by identity without starting a shell; closing that tab leaves the command running. **Stop** asks the command's process group to end and shows *Stopping*; **Force stop** appears only then. Repeating a request, or stopping a command that already ended, is safe, and final output and exit code stay readable. The host persists command ownership and a bounded output tail in SQLite. After a restart, commands without a verified live handle show **Unknown**, with inspect-only saved output and no input/stop controls. Completed commands retain their known exit outcome. Restored records never replay a command or authorize control by a saved PID. Deleting a thread stops its reviewed live commands first; unknown records require explicit acknowledgement and retaining the checkout files.

On mobile, the thread activity count and thread action open a background-command sheet even after the agent is idle. It lists commands from that execution host and thread, and shows bounded read-only output without opening an interactive shell. Hiding the sheet leaves the command running and preserves the draft. Output cursors discard duplicate chunks and retain the terminal viewport when the bounded tail advances. Stop rechecks live ownership and capabilities; force stop requires an earlier graceful request and explicit confirmation. Offline rows and restored Unknown records remain read-only, and older hosts show an update hint. Native input is disabled in the output viewer.

Agents can discover `background_terminal_launch`, `background_terminal_list`, `background_terminal_inspect` and `background_terminal_stop` through the existing Ramu tool connection. Launch uses the authenticated session's checkout and thread; arguments cannot redirect it to another host or directory. In Full access launch runs directly. In other access modes each launch asks for a once-only approval of the exact command through the thread's existing permission prompt; a refusal is final for that request and a change of access while waiting cancels it. Access is checked again on invocation. Stopping a command already owned by the thread needs no further approval. Commands launched by a sub-agent show **Started by a sub-agent** on desktop and mobile. Inspect returns the most recent bounded output with its cumulative cursor. Force stop requires a prior graceful request and host support. These tools manage Ramu-owned commands; commands started through native provider shells are not automatically registered. Launch records ownership before spawning. Streaming output is checkpointed about once per second and lifecycle changes flush it immediately, with the most recent 64,000 characters retained across restart; abrupt termination can lose the final uncheckpointed tail. Each thread retains its newest 100 records plus older active or uncertain records. Closing an output view retains the command record. Output views persist the exact background command ID and never open a substitute shell when it becomes unavailable. Automated archived-thread cleanup skips active or uncertain commands. Desktop and mobile deletion dialogs list unsettled managed commands before approval. The host rejects commands added after review and prevents new managed launches or shells during deletion. Graceful stop must finish within three seconds; otherwise the thread and output remain available for inspection and optional Force stop. No automatic force stop is performed. An unknown record cannot stop a process: the user can explicitly forget it while deleting only the thread, with checkout files kept. Worktree removal is blocked while command status is unknown, and shared worktrees remain protected. Failed worktree removal retains final command history for retry. Bulk archived deletion refuses unsettled commands and asks for individual review. Older clients cannot silently delete a thread with these commands; a host that predates reviewed deletion requires an update.

Markdown files open in **Preview**, a rendered view without editing. The file header offers **Source** (raw Markdown), **Edit** (rendered editing), and **Preview**. Settings → Editor → Default Markdown view changes the opening mode for newly opened files; switching a mode in one open file keeps its current buffer. Links to a source line or search match open Source so the requested location remains visible.

Editors, terminals, and attachments use native context menus. Keep clipboard and save-dialog operations in the main process.

## Notifications and background activity

The desktop bottom bar shows the current background job's label, or a running count for multiple jobs, beside a bell that counts only retained notifications. The job signal disappears when idle; a disconnected host shows Reconnecting or Pair again. Both controls open the same **Notifications and activity** popover, with Running first and Notifications below a divider. Notification dismissal and Clear all do not cancel running work.

Running jobs offer **Stop** only when their execution host supports cancellation. Stop stays disabled with **Stopping…** until the request settles, and failures remain visible for retry. App update checks/downloads, memory maintenance, skill learning, recaps and the managed Antigravity runtime update support cancellation. Cancelling a managed runtime update interrupts download, extraction or validation, cleans staging files and preserves the active version; once atomic activation starts, it finishes. ## Usage limit state

A thread at a usage limit is idle, not failed, and every surface words it **Limit reached · resumes around 5:00 PM** (or **resuming automatically** when the time is a guess). **Paused** means only a goal you paused yourself. The sidebar clock, the Home and Inbox **Limit reached** group, the goal bar and the mobile transcript all read the thread's `provider-wait` event; the shared helpers in `packages/shared/src/chat/providerWait.ts` and `limitPolicy.ts` (`providerWaitState`, `effectiveAutoResume`, `limitTrayView`, `limitChoiceOf`) keep desktop and mobile in step.

- **Settings → Models → When a usage limit is reached** is one choice: **Switch to another model**, **Wait on this model**, or **Stop and let me decide**. It writes both `defaultAutoFallback` and `fallback.autoResume` (`settings/LimitChoiceRow.tsx`). A stored switch-and-stop combination shows as a fourth item, **Switch, then stop if none has room**. **When to switch** and **Fallback order** apply only to the switching options. Across hosts the row reads **Mixed** when either value differs.
- **Tray row** (`models/ProviderWait.tsx`): clock, title, detail, then a button and the per-thread **Auto-resume** menu. **Try anyway** is quiet while a reset is known and ahead; **Try again** is primary when the time is unknown or guessed; **Resume** is primary when the limit has reset and auto-resume is off. All three call `agent.retryLimitNow`; a failed try reads **Still limited**. **Auto-resume** offers **Use default (on/off)**, **On** and **Off** through `agent.setAutoResume`, and the provider chip menu offers the same three items. The chip is always there when the thread has the control: near or at a limit it is the full chip, otherwise a quiet icon-only chip whose menu holds the three items and **Fallback settings…**. While held at a limit its menu also lists **Continue with <provider>** for every other provider not known to be limited (`models/continueWith.ts`); choosing one runs `agent.configure` then `agent.retryLimitNow`.
- **Composer** while at a limit: the placeholder says when the message is sent (or that it is queued until you resume), the send label is **Queue**, the empty-box play button becomes **Try again** or **Resume** when the tray makes that the main button, and the provider chip shows **Limit reached**. Stop is not shown because the thread is idle.
- A reset notice fires once per wait while auto-resume is off (desktop `agentNotifier`, mobile push).
- A **Context handoff** separator adds a line such as "Carried events 1–412 from Claude (compacted handoff, 3 old results shortened)" once the next launch has built the handoff (`views/agent/handoffLine.ts`). Returning native sessions say **new events only**. Full-history transfers say **compacted handoff** if content was shortened, omitted or replaced by a checkpoint (whose event boundary is shown); otherwise they say **full handoff**. Settings changes that resume the native conversation use **Settings changed**.

## Command palette

The palette (`apps/web/src/palette/`) is a set of sources, each drawn as its own group. No prefix searches files, projects, threads and text inside project files; `>` runs commands only; `#` searches file contents only. Results stay in their group (never one flat ranking), show the first few with **Show more**, and render through `VirtualList`.

To add a source, write a `PaletteSource` (`palette/sources.ts`) and add it to the list in `Palette.tsx`:

- `id`, `label` (translated), `priority` (group order), `modes` (`all`, `commands`, `content`).
- `query(text, { signal, limit, mode })` returns a batch (synchronous), a Promise, or an AsyncIterable of batches. Each result carries its label, optional highlight offsets, detail, snippet and a `run` that opens it.
- `minLength`, `debounceMs`, `limit`, `initialShow`. Keep cheap sources at `debounceMs: 0`; anything that waits on the server needs a debounce and a minimum length, and should honour `signal`. A new keystroke aborts the old query and its late result is dropped. Set `scope` (for example the task id) so a running query survives rebuilds of the source list but not a project switch.

Content search reuses `files.search` (ripgrep, ignore files, binary and size limits, `SEARCH_RESULT_LIMIT`). The server has no cancellation, so a superseded search finishes in the background and is ignored. Tests for the pure parts are in `apps/web/test/palette*.test.ts`.

Empty or failed catalogs never erase a known generated set. Before any usable catalog is known, legacy placeholders remain subject to pre-send availability checks.

The model picker follows the selected project's provider/model preferences after host catalog validation. Its compact notice names the source file or explains an unavailable preference; manual model selection and **Use host default** preserve the draft. **Use project default** restores model inheritance. Explicit choices retain the displayed access/fallback policy and stay qualified by host and draft scope. ## Workspace defaults and branch names

Manual edits survive prompt changes; generated candidates are restored only for matching prompt/title/settings. Mode changes retain optional candidates, while choosing an existing workspace skips naming. On mobile, New thread → Workspace exposes optional branch-name details for supporting hosts. An uncertain delivery cannot replace its plan. Before enqueue, reviewed previews last only for the mounted form; candidates remain in the current composer state.

Plain folders and repositories without commits visibly fall back to Current checkout when following a default; an explicit worktree request is blocked instead.

The host checks the original label before saving, so a concurrent change asks the person to reopen the editor and review it. Desktop new-thread drafts retain a host/project-qualified workspace choice: Use default follows current host/repository defaults, a manual mode stays explicit, and an existing workspace keeps its exact ID. Explicit workspace-scoped entry points override the restored choice. An unavailable saved workspace requires another choice before creation. Failed persistence keeps the current session choice with Retry; unreadable or unsupported saved metadata requires a fresh workspace choice and leaves message text intact. A late send acknowledgement clears only the unchanged choice it sent. This active metadata expires after 30 days.

Fixed names use `ramu/<title-slug>` by default, support an empty or nested namespace, and need no provider. The server owns allocation, includes pending database bindings when finding collisions, and stores the exact base commit for setup. A preview cannot authorize filesystem paths. A moved base with an explicit preview requires review. Creation request IDs deduplicate retries; setup refuses unowned branches and can retry partial failures. Settings also supports Semantic name and Custom instructions. These produce a complete branch name without adding the fixed prefix. Only the bounded opening message and naming instructions are sent to isolated analysis, with no tools, a 15-second deadline and no deferred provider-limit wait. Invalid output, unavailable providers and deadlines use `ramu/<title-slug>` and retain a visible “Used default branch name” notice on the thread.

Desktop worktree Details offers Generate name, Cancel and an editable branch name. Previews are provisional before generation; sending can generate automatically. Prompt/settings changes discard generated suggestions, manual edits win over late results, and abandoning generation asks the host to cancel it. Generated collisions get bounded suffixes; a manually entered name is used exactly or rejected if taken. Directory paths always come from the title. No generated result renames an already-created branch.

Naming runs outside the global allocation lock. In-flight creation request IDs coalesce generation; completed retries return the recorded allocation before contacting a model. Mobile freezes the strategy, instructions and bounded opening message with the resolved checkout mode and prefix in its outbox, and generates on the host at delivery. Mobile New thread offers existing isolated workspaces in its Workspace sheet. Explicit native generation/editing, desktop draft provenance, frozen preview bases and additional cross-host acceptance remain in the workspace plan.

## Mobile Explorer

Direct and transcript file links share a scoped viewer for code, Markdown, images and diffs. Host, context, repository and relative path qualify resource identity.

Directories load lazily in pages of at most 2,000 entries. **Load more files** continues each visible folder on supporting hosts; older hosts retain the truncation notice. Continuations belong to the exact directory revision, and a changed directory requires Refresh. Messages with more than 30 combined mentions and context references are blocked for correction instead of silently dropping files.

Long-pressing a row opens file actions. **Copy path** is always offered. When the host is reachable, **Share a copy** downloads a file's contents to this device and opens the system share sheet (it shares the device copy, never the host path). Unless the device is view-only, **Duplicate** (a free `name copy` sibling), **Move to folder** (a destination folder inside the same checkout), **Rename** and a confirmed **Delete** run through the host's `files.*` handlers; a name clash is refused by the host rather than overwritten, and only the affected folders reload.

**Show in Explorer** reveals the selected file in its exact host, checkout and repository, expands its ancestors and scrolls to the row. A missing path or one outside loaded entries is reported explicitly. Collapse remains in effect through refresh; an explicit reveal can expand the path again. Previews resolve read-only bindings before reading files, so opening an unstarted standalone thread never creates a working folder. Older hosts lacking this boundary explain that an update is needed. Plain folders offer file viewing without Git controls, and Markdown links with a line number open source for line navigation.

## Current chat state

Desktop and mobile automatically retain each composer's current unsent message in device-local storage, qualified by host and thread or new-thread scope. Returning to a chat restores its current input and supported context; desktop also restores the transcript position. Sending clears only the unchanged state that was acknowledged, so a late result cannot clear newer edits. The desktop composer clears its visible input before dispatch and keeps a recovery draft until acceptance; a rejected send restores it. The offline outbox and host queue keep their existing delivery behavior.

## Integrated browser

**Settings → Browser** separates the execution host's agent-browser choice from the device's clicked-link destination. Host defaults and per-provider overrides choose integrated or existing provider setup; new Default/Temporary tabs follow the host's selected profile. New empty installations default to integrated; legacy settings without a browser choice conservatively keep provider setup, including external CLI configurations Ramu cannot inspect. Explicit choices are preserved. Native/provider acceptance remains pending. Provider-native browser tools may remain available; Ramu does not overwrite global provider configuration or claim exclusive browser routing.

On the local execution host, explicitly selected integrated-browser root runs in Full access get status/profile-list/tab-list/open/snapshot/navigate/click/type/select/press/scroll/wait/screenshot/diagnostics/dialog/close tools. The server derives their thread/run identity, freezes the choice with the provider process, and binds operations to one registered desktop event stream. Readiness requires a completed registration handshake. Disconnects, timeouts and run stop fail pending work without replaying an operation; uncertain actions require inspecting the page before continuing. Stale provider connections cannot keep driving it. Other access modes and Ramu-managed helpers request browser-only approval through the existing thread permission UI. Approval lasts only for the current turn and includes website actions and scoped workspace transfers; denial cannot be retried in that turn. Helpers can use only tabs they opened after their own approval, never parent tabs. Stop/abort cancels pending approvals. Native provider helpers sharing their parent’s MCP connection cannot be identified as separate browser principals. An explicitly configured host-managed Chromium runtime supports remote execution and viewing through separate device/thread grants.

The guest has Chromium sandboxing, context isolation, no Node access or preload, and denied site permissions. Downloads require a one-use grant from the current controller. Fixed code in an isolated world reads bounded visible text and element references without cookies, storage or form values. DOM changes, navigation, ownership changes and an attempted action expire references. Password typing, rich editors, custom selection widgets and frames still require human interaction. Native select controls accept exact visible labels; keyboard and scrolling actions consume their observation. Waits are bounded and cancel on ownership changes. Screenshots capture only the guest page as a bounded JPEG; network excerpts retain method/origin/status/error rather than paths, queries, headers or bodies. Website-dialog replies require the exact live dialog id and current controller, and can unblock a preceding click without replaying it. A person's takeover blocks new agent mutations, waits for earlier input to drain and then enables native mouse/keyboard input. Disconnect pauses control; it never gives the page to the agent automatically.

The pane adopts the actual agent tab on first use in the active thread without opening a duplicate; background work never switches hosts or threads. Open browser also discovers existing tabs for its thread, and its tab selector lets the person choose one or start another. Native navigation, titles and controller changes refresh the pane. Take control / Give control to agent use a server-resolved active run; opening in the system browser stays a device action. Default shares website sign-ins on this desktop; Temporary is isolated per run and cleared at run end. Native transfer/viewer acceptance, optional verified session import and provider acceptance remain in the [browser plan](ROADMAP.md). Implementation checks are currently held until all planned code changes are complete; this guide describes the intended behavior of the working-tree implementation, not a native/provider acceptance result.


Settings → Browser manages named profiles on their owning desktop. Metadata is a bounded, atomically replaced local catalog; cookies and other website data stay in Chromium partitions. A damaged catalog disables mutation rather than overwriting unknown identities. Default and Temporary cannot be renamed or deleted. Sign in opens a user-only sandboxed window in the selected persistent profile without creating a project, thread or provider request. It reuses an unfinished sign-in window instead of restarting it. **Import…** (Chrome, Chromium, Edge and Firefox on macOS and Linux) copies sign-in cookies once into a new profile: choose a source profile, then websites (none preselected; Chrome and Edge ask macOS for keychain access at that step; on Linux Ramu reads values using Chromium's fixed key and, when `secret-tool` can supply it, the desktop keyring secret, and reports cookies it cannot decrypt), name the profile, review, and import. The copy runs in the desktop's privileged process on a private copy of the source database, keeps each cookie's host-only, path, secure, HttpOnly and SameSite attributes and never widens it to another host, skips partitioned and expired cookies with reasons, and reports exact counts. The new profile stays hidden from agents and the catalog until **Keep profile**; **Discard**, a failed write or flush, or an app restart removes it and its data. Safari and Windows sources show why they are unavailable and offer manual sign-in. Some logins live outside cookies, so a successful copy does not promise a signed-in site. The mobile browser viewer names the profile kind and whether it is shared, and says when control was disconnected; viewer frames larger than about 3 MB are refused.

The pane's profile selector opens a new page in the selected website identity after confirmation, and closes the old page only when the replacement loads. Failed or stale replacement leaves the original page available. Clear website data and Delete profile review the exact affected tabs, including sign-in windows; a changed review is refused. They block new contexts, wait for native pages to close, clear site/HTTP-auth/cache data and restore a deleted selected host default through a checked settings patch. A failed cleanup preserves metadata for retry. Temporary contexts receive fresh opaque partitions after their last tab closes, so asynchronous cleanup can never wipe or lend sign-ins to a later context. A cleanup failure is reported in browser readiness; its closed partition is not reused.

Agent browser activity stays in the thread’s existing composer tray, including after a turn ends. Agent research and verification pages open in the background by default. The agent can explicitly request foreground presentation when the person asked to see a page, should review a visual result, or needs to sign in/take control; that request reveals the pane only if its host and thread are already active. The person opens an existing native tab from Browser activity or the browser button; background work never switches the selected host or thread. A user-opened page, including an explicitly replaced profile context, remains after the agent run ends; an agent’s Temporary pages close at run end.

The mobile browser viewer is a full-screen surface laid out like a phone browser: close, page title and a tab switcher; back, forward, a rounded address field (keeping an unsent address as a draft), reload and a ⋯ menu; a strip saying who is in control with one Take control or Give back to agent action; then the page. The ⋯ menu lists only actions that work for that tab: Paste, Hard reload, Display, New tab, Read page text, Upload a file, Downloads and Close tab. Display holds the Phone/Desktop layout choice (remembered on the device, host-managed browser only), the page's System/Light/Dark appearance, zoom from 50% to 300% and Clear cache, which removes saved page files but keeps cookies and sign-ins. Zoom and appearance stay with the tab for everyone viewing it; changing them, reloading or clearing requires holding control. The same controls work on the attached desktop's browser, which also accepts the phone's taps, typing and scrolling. Electron applies zoom per website, so other tabs on that site follow it. While the phone controls a host-managed Chromium page, the host lays the page out at the phone's visible size (as a phone browser would) and restores its default size as soon as control changes hands, so the agent never inherits the phone layout; pages in the attached desktop's browser keep their size because the person at the computer also sees them. Tapping a page field asks the host what kind of field took focus (never its value) and raises the matching device keyboard: text, email, number, phone, web address, search, password or multi-line. Typing, autocorrect, emoji, Backspace and Return are sent as they happen; when the keyboard opens the page refits and scrolls the field into view. When the agent opens a new page in an open thread, a dismissible live preview floats over the chat and opens that tab full screen; it refreshes every two seconds only while visible and the app is in the foreground.

The mobile computer viewer uses the same chrome without mode buttons. Tap clicks, a double tap double-clicks, holding right-clicks, dragging scrolls, holding then dragging drags, and two fingers pinch-zoom or move the zoomed picture on the phone only. A floating keyboard button raises the device keyboard to type on the computer. The ⋯ menu holds Keys and shortcuts (Esc, Tab, Enter, Delete, arrows, Home/End, Page up/down, then Copy, Paste, Cut, Undo, Redo, Select all, Find, Switch app and Close window using the computer's own command key, Command on a Mac and Control elsewhere), Paste from the phone's clipboard, Fit screen and Stop computer use. Keys are sent one at a time in order. Landscape is supported, including the sheets opened over it. When a thread gains a computer or the agent starts driving it, a live preview of the screen floats over the chat like the browser's; only one preview shows at a time, the most recently started, and a covered one returns when the corner is free.

On desktop, a thread's Computer tray shows a slowly refreshing thumbnail of the shared screen that opens the viewer, the control action, and a ⋯ menu with Stop the agent (its work stops, access stays) and Stop computer use (access ends). The viewer fills most of the window. While you control the computer, click the screen to use your own mouse and keyboard on it as in a remote desktop: clicks, double-clicks, right-clicks, drags, the scroll wheel, typing and shortcuts, with Command and Control swapped when the viewer and the computer differ. Paste types this computer's clipboard there. Escape goes to the computer while the screen has focus; click outside it to get the keyboard back. A Keys menu sends shortcuts the viewer's own system would intercept, such as switching apps. The host reports its own system so shortcuts use the right command key; a remote runtime falls back to its host's.

Mobile threads expose Browser activity for the owning execution host through a metadata-only query. A paired owner device views and controls whichever browser the agent uses without a separate grant: the host-managed Chromium, or, when the host browser is off, the attached desktop's browser through the same private event stream (frames, take/give control, navigation, tabs and dialogs). File uploads and downloads stay on the host-managed browser; the desktop's transfers stay on the computer. Opening the sheet prepares the host runtime when needed and lists existing tabs without transferring sign-ins. Public web addresses have an explicit Open in system browser action; loopback, IP, local/private-name and credential-bearing URLs remain on their owning computer. Metadata activity is not a control grant. Paired viewer-role devices receive no implicit browser access.

Browser tabs show the site’s same-origin favicon, with a globe fallback while unavailable or after an image failure. Icons are decorative beside the accessible tab title; page-provided file/app URLs and icons from unrelated origins are refused. Navigation clears the old icon.

Agent browser uploads use `browser_upload` with a relative file path in the active run’s cwd or an explicitly authorized additional workspace root. The server checks real filesystem containment, rejects `.git`, outside symlinks, directories and files larger than 8 MiB, and verifies that the file did not change while reading. Bytes use ordered 64 KiB private bridge chunks and opaque, single-use handles bound to host/thread/run/tab/control generation. Staging stays in memory (at most four files), expires after one minute, and clears on tab/run cleanup. Applying the file consumes a fresh file-input reference under the normal browser control lease; takeover or page changes require a new observation. File input changes can trigger website writes, so uncertain uploads are never replayed automatically.

The browser address toolbar always offers New browser tab, including in an empty pane. Downloads opens an anchored popover from the toolbar, preserving page space. Hiding the workspace leaves the right tool sidebar open.

Downloads use a one-use, 60-second tab/controller grant before the triggering click. The desktop stages at most two active downloads and twenty retained files, each bounded to 32 MiB; active transfers time out after two minutes. Takeover, tab closure, disconnect, crash and run stop cancel active transfers. Completed files remain thread-owned for up to an hour, survive turn completion for explicit native Save, and are removed on quit/restart. Website names never choose staging paths. Agent saves transfer ordered 64 KiB chunks into a new file in an authorized workspace root; existing files are never overwritten and incomplete files are removed. Control changes invalidate agent reads. Files are never opened automatically.

Link context menus in the workspace and human-controlled guest pages offer both system and integrated destinations for that click. Provider adapters report integrated MCP support and explicitly report that native browser suppression is unavailable; ACP runtimes that negotiate no HTTP MCP report integrated tools unavailable rather than claiming readiness.


Settings → Browser manages the default host-owned Chromium runtime for local, headless and remote browsing. First use downloads a compatible runtime when needed and checks its sandbox; it never disables sandboxing. Desktop and mobile view the same host-owned browser through a private Chromium compositor feed over authenticated, cursor-based requests (up to 30 displayed frames per second; only the newest frame is retained, bounded to 180,000 base64 characters). Frame delivery runs independently of tab/dialog metadata refreshes, and an unwatched feed stops after a short idle grace period. Older hosts or unavailable compositor feeds fall back to bounded screenshots. The viewer provides explicit Take/Give control, address/history, tabs, named website profiles, dialog answers, tap/scroll input, the device keyboard and an accessible page-text read. Viewing sends neither cookies nor browser JavaScript authority to the client. Hidden/background viewers stop requesting frames; five seconds without a heartbeat pauses input. A stalled frame request disables page input until viewing recovers. Mouse-wheel and touch-drag scrolling sends input while moving, with adjacent deltas coalesced behind in-flight input rather than dropped. Clicks, keys and text stay ordered; a handoff or uncertain input failure drops queued actions without replay. The optional local Electron browser still displays directly on its owning desktop; host-managed Chromium uses the live viewer on every client. A failed or disconnected action is never replayed automatically.

The host browser is enabled by default and downloads Chromium on first use. Paired owner devices use the existing host connection, like terminals, without extra setup or expiring browser grants. Viewer-role devices cannot use it. Runtime on/off and profile administration stay on the owning host; controller disconnect pauses rather than transfers ownership. Profile clear/delete reviews the exact affected tabs before closing contexts and deleting site data. Host profiles are independent from local desktop profiles; credentials never synchronize between them. Native import discovery reports installed-but-unsupported browser sources with a manual sign-in alternative and never reads source cookies/passwords during discovery. Verified cookie-copy adapters remain deferred.

## Computer use settings

Computer access, real-pointer app drags, sharing a screen with another host, and allowing a paired screen runtime use switches. All access switches default off. Locked-screen use also defaults off; switching it on first explains the signed macOS components and starts the existing local setup after review. Each thread still needs a screen/app grant. Keep host awake reuses the same switch and battery policy as System → Background & updates; both edit the same saved preference.

**Reset defaults** turns off host computer access, real-pointer drags, approved paired screen runtimes and Locked Use, and revokes active sessions and viewer grants. On the owning desktop it also turns off its outgoing screen-sharing choices. Installed tools and macOS permissions remain. A failed Locked Use disable is reported rather than claiming the reset finished.

Open Computer Use is an optional Ramu-managed install, outside the desktop bundle, pinned to the version tested with Ramu. Install and Update use version-specific tool directories, verify the executable version and retain earlier installations. The host reports the actual installed and supported versions. When a managed installation differs from the tested version, an update notice appears at startup and is checked hourly, with an Update action also available in Computer use settings. Updates require all computer sessions to be stopped and are administered on the owning host. Custom executable paths are owner-managed and must match the tested version. New upstream versions become update targets only after Ramu validates and advances its pin; Ramu does not install arbitrary latest releases. The current npm-based installer requires Node/npm on that host. **Install & set up** installs the runtime and automatically launches `ocu doctor` on the owning Mac for Accessibility and Screen Recording setup. Once installed, **Set up permissions** opens onboarding for missing permissions. Settings reads `ocu doctor --json` without opening onboarding and refreshes while the page is open and when focus returns. After Accessibility and Screen Recording are granted, the disabled button reads **Permissions granted**. Installation alone never implies permission readiness. An older running service that omits the snapshot offers **Restart service** through the existing restart confirmation; a failed snapshot offers **Retry permission check**, without launching onboarding. Setup remains available while agent access is off; it does not grant any thread access.

## Viewer thread controls

On a viewer-paired desktop, the thread remains readable and question/approval replies remain available. Stop/Resume, goal changes, model/access changes, provider routing, limit retries and host queue mutations are disabled. A queued message can still be read; removing or recalling a device-local outbox draft remains a local action, while retrying delivery is disabled. Attachment pick, paste and drop cannot start a host upload. The composer explains how to obtain full access. Desktop helper panels and existing asides remain readable, with helper stop/message and aside creation/deletion disabled. Their local drafts remain mounted when the role changes. Sent-message Edit actions are omitted for viewers, and an already-open rewind dialog cannot fetch a revert plan or apply changes. Selection can still quote into local drafts, including a new-thread draft; asking an aside is disabled. Header command-stop and Continue controls are disabled; Commit & push is omitted. Role reads belong to their host: a late answer from another host cannot change the visible role, and a failed refresh retains an already confirmed viewer restriction.

## Mobile schedules

A viewer-paired phone can inspect schedules and their run history, but gets no create/edit action or mutation swipe gestures. Run, Pause/Resume and Delete are disabled, with an explanation and a request to pair with full access. Edit deep links show the same notice without discarding a local draft. Restoring full access restores the draft and controls. Offline hosts retain readable cached schedules and disable mutations; callbacks recheck the current connection and role before issuing a schedule RPC.

## Mobile thread surfaces

Mobile keeps its native navigation bar. Compact titles and subtitles live in a bounded leading toolbar item beside the native back/close button, with two-line compact titles and single-line subtitles; trailing controls retain their own space. Compact headers, including Chat and Explorer, reserve their height and use the same solid screen background in both native appearances, so transcript text and bubbles never show behind their controls. The title uses the space between the buttons; tapping it reveals its complete text. Chat keeps Source control (Explorer for standalone threads) immediately left of a native three-dot dropdown. The leading title leaves room for both trailing controls. The project picker uses a centered native title. The thread menu (native dropdown on iOS, sheet elsewhere) has the same sections on both: workspace tools (Browse files, Terminal, Background terminals, Browser, Computer, Side questions), then Plan usage (including context usage) and the host, then the thread itself (Pin, Rename, Rename with AI, Archive, Copy thread ID), then Delete. Archiving from the menu leaves the thread. Side questions on mobile are one chat per thread, as with Claude's /btw: new questions (and `/btw` from the composer) continue it, a long-pressed passage is quoted above the next question, and the trash button clears it. Bottom composers (thread, side chat, Source Control commit) ride the keyboard with `useKeyboardInset`, and page scroll views let iOS lift a focused field above the keys. Search has one rule: list screens (Explorer, Search, Folders, Rules) use the iOS 26 bottom search bar; screens with their own bottom actions (Source Control's commit box) put search behind a navigation-bar button (`BottomSearch placement="header"`), so the two never overlap. On desktop and mobile, for every provider, read, edit and write tool rows name only the file (`Edited App.tsx +12 −3`, from `@ramu/shared/chat/fileTools`); opening the row shows the full path and, for changes, the diff. Mobile ends a turn that changed files with the same Changes card as desktop (file list, line totals, View changes into that review). Inline code on mobile is a small rounded pill like desktop's; long snippets wrap as untinted mono text. The composer uses separate compact Queue and Steer actions rather than a mode switch. Inside the composer, one horizontally scrolling activity row leads with compact Computer and Browser pills, shown only when the thread has a computer session or browser tabs, followed by a Terminal action when terminals exist. The Computer pill carries an icon-only Stop; the Browser pill shows the page title ("Using browser" while the agent drives it) and opens the live viewer. Usage and Browse files stay in the top menu. Managed background terminals keep their own tray; the generic Working item is omitted. Sending clears the native field immediately, before restored-attachment checks or local outbox persistence. Streaming text is published with the transcript in batches of up to 50 ms rather than updating every screen for each token; control and approval state remains responsive. The saved draft remains until acceptance; failure or destination clarification restores it. The input is disabled while that decision is pending. iOS large-title headers in Threads, Inbox and Schedules use distinct native appearances: the standard bar uses native chrome material over the screen background, while the separate scroll-edge appearance is transparent. UIKit transitions between them as content scrolls; there is no custom fade. The marked scroll views use the screen background color so the native edge blends into the dark or light surface. These screens do not draw a custom top fade over the content; title alignment and native toolbar actions remain compact. Explorer uses the same alignment.

**New thread** opens one native-stack page: choose a project, then write the opening message. It uses normal page navigation instead of a draggable form sheet. The project selector switches back to the list inside that same page, without closing/reopening a second sheet. Existing scoped draft links open the composer directly. The draft remains mounted while browsing projects; choosing the same project restores it, and another project uses its own saved draft. Its compact title uses the same two-line treatment with an 11-point subtitle. The welcome heading becomes compact above the keyboard; redundant “Runs on…” copy is omitted.

**Browser** and **Computer** are in the thread menu and also appear as compact pills above the composer while the thread uses them. Browser opens the viewer for the browser the agent uses. Computer lets a paired owner phone select an allowed runtime, the main display or a known app, then opens its viewer in the same task surface. Paired owners do not need a second viewer grant after a thread target is shared; installation, Locked Use and runtime-sharing administration remain on the owning computer. Viewer-role pairing does not grant these controls. Questions and other complex thread panels use a full-screen, keyboard-aware surface with scrollable content and a close action; simple pickers keep sheets.

An agent can call **computer_open**, optionally naming an app. Root threads open targets automatically, in any access mode, once computer use is enabled on the host; enabling it is the one grant. Helpers and hosts with computer use off request approval in the thread when a target is needed. Approval enables ordinary computer use and grants that target through the existing server validation; denial is remembered for the run, and stale approvals cannot replace a target chosen while the request was pending. It does not enable Locked Use or pointer fallbacks. The phone can also explicitly share a target from its Computer menu and revoke it with Stop computer use. Platform support and macOS permissions still belong to the execution computer.

Computer video probes `NativeModules.WebRTCModule` before loading WebRTC JavaScript, so a development build without that compiled module uses image frames without triggering a native-module red screen. A linked build uses video when available and falls back to image frames if peer initialization fails. JavaScript updates cannot add WebRTC to an existing native binary; rebuild the development client when enabling that optional video module.


Computer access is visible in mobile thread rows with a monitor badge and a target/status row below the title. The same status sits above the chat composer, outside the horizontally scrolling tools, so **Stop computer use** remains reachable. Stop revokes only that thread’s computer grant and pending input; it does not stop other threads or disable the host setting. Offline access is labelled last-known and cannot claim to stop a disconnected host. One metadata poll per connected owner host feeds every row, with unchanged responses retaining their previous context identity. The new-thread mark remains visible at a compact size above the keyboard. Explorer search and notices belong inside its inset-aware scroll header, below the native navigation bar.
