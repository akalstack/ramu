# UI development

The renderer uses shadcn/ui with Base UI, Tailwind 4, and shared theme tokens. `components.json` defines paths and the `@` alias.

Add registry components with `pnpm ui:add <component>` and review generated changes. Treat existing components in `apps/web/src/components/ui/` as upstream-owned; do not edit or copy them for Ramu-specific styling or behavior. Compose reusable app components outside that directory, following `components/desktop-button.tsx`, and keep shared variants, tokens and interaction states there. Preserve accessibility, refs and composition APIs. Base UI triggers use `render`, not `asChild`; dialogs use `onOpenChange(open, details)`, `initialFocus`, and `finalFocus`.

`ui.css` maps colors and typography to Ramu's tokens. `styles.css` contains shared desktop sizing. Tailwind preflight is omitted because Monaco and xterm manage their own styles. Reuse shared components for menus, dialogs, list rows, and empty states. Respect reduced-motion preferences.

## Chat disclosures and motion

Desktop composer trays share the chat column width constraint, a narrower inset surface, compact headers and consistent height-and-opacity disclosure motion for questions, goals and queued messages. Collapsing retains the current question page and input. Desktop tool groups, individual tool output, thinking, helper groups, file changes and worked-for summaries ease between closed and measured content height. The scroll-to-latest control fades and moves into view, and scrolls smoothly when activated. System Reduce Motion and the desktop Reduce Motion preference disable these effects. A message being sent appears immediately as local sending feedback; the host's transcript or durable queue entry replaces it without a second copy. The composer draft clears only after acknowledgement, so a failed send remains recoverable. Sending restores scroll following immediately instead of jumping after provider preparation finishes.

Mobile uses shared height-and-opacity disclosure motion for grouped tools, tool output, plans, worked-for summaries, question options, completed goals and helpers. New non-text transcript blocks fade and rise into place; initial history, earlier-turn pagination and recycled rows do not replay arrival motion. Generated replies keep existing text stationary and give only newly received words a brief fade, with no stagger or delayed typing queue, on desktop and mobile. Desktop word fades, message arrivals and thread-list actions share a 180 ms duration and the chat easing curve. Mark done, Reopen, Pin, Archive, Delete and recap actions animate removed and arriving rows and the remaining list positions without delaying the action. System Reduce Motion reveals content immediately. Sending on mobile already uses the local outbox for immediate feedback; new outgoing bubbles arrive with a short native scroll animation, while streaming output continues following without a delayed animation queue. Consecutive tool calls share one expandable row, while each call retains separate input and output. Plans retain pending, running and completed states. Answered questions show the question and answer with their original options available on expansion, including typed answers and independent replies. Native sheets handle long logs, helper details and full-screen content; message actions remain available through long press.

## Workspace and terminals

Background terminal rows show whether the person or agent requested a stop. A human stop adds one transcript note per command, including after a retry or server restart, without submitting a message or waking an idle agent. Conversation handoffs retain that instruction: inspect current command state and do not relaunch without a new request. A stop request does not itself establish that the command has exited.

Git status, branch lists, history, stashes and change counts are cached by host, repository and checkout path. Threads and hover cards using the same current checkout or worktree share the latest state, keeping it visible during background refreshes. Separate worktrees and hosts keep separate state.

Thread and workspace panes share a resizable split. Bottom terminals span both panes. Terminals in the workspace share the file tab strip; selecting a terminal group shows its shells in place of the file. Resize handles support dragging and arrow keys, Home, and End.

Terminal tabs contain groups of panes. Splitting keeps the shell in its group; moving a pane to a tab preserves it. Hidden groups keep running. Layout and grouping persist with workspace state.

Persistent commands Ramu launched for a thread (`term.background.*`) are owned by the host, not by a tab. The thread's activity dock shows a **Background terminals** count whenever any exist, including after the agent is idle. **Open output** attaches the existing terminal by identity without starting a shell; closing that tab leaves the command running. **Stop** asks the command's process group to end and shows *Stopping*; **Force stop** appears only then. Repeating a request, or stopping a command that already ended, is safe, and final output and exit code stay readable. The host persists command ownership and a bounded output tail in SQLite. After a restart, commands without a verified live handle show **Unknown**, with inspect-only saved output and no input/stop controls. Completed commands retain their known exit outcome. Restored records never replay a command or authorize control by a saved PID. Deleting a thread stops its reviewed live commands first; unknown records require explicit acknowledgement and retaining the checkout files.

On mobile, the thread activity count and thread action open a background-command sheet even after the agent is idle. It lists commands from that execution host and thread, and shows bounded read-only output without opening an interactive shell. Hiding the sheet leaves the command running and preserves the draft. Output cursors discard duplicate chunks and retain the terminal viewport when the bounded tail advances. Stop rechecks live ownership and capabilities; force stop requires an earlier graceful request and explicit confirmation. Offline rows and restored Unknown records remain read-only, and older hosts show an update hint. Native input is disabled in the output viewer.

Agents can discover `background_terminal_launch`, `background_terminal_list`, `background_terminal_inspect` and `background_terminal_stop` through the existing Ramu tool connection. Launch uses the authenticated session's checkout and thread; arguments cannot redirect it to another host or directory. In Full access launch runs directly. In other access modes each launch asks for a once-only approval of the exact command through the thread's existing permission prompt; a refusal is final for that request and a change of access while waiting cancels it. Access is checked again on invocation. Stopping a command already owned by the thread needs no further approval. Commands launched by a sub-agent show **Started by a sub-agent** on desktop and mobile. Inspect returns the most recent bounded output with its cumulative cursor. Force stop requires a prior graceful request and host support. These tools manage Ramu-owned commands; commands started through native provider shells are not automatically registered. Launch records ownership before spawning. Streaming output is checkpointed about once per second and lifecycle changes flush it immediately, with the most recent 64,000 characters retained across restart; abrupt termination can lose the final uncheckpointed tail. Each thread retains its newest 100 records plus older active or uncertain records. Closing an output view retains the command record. Output views persist the exact background command ID and never open a substitute shell when it becomes unavailable. Automated archived-thread cleanup skips active or uncertain commands. Desktop and mobile deletion dialogs list unsettled managed commands before approval. The host rejects commands added after review and prevents new managed launches or shells during deletion. Graceful stop must finish within three seconds; otherwise the thread and output remain available for inspection and optional Force stop. No automatic force stop is performed. An unknown record cannot stop a process: the user can explicitly forget it while deleting only the thread, with checkout files kept. Worktree removal is blocked while command status is unknown, and shared worktrees remain protected. Failed worktree removal retains final command history for retry. Bulk archived deletion refuses unsettled commands and asks for individual review. Older clients cannot silently delete a thread with these commands; a host that predates reviewed deletion requires an update.

Markdown files open in **Preview**, a rendered view without editing. The file header offers **Source** (raw Markdown), **Edit** (rendered editing), and **Preview**. Settings → Editor → Default Markdown view changes the opening mode for newly opened files; switching a mode in one open file keeps its current buffer. Links to a source line or search match open Source so the requested location remains visible.

Editors, terminals, and attachments use native context menus. Keep clipboard and save-dialog operations in the main process.

## Notifications and background activity

The desktop bottom bar shows the current background job's label, or a running count for multiple jobs, beside a bell that counts only retained notifications. The job signal disappears when idle; a disconnected host shows Reconnecting or Pair again. Both controls open the same **Notifications and activity** popover, with Running first and Notifications below a divider. Notification dismissal and Clear all do not cancel running work.

Running jobs offer **Stop** only when their execution host supports cancellation. Stop stays disabled with **Stopping…** until the request settles, and failures remain visible for retry. App update checks/downloads, memory maintenance, skill learning, recaps and the managed Antigravity runtime update support cancellation. Cancelling a managed runtime update interrupts download, extraction or validation, cleans staging files and preserves the active version; once atomic activation starts, it finishes. Git operations and external CLI installers do not expose Stop.

## Usage limit state

A thread at a usage limit is idle, not failed, and every surface words it **Limit reached · resumes around 5:00 PM** (or **resuming automatically** when the time is a guess). **Paused** means only a goal you paused yourself. The sidebar clock, the Home and Inbox **Limit reached** group, the goal bar and the mobile transcript all read the thread's `provider-wait` event; the shared helpers in `packages/shared/src/chat/providerWait.ts` and `limitPolicy.ts` (`providerWaitState`, `effectiveAutoResume`, `limitTrayView`, `limitChoiceOf`) keep desktop and mobile in step.

- **Settings → Models → When a usage limit is reached** is one choice: **Switch to another model**, **Wait on this model**, or **Stop and let me decide**. It writes both `defaultAutoFallback` and `fallback.autoResume` (`settings/LimitChoiceRow.tsx`). A stored switch-and-stop combination shows as a fourth item, **Switch, then stop if none has room**. **When to switch** and **Fallback order** apply only to the switching options. Across hosts the row reads **Mixed** when either value differs.
- **Tray row** (`models/ProviderWait.tsx`): clock, title, detail, then a button and the per-thread **Auto-resume** menu. **Try anyway** is quiet while a reset is known and ahead; **Try again** is primary when the time is unknown or guessed; **Resume** is primary when the limit has reset and auto-resume is off. All three call `agent.retryLimitNow`; a failed try reads **Still limited**. **Auto-resume** offers **Use default (on/off)**, **On** and **Off** through `agent.setAutoResume`, and the provider chip menu offers the same three items. The chip is always there when the thread has the control: near or at a limit it is the full chip, otherwise a quiet icon-only chip whose menu holds the three items and **Fallback settings…**. While held at a limit its menu also lists **Continue with <provider>** for every other provider not known to be limited (`models/continueWith.ts`); choosing one runs `agent.configure` then `agent.retryLimitNow`.
- **Composer** while at a limit: the placeholder says when the message is sent (or that it is queued until you resume), the send label is **Queue**, the empty-box play button becomes **Try again** or **Resume** when the tray makes that the main button, and the provider chip shows **Limit reached**. Stop is not shown because the thread is idle.
- A reset notice fires once per wait while auto-resume is off (desktop `agentNotifier`, mobile push).
- A **Context handoff** separator adds a line such as "Carried events 1–412 from Claude (compacted handoff, 3 old results shortened)" once the next launch has built the handoff (`views/agent/handoffLine.ts`). Returning native sessions say **new events only**. Full-history transfers say **compacted handoff** if content was shortened, omitted or replaced by a checkpoint (whose event boundary is shown); otherwise they say **full handoff**. Settings changes that resume the native conversation use **Settings changed**.

## Command palette

The palette (`apps/web/src/palette/`) is a set of sources, each drawn as its own group. No prefix searches files, projects, threads and text inside project files; `>` runs commands only; `#` searches file contents only. Results stay in their group (never one flat ranking), show the first few with **Show more**, and render through `VirtualList`.

To add a source, write a `PaletteSource` (`palette/sources.ts`) and add it to the list in `Palette.tsx`:

- `id`, `label` (translated), `priority` (group order), `modes` (`all`, `commands`, `content`).
- `query(text, { signal, limit, mode })` returns a batch (synchronous), a Promise, or an AsyncIterable of batches. Each result carries its label, optional highlight offsets, detail, snippet and a `run` that opens it.
- `minLength`, `debounceMs`, `limit`, `initialShow`. Keep cheap sources at `debounceMs: 0`; anything that waits on the server needs a debounce and a minimum length, and should honour `signal`. A new keystroke aborts the old query and its late result is dropped. Set `scope` (for example the task id) so a running query survives rebuilds of the source list but not a project switch.

Content search reuses `files.search` (ripgrep, ignore files, binary and size limits, `SEARCH_RESULT_LIMIT`). The server has no cancellation, so a superseded search finishes in the background and is ignored. Tests for the pure parts are in `apps/web/test/palette*.test.ts`.

## Legacy models

The model picker hides older models by default. **Show legacy models** reveals them with a **Legacy** label; **Hide legacy models** collapses them again. Search includes older models, and the selected model and favorites remain visible. This presentation preference belongs to the device and does not change thread settings, drafts, custom sets or provider availability.

The execution host publishes optional `isLegacy` metadata with each provider catalog. Explicit lifecycle metadata wins. When that metadata is absent, Ramu marks an older recognized Codex or Claude family version only when the same provider reports a newer current version of that family. Aliases, custom IDs and unknown families are not guessed. Hidden provider entries are not reintroduced. Automatic Defaults prefer current models; if the entire usable catalog is legacy, they retain real catalog choices rather than inventing unavailable placeholders. Saved legacy choices remain selectable and use the usual pre-send availability checks.

## New-thread model defaults

Settings → Models → Model sets offers **Steps** and **Model then effort**. Steps walks the configured model/effort presets; Model then effort keeps the selected model while adjusting its actual supported efforts, with the existing model picker available separately. Changing the flow preserves the current provider/model/effort, composer, access/fallback policy and custom sets. Mobile exposes the same effective choice in the selected host’s Providers & models settings; older hosts omit the unsupported row. This is a host setting shared by its clients, not a global or phone-only preference.

The read-only **Default** set shares up to five distinct model/effort choices evenly across available providers in Codex, Claude, Antigravity, Cursor and OpenCode order. Extra slots follow that order; a provider with too few choices passes its spare slots to the others. If fewer than five distinct supported choices exist, the slider shows only those choices. Codex keeps its Luna/Sol/Astra presets and prefers Sol Low when offered. Smaller allocations keep lighter and everyday choices plus a capable option. Claude prefers Sonnet and Opus when reported; other catalogs begin with their reported default model. A provider with one slot uses its reported default model and effort (Codex prefers Sol Low). Models without effort controls contribute one choice per model. These provider groups do not rank quality across providers.

Refresh and provider-configuration changes regenerate untouched Defaults on the execution host. The user can select a step and a new-thread default step, but editing, renaming, reordering or deleting the automatic set requires a custom set instead. Previously edited sets remain editable and are preserved by their generation fingerprint; unmarked older sets are retained unless their untouched legacy shape is proven. A surviving selected default step stays selected; a removed step falls back to a valid generated default. Existing thread settings do not change. Empty or failed catalogs never erase a known generated set. Before any usable catalog is known, legacy placeholders remain subject to pre-send availability checks.

The model picker follows the selected project's provider/model preferences after host catalog validation. Its compact notice names the source file or explains an unavailable preference; manual model selection and **Use host default** preserve the draft. **Use project default** restores model inheritance. Explicit choices retain the displayed access/fallback policy and stay qualified by host and draft scope. Revalidation happens before creating a thread or enqueuing a message; superseded or changed results require review. Offline mobile drafts without loaded host defaults require a reviewed choice. Existing sessions and queued settings are not replaced by configuration changes. See [Configuration files](CONFIGURATION.md#repository-configuration) for precedence and storage.

## Workspace defaults and branch names

Desktop new-thread drafts retain optional manual/generated branch candidates and their bounded naming request in the host/project workspace sidecar. Manual edits survive prompt changes; generated candidates are restored only for matching prompt/title/settings. Mode changes retain optional candidates, while choosing an existing workspace skips naming. Storage failures retain the complete in-memory choice for Retry, and a late Send acknowledgement cannot delete a newer branch edit. This metadata follows the existing 30-day automatic draft expiry.

On mobile, New thread → Workspace exposes optional branch-name details for supporting hosts. Manual candidates remain editable offline and survive prompt changes; generated candidates belong to the prompt and naming settings that produced them. Generate name and Preview worktrees never create a thread. Dismissal, edits and host/project switches cancel or discard pending results. A provisional preview shows each repository’s base commit, branch and path. **Keep these base commits** freezes its bases when the unchanged request is queued; names and paths remain advisory. Editing the request requires a new review. A confirmed moved-base rejection offers review and explicit retry from the pending message, preserving its request ID and naming inputs. An uncertain delivery cannot replace its plan. Before enqueue, reviewed previews last only for the mounted form; candidates remain in the current composer state.

Settings → Git → New threads & worktrees saves the execution host's default checkout mode and Git branch prefix. Current checkout remains the initial default. An untouched new-thread draft follows the host default; a manual choice or explicit existing workspace wins. Use default clears a manual override. Plain folders and repositories without commits visibly fall back to Current checkout when following a default; an explicit worktree request is blocked instead.

**Rename workspace…** in a desktop thread’s menu or the selected-workspace menu edits the shared workspace label. On mobile, select an existing workspace in New thread → Workspace, then choose **Rename workspace**. The label is shared by all threads using that workspace; thread titles, branch names and folder paths retain their existing identities. The host checks the original label before saving, so a concurrent change asks the person to reopen the editor and review it. Lost-acknowledgement retries are safe, offline saves are disabled, and older hosts show an update hint. Viewer grants cannot rename labels.

Desktop new-thread drafts retain a host/project-qualified workspace choice: Use default follows current host/repository defaults, a manual mode stays explicit, and an existing workspace keeps its exact ID. Explicit workspace-scoped entry points override the restored choice. An unavailable saved workspace requires another choice before creation. Failed persistence keeps the current session choice with Retry; unreadable or unsupported saved metadata requires a fresh workspace choice and leaves message text intact. A late send acknowledgement clears only the unchanged choice it sent. This active metadata expires after 30 days.

Fixed names use `ramu/<title-slug>` by default, support an empty or nested namespace, and need no provider. The server owns allocation, includes pending database bindings when finding collisions, and stores the exact base commit for setup. A preview cannot authorize filesystem paths. A moved base with an explicit preview requires review. Creation request IDs deduplicate retries; setup refuses unowned branches and can retry partial failures. Settings also supports Semantic name and Custom instructions. These produce a complete branch name without adding the fixed prefix. Only the bounded opening message and naming instructions are sent to isolated analysis, with no tools, a 15-second deadline and no deferred provider-limit wait. Invalid output, unavailable providers and deadlines use `ramu/<title-slug>` and retain a visible “Used default branch name” notice on the thread.

Desktop worktree Details offers Generate name, Cancel and an editable branch name. Previews are provisional before generation; sending can generate automatically. Prompt/settings changes discard generated suggestions, manual edits win over late results, and abandoning generation asks the host to cancel it. Generated collisions get bounded suffixes; a manually entered name is used exactly or rejected if taken. Directory paths always come from the title. No generated result renames an already-created branch.

Naming runs outside the global allocation lock. In-flight creation request IDs coalesce generation; completed retries return the recorded allocation before contacting a model. Mobile freezes the strategy, instructions and bounded opening message with the resolved checkout mode and prefix in its outbox, and generates on the host at delivery. Mobile New thread offers existing isolated workspaces in its Workspace sheet. The host/project-qualified active draft retains default/manual/reused selection across reopening; changing checkout keeps the composer intact and resolves file references in the explicitly selected checkout. Existing-workspace IDs are frozen in the outbox and reused without branch generation or new-worktree planning; the server revalidates project membership and readiness before creating the thread. A missing workspace never silently becomes a new one. Hosts without workspace-default discovery can still accept an explicitly selected Current checkout. Explicit native generation/editing, desktop draft provenance, frozen preview bases and additional cross-host acceptance remain in the workspace plan.

## Integrated browser

**Settings → Browser** separates the execution host's agent-browser choice from the device's clicked-link destination. Host defaults and per-provider overrides choose integrated or existing provider setup; new Default/Temporary tabs follow the host's selected profile. New empty installations default to integrated; legacy settings without a browser choice conservatively keep provider setup, including external CLI configurations Ramu cannot inspect. Explicit choices are preserved. Native/provider acceptance remains pending. Provider-native browser tools may remain available; Ramu does not overwrite global provider configuration or claim exclusive browser routing.

On the local execution host, explicitly selected integrated-browser root runs in Full access get status/profile-list/tab-list/open/snapshot/navigate/click/type/select/press/scroll/wait/screenshot/diagnostics/dialog/close tools. The server derives their thread/run identity, freezes the choice with the provider process, and binds operations to one registered desktop event stream. Readiness requires a completed registration handshake. Disconnects, timeouts and run stop fail pending work without replaying an operation; uncertain actions require inspecting the page before continuing. Stale provider connections cannot keep driving it. Other access modes and Ramu-managed helpers request browser-only approval through the existing thread permission UI. Approval lasts only for the current turn and includes website actions and scoped workspace transfers; denial cannot be retried in that turn. Helpers can use only tabs they opened after their own approval, never parent tabs. Stop/abort cancels pending approvals. Native provider helpers sharing their parent’s MCP connection cannot be identified as separate browser principals. An explicitly configured host-managed Chromium runtime supports remote execution and viewing through separate device/thread grants.

The guest has Chromium sandboxing, context isolation, no Node access or preload, and denied site permissions. Downloads require a one-use grant from the current controller. Fixed code in an isolated world reads bounded visible text and element references without cookies, storage or form values. DOM changes, navigation, ownership changes and an attempted action expire references. Password typing, rich editors, custom selection widgets and frames still require human interaction. Native select controls accept exact visible labels; keyboard and scrolling actions consume their observation. Waits are bounded and cancel on ownership changes. Screenshots capture only the guest page as a bounded JPEG; network excerpts retain method/origin/status/error rather than paths, queries, headers or bodies. Website-dialog replies require the exact live dialog id and current controller, and can unblock a preceding click without replaying it. A person's takeover blocks new agent mutations, waits for earlier input to drain and then enables native mouse/keyboard input. Disconnect pauses control; it never gives the page to the agent automatically.

The pane adopts the actual agent tab on first use in the active thread without opening a duplicate; background work never switches hosts or threads. Open browser also discovers existing tabs for its thread, and its tab selector lets the person choose one or start another. Native navigation, titles and controller changes refresh the pane. Take control / Give control to agent use a server-resolved active run; opening in the system browser stays a device action. Default shares website sign-ins on this desktop; Temporary is isolated per run and cleared at run end. Native transfer/viewer acceptance, optional verified session import and provider acceptance remain in the [browser plan](BROWSER-PLAN.md). Implementation checks are currently held until all planned code changes are complete; this guide describes the intended behavior of the working-tree implementation, not a native/provider acceptance result.


Settings → Browser manages named profiles on their owning desktop. Metadata is a bounded, atomically replaced local catalog; cookies and other website data stay in Chromium partitions. A damaged catalog disables mutation rather than overwriting unknown identities. Default and Temporary cannot be renamed or deleted. Sign in opens a user-only sandboxed window in the selected persistent profile without creating a project, thread or provider request. It reuses an unfinished sign-in window instead of restarting it. **Import…** (Chrome, Chromium, Edge and Firefox on macOS and Linux) copies sign-in cookies once into a new profile: choose a source profile, then websites (none preselected; Chrome and Edge ask macOS for keychain access at that step; on Linux Ramu reads values using Chromium's fixed key and, when `secret-tool` can supply it, the desktop keyring secret, and reports cookies it cannot decrypt), name the profile, review, and import. The copy runs in the desktop's privileged process on a private copy of the source database, keeps each cookie's host-only, path, secure, HttpOnly and SameSite attributes and never widens it to another host, skips partitioned and expired cookies with reasons, and reports exact counts. The new profile stays hidden from agents and the catalog until **Keep profile**; **Discard**, a failed write or flush, or an app restart removes it and its data. Safari and Windows sources show why they are unavailable and offer manual sign-in. Some logins live outside cookies, so a successful copy does not promise a signed-in site. The mobile browser viewer names the profile kind and whether it is shared, and says when control was disconnected; viewer frames larger than about 3 MB are refused.

The pane's profile selector opens a new page in the selected website identity after confirmation, and closes the old page only when the replacement loads. Failed or stale replacement leaves the original page available. Clear website data and Delete profile review the exact affected tabs, including sign-in windows; a changed review is refused. They block new contexts, wait for native pages to close, clear site/HTTP-auth/cache data and restore a deleted selected host default through a checked settings patch. A failed cleanup preserves metadata for retry. Temporary contexts receive fresh opaque partitions after their last tab closes, so asynchronous cleanup can never wipe or lend sign-ins to a later context. A cleanup failure is reported in browser readiness; its closed partition is not reused.

Agent browser activity stays in the thread’s existing composer tray, including after a turn ends. Agent research and verification pages open in the background by default. The agent can explicitly request foreground presentation when the person asked to see a page, should review a visual result, or needs to sign in/take control; that request reveals the pane only if its host and thread are already active. The person opens an existing native tab from Browser activity or the browser button; background work never switches the selected host or thread. A user-opened page, including an explicitly replaced profile context, remains after the agent run ends; an agent’s Temporary pages close at run end.

Mobile threads expose Browser activity for the owning execution host through a metadata-only query. A ready host-managed browser also offers View host browser after the owning host grants this device/thread access. Opening the sheet lists existing tabs without opening a runtime or transferring sign-ins. Public web addresses have an explicit Open in system browser action; loopback, IP, local/private-name and credential-bearing URLs remain on their owning computer. Metadata activity is not a control grant. Paired viewer-role devices receive no implicit browser access.

Browser tabs show the site’s same-origin favicon, with a globe fallback while unavailable or after an image failure. Icons are decorative beside the accessible tab title; page-provided file/app URLs and icons from unrelated origins are refused. Navigation clears the old icon.

Agent browser uploads use `browser_upload` with a relative file path in the active run’s cwd or an explicitly authorized additional workspace root. The server checks real filesystem containment, rejects `.git`, outside symlinks, directories and files larger than 8 MiB, and verifies that the file did not change while reading. Bytes use ordered 64 KiB private bridge chunks and opaque, single-use handles bound to host/thread/run/tab/control generation. Staging stays in memory (at most four files), expires after one minute, and clears on tab/run cleanup. Applying the file consumes a fresh file-input reference under the normal browser control lease; takeover or page changes require a new observation. File input changes can trigger website writes, so uncertain uploads are never replayed automatically.

Downloads use a one-use, 60-second tab/controller grant before the triggering click. The desktop stages at most two active downloads and twenty retained files, each bounded to 32 MiB; active transfers time out after two minutes. Takeover, tab closure, disconnect, crash and run stop cancel active transfers. Completed files remain thread-owned for up to an hour, survive turn completion for explicit native Save, and are removed on quit/restart. Website names never choose staging paths. Agent saves transfer ordered 64 KiB chunks into a new file in an authorized workspace root; existing files are never overwritten and incomplete files are removed. Control changes invalidate agent reads. Files are never opened automatically.

Link context menus in the workspace and human-controlled guest pages offer both system and integrated destinations for that click. Provider adapters report integrated MCP support and explicitly report that native browser suppression is unavailable; ACP runtimes that negotiate no HTTP MCP report integrated tools unavailable rather than claiming readiness.


Settings → Browser also offers an optional host-managed Chromium for headless execution and remote viewing. Setup downloads a compatible runtime when needed and checks its sandbox; it never disables sandboxing. Desktop and mobile view the same host-owned browser over bounded authenticated JPEG requests (1024×768, at most two captures in flight), with explicit Take/Give control, address/history, tabs, named website profiles, dialog answers, keyboard/tap/scroll controls and an accessible page-text read. Text entry is masked by default and clears only after a successful send. Viewing sends neither cookies nor browser JavaScript authority to the client. Hidden/background viewers stop requesting frames; five seconds without a heartbeat pauses input. A failed or disconnected action is never replayed automatically.

Only the owning host can provision the runtime, administer its profiles or grant paired owner devices one hour of browser viewing/control and scoped transfers for a specific thread. Pairing and viewer roles confer no browser grant. Revocation/expiry/restart removes the grant; controller disconnect pauses rather than transfers ownership. Profile clear/delete reviews the exact affected tabs before closing contexts and deleting site data. Host profiles are independent from local desktop profiles; credentials never synchronize between them. Native import discovery reports installed-but-unsupported browser sources with a manual sign-in alternative and never reads source cookies/passwords during discovery. Verified cookie-copy adapters remain deferred.
