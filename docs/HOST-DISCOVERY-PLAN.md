# Automatic host discovery

Proposal, 2026-10-18. All work below remains unfinished. Let desktop and mobile find nearby Ramu hosts without asking the user to type an IP address. The general term is **network service discovery**; the feature name is **Automatic host discovery**. Evaluate mDNS/DNS-SD (often called Bonjour) as the initial local-network mechanism. Dependency and native-platform choices remain implementation decisions.

Keep this plan limited to unfinished work. Move shipped behavior into the remote-access feature guide and [mobile guide](../apps/mobile/README.md), remove completed items, and delete this plan when finished.

## Delivery

A person opens Add host, recognizes a nearby machine, pairs through the existing code flow and opens its threads after authenticated connection verification. Deliver initial discovery and pairing without requiring route failover or automatic address migration. Keep QR/manual/SSH fallbacks immediately reachable as specified below; discovery permissions or failure must not become a setup dead end. Validate this flow on a supported device with both discoverable and multicast-blocked networks. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

## Scope and existing behavior

- Discover hosts on the same local network, then use the existing pairing flow. Finding a host does not grant access or create a pairing code.
- Preserve manual address entry, mobile QR pairing, desktop SSH connections and existing saved hosts. Desktop can still display a pairing QR code for a phone; desktop QR scanning is outside this plan. Discovery is optional assistance; blocked multicast, guest Wi-Fi, VPNs and routed networks must leave these paths usable. Internet discovery, relays, subnet scanning and VPN-provider account integrations are outside this plan.
- `apps/server/src/remote/network.ts` already owns listener settings and candidate addresses. Advertise only while remote access and a separate **Discoverable on this network** setting are enabled; default discoverability off and explain that nearby devices can see the chosen host name. Honor the selected listening interface and never enable network access as a side effect of discovery.
- `apps/server/src/remote/presence.ts` and `packages/client-runtime/src/presence.ts` already send and verify signed availability announcements for paired clients. Preserve that reconnect mechanism. It does not discover unpaired hosts or authenticate a newly advertised address.

## User experience

1. On mobile, opening **Pair / Add host** defaults directly to nearby-host discovery and starts browsing, requesting local-network permission when needed. Keep the choices ordered **Nearby hosts → Scan QR code → Enter details manually**: discovery is the primary flow, QR scanning is secondary, and manual address/code entry is the final fallback. QR and manual choices remain immediately accessible during discovery, including empty, denied and unavailable states; do not require a failed scan or a timeout to reach them. Opening pairing must no longer launch the camera immediately. On desktop, opening **Connect to a host** also defaults directly to nearby-host discovery and starts browsing, requesting local-network permission when needed. Order its choices **Nearby hosts → Enter address / SSH**. Keep manual address and SSH entry immediately accessible during browsing and in empty, denied and unavailable states; no camera or QR-scanning step. On both platforms, start browsing only when the discovery flow opens; stop when it closes, switches to another connection method or the app backgrounds.
2. Show host name, candidate address and an existing-pairing indicator where identity is verified. Support searching, empty, permission-denied, unavailable and retry states. Say **No hosts found** without claiming no hosts exist; explain how to enable discoverability or use the platform’s fallback: QR/manual entry on mobile and address/SSH entry on desktop.
3. Selecting an unpaired result reviews the address and opens the existing pairing-code flow. Keep transport warnings, role selection and host-side pairing approval/code issuance intact. Never pair or send a stored credential merely because an advertisement has a familiar name or identifier.
4. Expire disappeared results and merge multiple interfaces into one host only when the available identity evidence permits it. Distinguish duplicate names. Preserve a selected row while refreshing, and revalidate its endpoint before continuing if it changes.
5. An already-paired host whose address changed may offer **Review new address**. Require verification against the paired identity or explicit re-pairing before replacing its saved endpoint. Do not silently redirect authenticated requests based on an unauthenticated advertisement.

Follow [Architecture](ARCHITECTURE.md) and [UI](UI.md). Use existing desktop app-composed controls outside `components/ui/` and existing native mobile sheets/rows. Include English/Indonesian strings, keyboard navigation, screen-reader status announcements and large-text layouts. Host advertisement settings use the existing validated named server API and administration allowlists; device browsing uses typed local/native bridges, not RPC to the selected remote host. Keep discovery state device-local and paired-host queries/events host-qualified; no additional renderer or parallel host store is needed.

## Implementation work

1. **Protocol and platform spike.** Verify mDNS/DNS-SD advertisement and browsing on supported packaged desktops and physical iOS/Android devices. Choose maintained dependencies/native adapters after reviewing licensing, packaging, OS permissions and interface selection. Decide the service type and a versioned minimal metadata contract: display name, opaque host identifier, protocol version and endpoint transport/port. Treat every advertised field as untrusted; identifiers are hints until authenticated. Do not broadcast pairing codes, tokens, project paths, usernames or provider/account details. Document name disclosure and identifier tracking implications before finalizing the contract.
2. **Host advertisement lifecycle.** Add the saved discoverability control to host Settings/CLI through existing network administration boundaries. Start advertising only after the listener binds successfully, publish the actual bound endpoint, and withdraw on disable, shutdown or listener/interface change. Handle name conflicts, network changes, sleep/wake and advertisement failures without breaking the listener or startup. Do not publish loopback-only or non-listening interfaces; verify specific-interface binds cannot leak advertisements onto other networks.
3. **Device-owned browsing.** Put desktop discovery in Electron main behind narrow typed preload APIs; put mobile discovery behind a native adapter with platform permission/configuration changes. Browsing runs on the connecting device, not the selected remote host. Share only pure result-validation/expiry/state logic under `packages/shared`; keep native dependencies out of shared code. The existing Node-only client runtime is not a universal mobile adapter. Bound result counts, metadata lengths, browse duration and resource use; cancel subscriptions and reject late callbacks after close/retry.
4. **Pairing integration.** Make discovery the default entry screen on both platforms: mobile uses nearby hosts, then QR, then manual entry, replacing the current immediate-camera entry; desktop uses nearby hosts, then manual address/SSH entry, without QR scanning. Feed validated candidate endpoints into existing desktop/mobile pairing forms. Handle IPv4/IPv6 and scoped addresses through existing URL validation, explicitly defining unsupported address forms. Never fetch arbitrary URLs from TXT metadata or accept embedded credentials. Keep advertised metadata out of privileged IPC/RPC routing. No browser LAN scan: browser clients retain manual/QR setup unless a separate supported discovery bridge is designed.
5. **Pairing lifecycle and host identity.** Implement the pairing enhancements below through existing server/client boundaries. Audit existing pairing identity/certificate guarantees before attempting address migration. If they cannot securely verify continuity, ship discovery for initial pairing first and retain explicit re-pairing for changed addresses. Coordinate native HTTPS/certificate work with the [remote security plan](REMOTE-SECURITY-PLAN.md); discovery must not weaken HTTP consent, certificate checks, credential expiry or revocation.

## T3 Code reference and pairing enhancements

Use T3 Code as a reference, inspected at [`9c161462c94f7d9d6d9169da5c841457cbadf213`](https://github.com/pingdotgg/t3code/tree/9c161462c94f7d9d6d9169da5c841457cbadf213) on 2026-10-18. These observations concern that revision, not every released build. Its [remote-access guide](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/docs/user/remote-access.md) documents one machine with multiple routes, re-pairing to update grants, and separate revocation of unused links and established sessions. Its [pairing grant store](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/apps/server/src/auth/PairingGrantStore.ts) supplies expiring one-time grants, revocation and change events. Its [route implementation](https://github.com/pingdotgg/t3code/blob/9c161462c94f7d9d6d9169da5c841457cbadf213/packages/client-runtime/src/connection/routes.ts) tracks credential provenance and guards against sending a credential through an unapproved plain-HTTP route. Use these behaviors to inform Ramu's implementation; review licensing before copying source. This reference does not establish that T3 implements the proposed nearby-host discovery or platform choice order.

Keep Ramu's existing one-time codes, attempt throttling, per-device credentials/revocation, owner/viewer roles, signed reconnect announcements and remote-access settings. Extend `apps/server/src/remote/`, existing named methods/contracts, Electron main-owned connections and mobile storage/runtime. Keep the single desktop shell, host-qualified stores/events and Ramu's composed/native controls; do not introduce T3's Effect services, environment registry, cloud account or relay architecture.

1. **Stable host identity and multiple routes.** Define a durable server identity with a verifiable continuity mechanism, persisted across normal restarts/upgrades. A UUID, hostname, discovery TXT field or successful health check alone is not proof. Bind the identity during explicit pairing over the approved transport; define key/certificate changes and cloned/reset host profiles as review/re-pair cases. Extend existing saved-host records with verified identity and route metadata so LAN/VPN addresses and desktop SSH can belong to one host. Keep credentials and grants associated with the route/session that issued them; route selection must not combine permissions or upgrade a viewer. Expose routes inside existing host details, including the active route and effective access, using current device-local connection controls. Keep reconnect/backoff and signed wake behavior; automatic route probing, preference and failover need bounded attempts and cleanup, not a new background polling service.
2. **Safe re-pairing and migration.** Re-pairing a verified known host updates its grant or adds a route while retaining its local host ID, drafts, unread state, queues and selection. Today desktop re-pairing an address creates a new saved ID and mobile primarily matches addresses; migrate both formats without losing host-qualified data. Merge only with verified identity and an explicit conflict policy: never overwrite another host's drafts, merge queued sends blindly or deduplicate by display name/IP alone. Retain unresolved legacy duplicates for review. Revoke/clean up a superseded remote credential only after the replacement is durably stored and verified, with recoverable failure states; local Forget and host-side Revoke remain distinct actions.
3. **Cancellable pairing offers.** Give each pending offer a non-secret ID and lifecycle state in the existing `DeviceStore`. Add validated host-admin methods/CLI actions to list and revoke unused offers separately from paired devices. New code/role changes supersede the previous offer owned by that dialog, while other independently created offers retain their own lifetime. Closing the dialog explicitly cancels its unused offer; a crash still relies on expiry. Make redeem versus cancel/replace atomic across server and CLI writers so one offer cannot both be cancelled and create a device. Never change an issued offer's role in place. Preserve existing TTL, attempt limits and secret hashing; offer IDs, list/status responses and events must not disclose codes or tokens.
4. **Exact completion and recovery.** Correlate host success with redemption of that offer, not the arrival of any new device. Show the actual device name and granted role; refresh through existing authorized status/event paths and handle reconnect without losing correlation. On the receiving device, validate the pairing response, durably save its credential, then perform a normal authenticated capability/status request before showing Connected. Apply this to desktop and mobile; distinguish access granted but host offline/incompatible from a code rejected. Handle timeout after redemption and credential-storage/verification failure without silently creating duplicate devices, discarding a recoverable credential or repeatedly spending the same code. Define safe recovery/re-pair and cleanup for orphaned grants; clear temporary secrets when settled and keep them out of diagnostics.
5. **Address and transport continuity.** Discovery offers candidate routes only. Authenticate continuity before sending an existing bearer credential to a new endpoint, or require explicit pairing when that cannot be proven. Validate redirects and origin changes in both fetch/RPC and streaming transports. Record the transport approval and credential origin; do not reuse an HTTPS/SSH-paired credential over plain HTTP automatically. A changed scheme, certificate or unverified route needs appropriate review/re-pairing, preserving current explicit HTTP consent. Learn additional addresses only through an authenticated host response, and still verify the endpoint's identity before credential reuse. Test permissions per active grant and make route replacement failures leave the working route intact.

Stage offer lifecycle and completion fixes independently, then identity/storage migration, then route learning/failover after transport verification is available. Initial discovery can ship with explicit pairing for each unverified endpoint; do not claim automatic safe address migration until that acceptance passes. Client-key-bound credential evaluation and rotating renewal belong in the [remote security plan](REMOTE-SECURITY-PLAN.md), rather than a second pairing/session system here.

## Verification and acceptance

- Add focused shared tests for malformed/oversized metadata, incompatible versions, duplicate names/identifiers, multiple interfaces, endpoint parsing, expiry, bounded results and stale callbacks. Add adapter integration tests for permission denial, cancellation, listener/advertisement failures and lifecycle cleanup.
- Extend existing desktop/mobile pairing tests for discovery selection, manual/QR fallback, vanished/changed endpoints, duplicate names and failures. On mobile verify discovery opens by default without activating the camera, the order is nearby hosts then QR then manual, both fallbacks stay reachable during browsing and after permission denial, and changing methods stops browsing. On desktop verify opening Connect to a host starts discovery, address/SSH fallbacks stay reachable during browsing and after permission denial, changing methods stops browsing, and no camera permission or QR scanner is introduced. Verify advertisements cannot trigger pairing, privileged requests, stored-token transmission or saved-address replacement. Cover spoofed known-host identifiers and revoked credentials.
- Add server regression tests for offer-specific redemption status, cancellation, supersession/role changes, independent offers, expiry and concurrent CLI/server redeem/cancel writes. Client tests cover unrelated device arrivals, stale offer events, malformed responses, timeout after redemption, secure-storage failure, authenticated verification failure and retry/recovery without duplicate grants.
- Verify legacy host migrations and re-pairing preserve host IDs, drafts, unread state, queues and selection. Cover duplicate identities/names, conflicting cached data, host reset/key change, multiple routes with different grants, revoked route credentials, route removal and failover. Test forged discovery/redirects and HTTPS/SSH-to-HTTP downgrade attempts before any stored credential is transmitted; retain a working route when adding another fails.
- Run tests and types scoped to each touched package. For desktop-facing implementation run `pnpm build`, then the existing `pnpm test:desktop-smoke`; do not add a second desktop end-to-end suite. This documentation-only change needs no build or smoke run.
- On packaged desktop and physical iOS/Android devices, verify first discovery, permission grant/denial/revocation, host restart, sleep/wake, DHCP address changes, IPv4/IPv6, multiple adapters, same-name hosts, foreground/background cleanup and remote-access/discoverability toggles. Verify discovery traffic stays within the chosen interfaces.
- Exercise guest Wi-Fi/client isolation, blocked multicast and VPN networks; pairing by reachable manual address or mobile QR must still work, and existing desktop SSH connections must remain usable. Record supported OS/network combinations, discovery latency and idle traffic before claiming reliable automatic discovery. Confirm no secrets appear in advertisements, diagnostics or logs.
