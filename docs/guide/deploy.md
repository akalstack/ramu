# Deploying an app

Ramu deploys a project to a hosting platform on your own account. It hosts nothing itself: the app, its deployments, its database and their billing stay with the providers, and the repository stays a normal GitHub repository. Vercel and Netlify host apps linked to the repository; Railway, Fly.io, Cloudflare and Supabase are run by an agent through their own CLI, from their [plugins](plugins.md) ([Railway, Fly.io, Cloudflare and Supabase](#railway-flyio-cloudflare-and-supabase)); Neon provides Postgres databases; Expo (EAS) builds phone apps for the App Store and Google Play ([Store releases](#store-releases)).

## Connect an account

**Settings → Deploy** lists Vercel, Netlify, Neon and Expo with their marks, for the host you choose at the top. Other platforms and the services dashboards read come from [plugins](plugins.md). Where the deploy sheet, **Provision** or **Publish to the web** needs a platform that is not connected, **Connect** with its name opens this page on the project's host, at that platform. **Connect** offers two ways, in this order:

1. **Sign in with Vercel** or **Sign in with Netlify**, when the platform's CLI (`vercel` or `netlify`) is installed on the host. Ramu runs the CLI's own browser sign-in on the host and shows its link (and the code, for Vercel) in Settings; **Open the sign-in page**, sign in and authorize. Ramu then reads the token the CLI saved, checks it with the platform and shows the account name. The CLI runs against a private configuration folder that is deleted afterwards, so your own CLI login is not read, changed or signed out.
   - **Sign in with Neon** runs `neon profile create ramu --mint` (the `neon` or `neonctl` CLI on the host, or the published one through `npx`) in a private configuration folder. It opens Neon's sign-in in this computer's browser and shows the link; after you approve, the CLI mints an API key and drops the session, and Ramu keeps only that key. Neon keys do not expire, so revoke it on Neon when Ramu no longer needs it.
   - **Sign in with Expo** runs `eas login --device` (the `eas` CLI on the host, or the published one through `npx`) and shows Expo's link and code, which work from any device. If Expo's page shows a number to pick, type it into **The number the sign-in page shows** and press **Send**. Ramu then turns the Expo session into an access token named Ramu, ends the session and keeps only the token, which you can revoke on expo.dev.
   - Vercel's sign-in is a session that renews itself; Ramu renews it before it expires. A Vercel CLI that signs in with a key bound to the computer cannot be used; use a token instead.
2. **A token**, when there is no CLI or the sign-in fails (a team that blocks CLI logins, single sign-on). **Open the token page** goes to the platform's token page, and a short checklist says what to pick: name it Ramu, the smallest scope (on Vercel, the team your projects are in rather than Full Account), and an expiry where the platform offers one. Paste it into the secret field: it goes straight to the host's credential store, is checked with the platform on the spot, and is never shown again. Settings shows the account, an expiry date, and a note when a Vercel token reaches your whole account.

Without the sign-in, Neon connects with an API key: create a personal key named Ramu on Neon's API keys page and paste it. Neon keys reach your whole account and do not expire, so revoke it on Neon when Ramu no longer needs it.

Without the sign-in, Expo connects with an access token: on Expo's access tokens page, create a robot user with the Developer role on the account that owns the app and create its token (a personal token reaches every account you belong to, and Settings says so). Revoke it on Expo when Ramu no longer needs it.

A token with an end date shows it in Settings, and a week before it runs out each project deploying with it gets a notice in its latest thread naming the date and **Replace**; an expired one says so.

Agents never create tokens by driving your browser: a signed-in dashboard gives full account power, and a new token would end up in screenshots and the transcript.

Hosting accounts are added, replaced and removed on the computer running the host; from a paired owner device, **Sign in with Vercel**, **Netlify** or **Expo** also works, since their sign-in runs on the host, keeps the token there and only shows the device its link. Paired devices see their status: the phone shows each platform's account under **GitHub on this host**, and a project's deployments under **Deployments** ([On the phone](#on-the-phone)). **Disconnect** deletes Ramu's copy only; to revoke the token itself, delete it on the platform.

The same accounts publish artifacts with **Publish to the web** ([Artifacts](artifacts.md)).

## Deploy a project

**Deploy…** in a project's menu opens the deploy sheet, for a project on this computer or on a paired host, which runs it there. When a thread's [goal](goals.md) is met in a project with a repository, the same **Deploy…** sits under it in the thread.

- **Link repository:** pick the platform (the one the project's stack names in `ramu.json` is recommended, see [Configuration](configuration.md)) and, with several, the repository. The repository must be on GitHub; one with no remote yet gets **Publish to GitHub…** in the sheet, which creates the repository (private by default) and pushes it. Ramu links them through the platform's Git integration: every pull request gets a preview deployment, shown on the pull request's card in Source Control and on the phone ([The Pull requests page](git-hosting.md#the-pull-requests-page)), and pushes to the default branch deploy to production, with no deploy token in CI.
  - **Vercel** creates the project (named after the Ramu project) or links an existing one of that name. Vercel's GitHub app must be installed for the repository; the sheet says so when it is not.
  - **Netlify** creates the site and, through the repository's GitHub account in Settings, adds a read-only deploy key and a build webhook to the repository, as Netlify's own CLI does.
- **Once linked**, until the first production deployment is live the sheet says what comes next: push the production branch or merge a pull request into it, the first deployment building, or that it failed (with **Logs**). It then shows the platform, the live address with **Open**, and the latest deployments with their state, branch and commit message. **Logs** shows the end of a deployment's build log.
- **Deploy to production** builds the default branch. It asks once more, naming the address that changes, before anything starts.
- **Roll back** on an earlier production deployment makes it live again, after a confirmation naming the address.
- **Environment variables** lists the variables the app reads (names in `.env.example`, `.env.sample` or `.env.template`, and code that reads `process.env`, `import.meta.env`, `os.environ`, `ENV` or `os.Getenv`) next to where each is set: this host's **Environment variables** ([Providers](providers.md#environment-variables)), GitHub Actions repository secrets (or GitLab CI/CD variables for a GitLab repository, written protected and masked when GitLab can mask them), and the platform's preview and production variables. **Sync** copies each value this host has to the places that lack it; values already set elsewhere are not changed. A variable this host has no value for is named, so you can add it in Settings (or an agent can ask for it with `request_secret` and keep it), then sync again. Values are never shown, only names, on this computer and on paired devices.
- **Domains** lists the project's custom domains. Type a name such as `www.example.com` and press **Add domain**: Ramu asks the platform to add it and shows, in plain words, each DNS record to create ("At your domain provider, add a CNAME record named www pointing to …"), including the ownership record Vercel asks for when the domain is used elsewhere. A domain itself (`example.com`) gets an A record named `@`.
  - When the domain's DNS is hosted by the same platform (Vercel DNS or Netlify DNS, on the connected account), **Create records** makes them after one confirmation naming the change.
  - When the DNS is at Cloudflare, **DNS at Cloudflare? Create them there…** takes a Cloudflare token with **Zone → DNS → Edit**, adds the records unproxied (so the platform can verify them and serve its certificate), replacing an A or CNAME record of the same name, and does not keep the token.
  - Each domain shows **Waiting for DNS**, **Waiting for the HTTPS certificate** or **Live over HTTPS**. Where the platform does not report a step, Ramu checks it from the host: public DNS for the records, then an HTTPS request to the domain once the DNS points at the platform.
  - Ramu checks a newly added domain every minute for up to three days, and when it serves HTTPS it wakes the project's most recent thread with one message, through the same queue as pull request feedback.
- **Checks** says whether the repository has CI and offers **Set up CI** when it has none ([Set up CI](git-hosting.md#set-up-ci)).

## Railway, Fly.io, Cloudflare and Supabase

These platforms are [plugins](plugins.md) by Ramu (**Railway CLI**, **Fly CLI**, **Cloudflare CLI** and **Supabase CLI**), each with its CLI, the token it needs and a short skill on running it in Ramu. Railway, Cloudflare and Supabase also have their own plugin in Claude's directory, whose skills teach the platform in full; installing Ramu's offers it next, and Ramu's skill tells agents to follow those skills while running every command through `platform_cli`. Agents already know their CLIs, so an agent writes the setup (`railway.json`, `fly.toml`, `wrangler.jsonc`, `supabase/config.toml`) and runs the CLI through `platform_cli`, while Ramu keeps what an agent cannot do for itself:

- **Your account, never the agent's:** install the plugin and paste its token on its card in **Customize → Plugins**. `platform_cli` runs the CLI in the thread's checkout with the token in its environment (`RAILWAY_API_TOKEN`, `FLY_API_TOKEN`, `CLOUDFLARE_API_TOKEN` with an optional account id, `SUPABASE_ACCESS_TOKEN`), never in its arguments, and replaces the token with `[token]` in anything the CLI prints. The CLI gets a home folder of Ramu's own, so your own CLI login is not read or changed.
- **Asking before a change:** commands that only read (such as `status`, `logs --no-tail`, `list`, `whoami` and `--help`) run straight away; every other command shows a card naming it, and a refusal is final for that request. `railway variables` asks too, since it prints values.
- **The CLI:** the installed `railway`, `fly` (or `flyctl`), `wrangler` or `supabase` on the host, or for Railway, Cloudflare and Supabase their published CLI through `npx` when none is installed. Fly.io needs `flyctl` installed.

When the project's stack recommends one of them (the Node API, Django and FastAPI stacks name Railway; Rails and Go name Fly.io), the deploy sheet says so and opens **Customize → Plugins** to install its plugin; an agent can also offer the install with `plugin_install`. Linking, the deployment list, rollbacks, uptime, usage and secrets sync in the sheet are for Vercel and Netlify; on these platforms, ask the agent.

## On this computer

For demos and home use, **Run on this computer** in the Deploy sheet publishes the selected repository's app from this computer, with no account or server. Ramu builds it into a Docker container (with the repository's Dockerfile, or one it writes for the stack and passes to the build without adding it to the repository), runs it with only its port published to this computer's loopback address, and gives it a public address of its own through a separate tunnel of the kind chosen for artifacts opened to anyone (Cloudflare or ngrok without a fixed domain). The address reaches only the app, never Ramu, and changes when Ramu restarts. The app is offline while the computer sleeps or Ramu is not running; an app left published starts again with Ramu. **Stop** takes the address down first, then the container. Of this host's saved Environment variables, the app gets only the ones its code reads. Docker must be installed and running.

Without Docker, **Run without Docker…** says first what it means, then runs a Node app with a `start` script as a program here: it installs dependencies when there is no `node_modules`, runs the `build` script if there is one, and starts the app with `PORT` and `HOST` set to a loopback port, which the tunnel names once the app answers there. The program gets the project's variables and none of Ramu's environment, but it has your own permissions, so use it only for code you trust. **Stop** ends its whole process group, and a program that exits takes its address down and shows the end of its output.

**Give it a lasting address…** keeps one hostname across restarts instead of a new quick-tunnel address each time. Enter a hostname on a domain in your Cloudflare account and a Cloudflare token with **Account → Cloudflare Tunnel → Edit** and **Zone → DNS → Edit**. Ramu creates a Cloudflare Tunnel whose only route is that hostname to one fixed port on this computer (anything else gets 404), adds its DNS record, and runs `cloudflared` with the tunnel's own token whenever the app is published. It cannot reach Ramu's own port, and a wildcard hostname is refused. **Remove** deletes the record and the tunnel.

## When a deployment finishes

Ramu follows a deployment until the platform finishes it, then wakes one thread with one message, through the same queue as pull request feedback:

- **What starts it:** a deploy from Ramu (**Deploy to production**, `deploy_production` or `deploy_preview`); a push of the production branch from a thread (**Push** or **Sync**, or a `git push` the agent runs in its own shell) to the repository the platform watches; **Merge…** of a pull request into that branch; and a push of any other branch from a thread, when the platform builds a preview of it. For a push, Ramu finds the platform's production deployment of the pushed commit; for a merge, the first production deployment that starts after it.
- **Which thread:** the one that deployed, pushed or is linked to the merged pull request, or the project's most recent thread when there is none or it was closed since.
- **Deploys started elsewhere:** every ten minutes Ramu also looks at each linked project's latest deployments, and a production deployment that failed without Ramu following it (a push from another computer, a merge on the website) wakes the project's most recent thread once with the end of its log. A deployment that succeeds is not told.
- **What it says:** the live address when the deployment is ready (for another branch, its preview address, which the agent passes on); when it fails, the deployment and the end of its build log, with anything that looks like a secret replaced by `[redacted]`, so the agent can find the cause and propose a fix. A failed production deployment leaves the previous one live.
- **Migrations:** a push or merge that the platform deploys on its own runs no migration from Ramu. When `ramu.json` names a `migrate` command, the message says so, and the agent offers **Deploy to production** (through `deploy_production`, which runs the migrations first) if the change adds one.
- A push the platform has not started deploying within 20 minutes, or a deployment still building after two hours, is no longer followed. A push replaced by a newer one is followed through the newer push.

Pushes made outside Ramu, such as from a terminal or GitHub's website, are not followed. For those, a **Deployment failed** [webhook schedule](background-work.md#when-a-request-arrives) for Vercel or Netlify starts a thread instead.

## Store releases

For an Expo app (an `app.json` or `app.config.*` at the repository root, as the Expo stack creates), the deploy sheet shows **Store releases**. A project whose stack names Expo, or with no stack in `ramu.json` and an app that depends on `expo`, shows only this, not the hosting platforms. **Connect Expo** opens Settings → Deploy at Expo when the host has no Expo account yet.

- **What the stores need**, checked from `app.json` and `eas.json`: an `eas.json` with a `production` build profile, the EAS project the app is linked to (`extra.eas.projectId`, which an agent sets with `eas init`), the iOS bundle identifier and Android package, the icon file, the version, build numbers that EAS raises on every build (`autoIncrement` or `appVersionSource: "remote"`; numbers set by hand are a warning), the App Store Connect app (`submit.production.ios.ascAppId`), Android submissions to the internal track only, and the iOS permission texts the app's Expo libraries need (such as `NSCameraUsageDescription` for `expo-camera`), set in `ios.infoPlist` or in the library's plugin options. An app that computes its configuration in `app.config.*` is checked from `app.json` until you press **Read it by running expo config**, which runs the project's own `expo config` on this computer (so its code runs, only then) and checks the configuration it prints, until that file changes.
- **Add eas.json in a pull request** opens a pull request with an `eas.json` whose `production` build profile raises build numbers and whose `production` submit profile sends Android to the internal track, made in a temporary worktree as [Set up CI](git-hosting.md#set-up-ci) does.
- **What only you can do on the stores** lists the steps Ramu cannot take: enrolling in the Apple Developer Program, creating the app in App Store Connect and in Google Play Console, the first iOS build in a terminal so EAS can create the signing credentials with your Apple sign-in, the first Android upload to Play Console by hand, a Google service account key for submissions, and inviting testers, the store listings and submitting for review.
- **Release** builds iOS and Android, or one of them, on EAS from the default branch, then uploads the iOS build to TestFlight and the Android build to Play's internal testing track. It asks once more before anything starts, and is refused while a check that matters for the chosen platforms is missing or the project's checkout is on another branch. Ramu runs `eas build --non-interactive --no-wait --json` with the `production` build and submit profiles (the `eas` CLI on the host, or the published one through `npx`), since EAS starts builds only through its CLI; the token is passed in its environment.
- **Pull request previews:** once the app has `expo-updates`, a `runtimeVersion` and `updates.url` (the sheet lists what is missing; `eas update:configure` writes the last two) and is linked to an EAS project, **Add previews in a pull request** keeps the connected Expo token in the repository's Actions secrets (`EXPO_TOKEN`) and opens a pull request with `.github/workflows/eas-preview.yml`. After it merges, each pull request from the repository itself is published to its own EAS Update branch, `pr-<number>`, and Expo's preview action comments a QR code on it that opens the update on a phone: in Expo Go, or in a development build when the app uses `expo-dev-client` (the sheet says which). Pull requests from forks get no secrets and no preview, and a change to native code still needs a new build.
- **Nothing is submitted for review.** Submitting a TestFlight build to App Review or promoting a Play release to production is your step on each store.
- The latest store builds list each build's platform, state, version and build number, the upload's state, **Open** on expo.dev, **Logs** and **Upload log**.
- **When a build finishes:** Ramu follows each build and its upload, for up to eight hours, and wakes the project's most recent thread (or the thread that started the release) once: when the upload is done, or with the end of the build's or upload's log when either fails, redacted as for deployments.

## On the phone

**Deployments** in a project's menu on the phone shows the platform and repository, the live address with **Open**, the latest deployments with their state, branch, time and **Open**, the project's custom domains with where each is (**Open** once live over HTTPS), its databases with the variables they set and **Open** for their page, the [uptime](#uptime) watch with any open incident and its switch, and [usage](#usage) with **Open billing**. **Roll back** on an earlier production deployment asks first, naming the version and the address that changes, as in the deploy sheet. For an Expo app it also lists the latest store builds with their upload to TestFlight or Play, and **Release** asks which stores and then confirms, as the deploy sheet does; what the stores need is set up on a computer. **Logs** under a deployment shows the end of its build log, and **Deploy to production** (on platforms that deploy from Ramu) says which branch it builds and which address changes before it starts, as in the deploy sheet. Linking, adding domains and provisioning databases are on a computer. Viewer pairings do not see deployments.

## Usage

**Usage this billing period** in the deploy sheet shows what the project's platforms report through their APIs, next to the plan's limit when the API reports one. **Open billing** opens the platform's billing page. Ramu never changes a plan or adds a payment method, and neither can an agent.

| Platform | Figures | Limit |
| --- | --- | --- |
| Vercel | Each service's usage this calendar month (such as data transfer and function invocations), summed from Vercel's billing charges, for the account or team the project is linked under | Not reported by Vercel's API; **Open billing** shows it |
| Netlify | The team's build minutes for the billing period | The minutes included in the plan, with any add-on packs |
| Expo | When the project has an Expo app on EAS, its owner account's build credits and update users (monthly users who downloaded an update) in the billing period | The plan's included credits and update users, as Expo reports them |
| Neon | The main branch's size, compute time and data transfer for the billing period (Neon's own counters, which lag a little) | Storage against Neon's branch size limit; compute against the plan's compute time; transfer has none |

When the API reports no figures for an account or plan (Vercel refuses billing data to some roles; Netlify plans billed in credits have no build minutes), the sheet says so instead of showing numbers.

Every six hours the host reads the same figures. A figure with a reported limit that reaches 80%, and again at 100%, raises one notice per billing period in the notifications (on the phone, under **Missed**), naming what grows and the cheapest fix, such as building only when the app's files change, deleting data and branches the app no longer needs, or shipping JavaScript changes as EAS updates instead of new Expo builds. The notice opens the project's most recent thread, where an agent can read the figures with `deploy_usage` and propose a fix as a pull request.

## Uptime

Once a project has a live production deployment (or its app runs on this computer at a [lasting address](#on-this-computer)), **Watch the live address** in the deploy sheet is on. Untick it there, or turn off the switch beside **Uptime** in the project's **Deployments** on the phone, to stop the checks.

- **What is checked:** every five minutes, the host sends one `GET` to the production address and the project's health path (`"healthPath"` in the stack of `ramu.json`, such as `"/api/health"`; `/` by default). An answer within 10 seconds that is a success, a redirect, or a sign-in or rate-limit page counts as up. Redirects are followed on the same host name only; a redirect to another host is an answer and is not followed. The sheet shows the last check with its status code and response time.
- **Incidents:** two failed checks in a row open a thread in the project titled **Down: …**, with the status code or the reason there was no answer, the response time, the last production deployment and the end of its build log, and notify your phones (the phone's **Failed** notifications). The thread uses the model of the project's most recent thread, with at most Auto access. Its agent reads the logs first and, when the last deploy is the likely cause, offers **Roll back** through `deploy_rollback`, whose card always asks you. A project has at most one open incident.
- **Recovery:** the first good check after an incident posts into the same thread, which answers with a short recap of what failed and what was done. The incident is then closed.
- **When the host cannot tell:** checks run only while this computer is awake and Ramu is running. A gap of more than eleven minutes between checks is shown as **Unknown** with its start and end, not as downtime, and failed checks before and after it are not counted together. A check with no answer while the hosting platform's API cannot be reached either means this computer is offline, and is counted as unknown too.

Turning the watch off forgets its checks and closes an open incident without a recap.

## Databases

The deploy sheet shows **Database** when the project needs one: its stack stores data (`"database": true` in `ramu.json`, set for the Next.js, Django and Rails stacks), or its code reads `DATABASE_URL`.

- **Provision** creates a Postgres project named after the Ramu project on your connected Neon account, and a `preview` branch of it (a copy that shares storage until it changes). Production uses the main branch; preview deployments, this host and GitHub Actions use the `preview` branch, so they never change production data.
- **Netlify Database:** for a project deployed to Netlify, the sheet notes that adding `@netlify/database` (which `netlify database init` does) is enough: Netlify creates the database on the next deploy, gives each deploy preview its own branch and applies the migrations in `netlify/database/migrations/`. Ramu provisions nothing for it.
- Ramu keeps both branches' connection values in the host's credential store and sets the preview branch's `DATABASE_URL` (pooled, for the app) and `DATABASE_URL_UNPOOLED` (direct, for migrations) in this host's Environment variables. **Sync** in **Environment variables** then copies them on: the main branch's values to the platform's production variables, the preview branch's to its preview variables and GitHub Actions. The sheet shows names only.
- **A branch per pull request:** on Vercel and Netlify, each open pull request (up to four at a time) gets a Neon branch of its own (Neon only), copied from production, named `pr-` and its git branch. Its `DATABASE_URL` and `DATABASE_URL_UNPOOLED` are set on the platform for that git branch only, and its preview is deployed once more to use them. When the pull request closes or merges, Ramu removes those variables and deletes that branch. Pull requests past four, and platforms without per-branch variables, use the shared `preview` branch.
- Once provisioned, the sheet shows the database, and **Open** for its page on the provider; Neon's size and compute time are under [Usage](#usage). Resizing and deleting it are done on the provider's page; neither the sheet nor an agent deletes a database.
- **Migrations:** when `ramu.json` names a `migrate` command (the Django and Rails stacks fill it in), **Deploy to production** and `deploy_production` first run it on this host against the production database, in the repository's checkout of the production branch. The checkout must be on that branch at the commit pushed to GitHub, so the migrations match what deploys. A failed migration stops the deploy: the sheet shows its output, and the project's most recent thread is woken with it to find a fix. Pushes to the default branch that the platform deploys on its own do not run migrations from Ramu; the thread woken when that deployment finishes is told so.
- **Run the migrations before each production build goes live** (Vercel and Netlify, in the deploy sheet) covers those pushes too. The platform then holds every finished production build instead of making it live (Vercel stops assigning the production domains on its own; Netlify locks auto publishing). When the deploy watch sees a held build finish, Ramu runs the `migrate` command on this host against production, with the checkout at that build's commit, and only then makes the build live. A failed migration leaves the previous build live and wakes the thread with its output. This computer must be awake for production deploys, and each migration must suit the version still running (add a column before the code uses it), so the hold is off until you turn it on; linking another site turns it off.

The project stays linked to the account that linked it. If you connect a different account later, deploy actions are refused until you connect that account again or link the project again.

## Agents

Threads in a project get deploy tools for that project, on its linked platform and account:

- `deploy_status`: the target, live address, what the platform can do, and the latest deployments.
- `deploy_logs`: the end of a deployment's build log.
- `deploy_preview`: a preview deployment of the thread's current branch (Vercel; Netlify builds previews from pull requests). Outside Full access it asks first. The thread is woken when it finishes, as after `deploy_production` ([When a deployment finishes](#when-a-deployment-finishes)).
- `deploy_domains`: the project's domains, the records each needs and whether it is live.
- `deploy_usage`: what the platform and database report for the billing period, beside the plan's limits, and the billing page. Read-only.
- `deploy_domain_add` and `deploy_domain_records`: add a domain, or create its records in the platform's DNS. They always ask you with a card naming the domain and each record, in every access mode, and the thread is woken when the domain is live.
- `deploy_production` and `deploy_rollback`: always ask you with an approval card naming the address and what changes, in every access mode. A refusal is final for that request.
- `platform_cli`: runs an installed plugin's CLI, such as Railway's, Fly.io's, Cloudflare's or Supabase's, with the token saved for it, in any thread ([Railway, Fly.io, Cloudflare and Supabase](#railway-flyio-cloudflare-and-supabase)). Commands that only read run straight away; every other command asks you with a card naming it.
- `release_status` and `release_logs`, for a project with an Expo app: what the stores need, the steps only you can do, the latest store builds, and the end of a build's or upload's log. Read-only.
- `release_start`: builds the app on EAS and uploads it to TestFlight and Play's internal track. It always asks you with a card naming the app, its version, the platforms and the Expo account, in every access mode, and the thread is woken when each build and upload finish. Agents never submit an app for review.

`deploy_production` runs the project's migrations first, and a failed migration returns its output to the agent instead of deploying. Agents cannot create or delete databases.

A deploy whose reply never arrives is not retried: Ramu reads the deployment list again and reports the deployment it finds, so a retry never deploys twice.
