# Plan: shared theme components, light/dark and custom themes

Status: phase 1 is working on desktop (19 October 2026): Settings → Appearance → Theme offers Match device / Light / Dark, stored per device in `deviceStorage` (default Dark, so upgrades keep their look), with a light palette in `styles.css` (overlay tokens derive from `--ink`), Monaco/Shiki and terminal light variants, deeper light accents, and native `nativeTheme` and window color. The home screen, settings, palette, model picker, a thread with tool rows, Source Control, the diff view, the terminal and the markdown editor were reviewed in light in the built app. Mobile already had System/Light/Dark. Also in place: the shared token schema, validator, canonical digest and contrast checks (`packages/shared/src/theme.ts`, kept in step with `styles.css` by a test), a local library of kept themes, and Settings → Appearance → Customize colors, a manual editor for every role in both appearances with per-role reset, Undo/Redo, a live trial of the draft in the app and a fixed-color Keep/Revert bar (Keep is refused while a readability check fails). Custom themes recolor the app chrome, terminal and Monaco editor surfaces (token colors stay GitHub's). Themes export to `<id>.ramu-theme.json` (digest included) or copy as JSON, and import from a file into the same trial/Keep flow; an edited file is flagged, a changed copy of an installed id becomes its own theme. `test/themeLiterals.test.ts` fails on new color literals in components, with a short documented exception list. The trial lasts while the editor is open and is never persisted, so closing it or restarting restores the previous theme. Settings, the Source Control panel, the commit toast and the Schedules page were reviewed in light, pasted-JSON import works, and interactive documents now follow appearance changes. The quiet button states are one shared module (`components/button-classes.ts`). AI creation and refinement now work from the editor (phase 3): `theme.generate` drafts a theme from a brief on the host's default model (the same one maintenance uses), with the current draft as the seed, a bounded repair loop fed the validator's failures, and colors you set by hand locked until released; the result lands in the same trial, Undo and Keep/Revert flow, and a draft that still fails stays unkeepable with its failures shown. A creation recipe copies as short Markdown. After a draft, Another direction (up to three per wish) tries a different palette and Undo steps back between them; the validator also refuses status colors (success, warning, error) that look alike. The editor shows a preview of the selected appearance (sidebar, messages, status chips, actions, code), drawn from the draft's own tokens, even when the app is in the other appearance. The preview also shows advisor, goal, question and limit-notice cards, and Compare 3 asks the host for three differently-directed drafts shown as small swatch cards to pick from (each costs a draft's usage). Still open: reference images (the one-shot analysis path takes text only), creating a theme from a normal thread (needs an agent tool and a Preview theme result), the remaining shared-control audit (phase 0; the primary and destructive actions and the quiet buttons are shared classes in `components/button-classes.ts`; the commit split button and full-width Sync now share the primary action states, and Stash/Git heading use shared variants, with superseded button rules removed from both stylesheets; still to audit: other specialized controls in `styles.css` and feature wrappers), and preview built from more production components (the preview already uses the real Button; the sidebar rows, messages and cards are still token-styled stand-ins) (phase 5). Complements [Thread activity](THREAD-ACTIVITY-PLAN.md) and [Interactive content](INTERACTIVE-CONTENT.md).

## Smallest usable delivery

A person can choose System, Light or Dark and comfortably read a thread, code changes and approval controls without a model call or token knowledge. Deliver this foundation before the custom-theme editor, AI refinement and sharing. Keep the initial Appearance view focused on the current appearance/theme; reveal exact tokens and revision details in advanced controls. Validate readability and Keep/Revert with real app components during an ordinary agent task, alongside the accessibility checks below. Follow the [root product and planning guidance](../AGENTS.md#product-design-and-architecture) for this and later increments.

## Product decision

Keep **System / Light / Dark** as immediate, deterministic appearance choices. Offer both **Create/refine with AI** and an **Advanced color/token editor**, following the user's updated request. Users can select, edit, import, share, reset and remove themes without an AI call. AI and manual editing use the same draft, token schema, validation, preview and version history; neither maintains a separate kind of theme.

The first experience is Ramu Default in both appearances, plus **Create with AI**, **Customize colors**, **My themes** and **Import theme** in Settings → Appearance. Do not require users to know color names or decide every detail: they can start with “make this calmer and easier to read,” choose between a small number of AI proposals, or keep the current look and ask for one improvement. Advanced users can edit exact values. Every theme remains recognizably Ramu through its layout, component behavior and platform materials.

## User flow

1. **Choose appearance.** System follows the device; Light and Dark override it. No model, network or host connection required. On first migration preserve the existing visible appearance rather than unexpectedly changing a dark desktop to light. New profiles can follow System.
2. **Describe a theme.** Settings → Appearance → Create with AI opens a focused theme conversation. Supply a prompt or use a suggestion such as “soft graphite with muted lavender,” “warm paper, less glare,” or “more contrast while keeping this palette.” Optional reference images use the normal attachment path and are sent only when the user includes them.
3. **Preview real components.** Show a small number of named candidates in a common preview: sidebar/thread, composer, agent card, advisor, goal, Q&A/approval, menu, code/diff, terminal and interactive chart. Toggle both appearances and mobile/desktop preview widths. Preview components are Ramu-owned and use the same renderer/tokens as the app, not AI-authored imitations that can claim to be readable without matching reality.
4. **Refine with natural language or exact colors.** “The text is too faint,” “keep the backgrounds but soften the violet,” or “the light version needs warmer surfaces.” Pass the current candidate, original brief, latest feedback and specific validation failures to the AI. Prefer changing only relevant roles; allow **Keep this part** / **Undo refinement**, and let the user switch to the manual editor without losing the draft. Locked manually edited roles remain locked during AI refinement unless the user releases them. If a user is unsure, explain the visible difference in one sentence and offer another direction without an endless generation loop.
5. **Try it temporarily.** A native preview session can apply the candidate to the current device/window set, with an always-visible **Keep theme / Revert** bar outside generated content. A bounded trial automatically reverts if not kept. Preview generation never applies itself. Preserve a known-good theme and a native reset path that works without AI, connectivity or readable custom colors. Do not change the other device or paired hosts during a trial.
6. **Keep and name.** Save an immutable theme revision and select it locally. Keep a small local history so the user can return to an earlier revision. A failed generation, cancel, app restart during a trial or missing provider keeps/restores the previous saved theme. No automatic retry that repeatedly spends model usage.
7. **Share or remix.** Export the exact saved theme or copy its JSON; optionally include an edited creation recipe. Recipients preview before installing/applying. **Remix with AI** forks the imported theme under a new identity, preserves optional attribution, and leaves the original intact.

Users can also ask in a normal thread to make a theme. The AI produces a draft theme result with **Preview theme**; the same native validation/preview/apply flow handles it. It cannot silently alter appearance through a general agent tool. Make it clear that theme generation uses the selected host/provider and may consume that provider's usage; theme selection and sharing remain free of AI calls.

### Manual color and token editor

**Customize colors** opens an advanced native/Ramu-owned editor with a Light/Dark variant switch, searchable semantic roles and the same real-component preview. Group tokens by Surfaces, Text, Actions, Inputs/Focus, Status, Code/Diff, Terminal and Charts. Show a readable role label and optional technical token name so users can understand what a value changes. Clicking an element in the dedicated preview can select its role in the editor; never install an inspector into arbitrary app content or user-generated HTML.

Each editable color has a swatch, color picker and exact hex input; alpha editing appears only for roles whose schema permits it. Include Reset role, Reset group and Undo/Redo. Keep an unfinished hex entry local to the field without applying an invalid value to the preview. Committing a valid field updates the draft preview immediately, not the installed theme. Preset/default editing starts a local fork rather than modifying the built-in definition.

Show the affected component states next to changes: default, hover/pressed, selected, disabled, focus, loading and destructive where applicable. Keep light and dark values independent unless the user explicitly asks AI to make a matching variant; a manual edit to one appearance must not silently rewrite the other. Derived tokens show their source and resolved value; offer an explicit override only where supported, and resetting that override restores derivation.

Manual edits run the same readability and semantic-state checks as AI output/imports. Explain a failing foreground/background pair with a link to the relevant role. Users can retain incomplete/invalid drafts locally, but applying/exporting a finished theme requires passing mandatory checks; optional recommendations remain distinguishable. An AI-assisted **Fix readability** action proposes a patch and respects locked tokens. It never discards exact user choices without review. Both editing modes work through the same temporary trial/Keep/Revert flow and produce the same `.ramu-theme.json` format.

## What can change, and what stays stable

The initial custom theme controls colors: neutral surface hierarchy, text levels, borders, accent/action/focus states, selection, semantic statuses, chart series, editor/syntax/diff and terminal palette roles. Both light and dark variants must be complete, resolved and validated before the pair is shared as a finished theme. A draft missing a variant remains a draft; do not claim an inverted palette is an intentionally designed second variant.

Preserve Ramu's geometry, navigation, icon meaning, touch targets, spacing and interaction behavior. Initial themes cannot replace components, inject CSS/HTML/JavaScript, load fonts/wallpapers from URLs, remove focus indicators, hide controls or rename statuses. Existing font-size, reduced-motion and accessibility choices stay device preferences outside theme exports. Reconcile the current accent dropdown with theme ownership: custom themes derive their accent from the saved palette; changing that accent edits the same theme draft through the manual editor or AI refinement. Avoid two competing sources silently overriding one another.

Ramu Default remains the graphite/violet baseline plus a deliberately designed light variant. Custom themes can use other accent colors while keeping the hierarchy and structure. iOS glass, Android Material and native permission dialogs remain system-owned; adapt their supported color/appearance inputs, but do not promise identical pixels on every OS. Keep the shell's status/bar text legible. Terminal and editor mapping must include selection, ANSI/syntax and inserted/deleted states, not just the background.

## Sharing: exact file plus optional recipe

Recommend **`<name>.ramu-theme.json`**, a readable versioned JSON document. The compound extension identifies it as a Ramu theme while retaining standard JSON tools. A plugin/custom executable extension is unnecessary. Add OS file association only after normal import works; desktop file-open and mobile document/share-sheet import must share one validator. File association imports into a preview, never directly activates it.

The theme file contains a schema version, stable theme ID, revision ID, display name, optional author/license/attribution, complete light/dark semantic token values, supported theme API version and a digest of the canonical theme data. It contains no provider credentials, host names, filesystem paths, conversation IDs, telemetry, model settings, device preferences or remote asset URLs. The digest detects content changes; it does not authenticate the author. Escape all display metadata and treat imported strings as data.

Two share actions serve different needs:

- **Share exact theme**: download/share the `.ramu-theme.json` or copy the same JSON text. Reproduces the saved token values without AI. It opens/imports offline and includes both appearances. Optional platform preview images can accompany it, but are not required by the format.
- **Copy creation recipe**: a short, editable Markdown prompt describing the style, constraints, desired light/dark pair and optional source-theme digest. It helps another person ask their AI for a variation; it does not promise an identical result. Never export the entire theme conversation by default. Including the recipe in the file is opt-in after a visible preview; remove private details from the suggested recipe.

Import accepts the dedicated file and pasted JSON in bounded size. Validate schema/token values, readable semantic combinations and supported versions. The schema accepts explicit color values only, not arbitrary CSS expressions, references or network resources. Unsupported future schema versions produce an explanation; unknown optional metadata may be ignored, but unknown executable-like fields are never interpreted. Use only the file's declared data, never instructions hidden in a prompt. A recipe only reaches a model when the recipient explicitly chooses Remix with AI.

If an imported theme matches an installed ID/digest, reuse it. A changed revision of that ID is offered as another version; it never silently overwrites the active theme or an author's identity. Names do not confer trust. Keep attribution editable only in the recipient's own fork. No public theme marketplace, account service or hosted share links are required initially. File/text sharing works with ordinary messaging tools and native share sheets; sending to another person remains the user's action.

An optional later **Send to my device** action can transfer a theme to an explicitly selected paired device through existing authorized transport. It still requires that recipient to choose Preview/Apply. Do not add sync-everywhere semantics to host pairing.

## Architecture

### Shared components before broad theme rollout

Refactor controls that currently carry their own visual design into a small shared component system. Changing one theme role should update every equivalent control, including less frequently used dialogs, toolbars and transcript actions. This is a prerequisite for declaring custom themes consistent; tokenizing a stylesheet while feature components override it is incomplete.

Ramu already has useful primitives: desktop `components/ui/button.tsx` supplies the Base UI/CVA primitive and `components/desktop-button.tsx` supplies app density/settings behavior; mobile `components/ui.tsx` exposes `Button`, `IconButton` and `Toggle`; menus, input and toggle primitives also exist. Extend and consolidate the app-composed desktop wrappers and existing mobile controls. Treat every desktop `components/ui/` registry primitive as upstream-owned: do not edit it, copy it or add Ramu variants there. Keep variants and interaction states in reusable app components outside that directory, and map theme tokens through the existing app styles. Do not add a third button implementation, force React Native to render web DOM, or replace a functioning native control with a generic custom one.

Audit both platforms and keep a migration inventory: raw buttons/Pressables, shared buttons with color/background/border/radius overrides, duplicated class constants, hardcoded hex/RGB/white/black and dark-only alpha fills, `!important`/specificity patches, custom links/chips/toggles and CSS selectors targeting component internals. Classify each occurrence as migrate, intentional specialized control, generated/user content, or non-theme artwork; record a reason/owner for exceptions. A raw Pressable may be a valid gesture target rather than a button, so review semantics rather than blindly replace tags.

Observed starting examples include desktop `views/agent/components/AgentTaskCard.tsx`, which uses shared Button but layers local background/hover/border styles; the reusable text/ghost action class strings in `views/agent/styles.ts`; dark-specific literals in that same transcript styling; and the hardcoded accent swatches in `settings/AppearanceSettings.tsx`. Mobile Composer/Transcript use many specialized Pressables alongside the shared controls. These are audit inputs, not a claim that every occurrence is incorrect or can use the exact same variant.

Define semantic variants and states centrally, with names aligned across platforms where the meaning is shared:

- **Button:** primary, secondary, quiet/ghost, destructive and link; **IconButton** shares those semantics with required accessible labels. Preserve a dedicated tree/navigation or disclosure wrapper when its selection/expansion behavior requires it.
- **Button states:** normal, hover where supported, pressed, focus-visible, selected/expanded, loading and disabled. Foreground/background/border/focus tokens cover each state, including semantic status actions. Loading must preserve width and provide accessible status rather than silently changing labels.
- **Related controls:** text input/textarea, switch/checkbox, segmented control, chip/badge, menu item and card/surface primitives. Unify repeated visual/state behavior through these components; do not put every app layout into a universal Card or Button.

Use two layers of tokens: shared semantic roles (accent, raised surface, text, warning, focus) and deterministic component aliases (button-primary foreground/background/pressed, input border/focus, chip-selected surface/text). Component aliases resolve from the theme and may be overridden only through the validated theme schema, not arbitrary CSS strings. Keep platform-specific density, touch targets, native materials and interaction feedback. Desktop hover and mobile pressed states share intent without requiring identical implementations.

Feature call sites select variant, size, state, icon/content and arrangement. Allow explicit layout composition (margin, alignment, width) without permitting routine feature-local overrides of component colors, borders, shadows, typography or state selectors. Repeated exceptions become named supported variants/wrappers; avoid a prop for every historical one-off. Preserve disabled propagation from Settings, ref forwarding, menu-trigger composition, form submit behavior, keyboard focus, tooltip anchoring, hit slop and native accessibility during migration. Links remain links; custom gesture surfaces keep their real interaction model.

Stage changes by component family and product surface, starting with buttons/icon buttons and settings, then thread/composer/agents/advisor/goals/Q&A, then menus/forms/SCM/terminal chrome and remaining dialogs. Use a component-state preview built from production components in both appearances and at least one non-default palette. Verify before/after behavior for compound controls rather than mechanically deleting every class. Remove superseded utility constants/selectors after their callers migrate, leaving one authoritative state style. Do not merge this into a single mass rewrite across unrelated files in the shared working tree.

Add a narrowly scoped lint/style rule or repository check for migrated component paths: forbid newly introduced raw color literals and visual overrides on shared controls outside token definitions, approved specialized wrappers, theme swatches/data visualizations and explicit documented exceptions. Establish the rule on migrated scopes first, then expand as the backlog shrinks; avoid an unreviewable baseline of blanket ignores. Keep a migration ledger, and do not mark a surface theme-ready while it retains undocumented conflicting overrides.

### Shared token engine

Add a versioned theme schema, canonicalizer, complete Default variants, semantic role resolver, theme-import parser, contrast/state validation and platform mappings in `packages/shared` (proposed `theme/` folder). Convert existing desktop CSS variables, mobile palette, editor theme and terminal/chart colors to consume resolved semantic tokens. Existing Ramu components remain in charge of layout and behavior. Accept only bounded explicit color values; derive overlays and platform-specific fills in deterministic code.

Separate `appearance` (system/light/dark), `themeId`/`revisionId` and theme documents. Theme selection is device-wide. Desktop applies it before renderer paint through a validated device theme store/boot snapshot, then fans changes to current host windows. Keep small selection metadata in `deviceStorage`; store versioned theme documents in a dedicated local theme repository rather than stuffing an unlimited library into the key-value state file. Mobile keeps its own local theme repository and startup-resolved palette. A plain web client uses the corresponding local fallback. Neither waits for a remote host to render its theme.

Migration preserves old font/size/accessibility choices, existing selected accents and mobile appearance; derive a local legacy preference variant where necessary rather than discard a user's accent. Default, invalid/missing revision and unknown theme API cases have deterministic fallbacks. Failed writes never leave half-written documents or an active pointer to missing data. Keep startup/splash and native navigation in sync to avoid bright flashes.

### AI workflow

Use existing host/provider invocation through a narrowly scoped theme-generation service with a structured output schema. Follow [Architecture](ARCHITECTURE.md): extend the named shared API and validated server handlers through the existing registry/dispatcher and provider adapters; use host-qualified requests/events. Theme documents and application remain device-owned through existing native/device APIs, with no server import of Electron or new theme HTTP transport. Do not spawn a shell agent to edit CSS in the user's checkout. Inputs are the token schema, Ramu design constraints, seed candidate, user-supplied brief/reference and current feedback. Do not send unrelated threads, projects, goals, advisor output or host configuration. The service inherits provider authentication and cancellation/usage-limit handling; presentation remains on the requesting device. Limited/offline providers leave drafts intact and explain how to retry.

Validate every result deterministically. Check foreground/background and text/action/focus/status pairs on their actual component surfaces, including alpha compositing; catch indistinguishable critical states and chart series. Automated contrast tests are a minimum, not evidence that a user likes a theme. Invalid candidates return targeted repair feedback to the model within a bounded retry budget; failing repair keeps the previous theme and reports what could not be made readable. Never silently mutate the exported token values during import and then call them an exact copy.

Store drafts separately from applied themes. A theme result references its immutable document/digest. Native Preview/Keep/Revert actions own the application of that result, so an agent or interactive document cannot call a generic apply-theme bridge. A temporary preview session includes the initiating device, revision, prior theme, expiry and a generation ID; a stale generation cannot replace the latest candidate. Use existing provider/session infrastructure without expanding restricted review/advisor permissions.

### Interactive content and other surfaces

The [interactive-content theme API](INTERACTIVE-CONTENT.md#document-contract) consumes the same resolved tokens. Update active documents through a typed theme message without resetting their local controls. Theme previews are native components, not evidence supplied by untrusted interactive HTML. Allow an artifact to declare its own illustrative palette when its subject requires it, but keep its native frame/actions in the app theme and label authored interface concepts clearly.

Agent cards, advisor, goal, Q&A, provider-limit notices, permissions, menus and queue states all belong in the preview coverage. An accent choice cannot make errors resemble success or waiting resemble completion. Native fallback/restore controls retain guaranteed readable styling independent of custom tokens. Reduced motion and system accessibility always take precedence over a theme.

The basic token engine can precede interactive-content implementation. Its integration is additive later. Defer galleries/marketplaces, hosted links, cross-device automatic sync, external theme formats, custom CSS/layout/font/wallpaper packs and third-party executable theme plugins. Record these as deferred, not partially supported file formats.

## Validation

Unit tests cover schema/size/value limits, duplicate/reserved IDs, light/dark completeness, canonical serialization/digest round-trips, migrations, supported-version fallback, token mappings and actual surface contrast validation, semantic status distinctions, stale preview results and bounded repair attempts. Also cover manual field validation, independent light/dark edits, derived-role reset, Undo/Redo and preserving locked roles in AI patches. Imported prompt text must stay inert. Unknown/malformed themes cannot alter unrelated preferences.

Integration tests cover the structured generation boundary with simulated providers, cancellation/limits/offline drafts, atomic install/select/rollback, desktop multi-window device state, mobile persistence, import/export across clients, ID/revision conflicts and invalid startup data. AI makes candidate data only; tests prove it cannot silently apply a theme or edit repository source. Exercise startup to avoid a flash or migration reset.

For shared-control migrations, test meaningful behavior changes at the existing component/feature boundary: keyboard activation/focus, ref/trigger composition, Settings disabled state, loading/double-submit prevention, selected/expanded state and accessible icon labels. Do not add tests that simply repeat class strings or duplicate every wrapper. Visual acceptance uses the production-component state preview in both appearances and a custom palette; check hover/pressed/focus/disabled and semantic colors, not just idle screenshots. Run the scoped override/literal guardrail on migrated paths.

Manual visual checks cover both appearances on desktop/iOS/Android, system appearance changes, native headers/sheets, light/dark code/diffs and ANSI terminal colors, every critical request/status card, large text/reduced motion/screen readers, offline selection/revert, and artifact interaction state through theme updates. Preview every candidate in context rather than only swatch circles.

Run scoped shared/mobile/web/server/desktop tests and types for touched packages. Desktop-facing implementation requires `pnpm build` followed by the existing `pnpm test:desktop-smoke`; do not build during smoke or recreate an e2e suite. No tests/build/smoke are claimed for this documentation-only plan.
