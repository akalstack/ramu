# Security

Security fixes target the latest release.

## Reporting a vulnerability

Use **Security → Report a vulnerability** on GitHub for a private report. If that is unavailable, open an issue asking for a private contact, without exploit details or secrets.

Include the version, OS, reproduction steps and impact. Remove credentials and private code from attachments.

## What Ramu can do

Agents run with your user permissions: they can read files, edit code and run commands. Providers receive the context you send them, including attached files and unsaved editor content. Closing the window leaves background agents and schedules running; stop them in Ramu when needed.

## Remote access

A device paired with **full access** can read workspace data, run agents and terminals, edit files and use the host's provider credentials. Pair only devices you trust.

A **viewer** can read conversations and answer approval and question requests. Approving a request can authorize the agent to act on it, so use viewers for trusted reviewers, not public sharing. The host enforces the viewer role with a method allowlist (`viewerMayInvoke`, `packages/shared/src/viewerAccess.ts`); new methods are denied to viewers by default. Disabled controls in the apps are a convenience, not the boundary.

- **Pairing:** `ramu pair` creates a full-access code and `ramu pair --role viewer` a viewer code. The role belongs to the single-use code; a device cannot ask for more. Failed attempts are rate limited per peer with exponential backoff.
- **Device permissions:** a full-access device also needs a permission for each of computer use, the browser, terminals, changing settings and agents (reading status and settings stays open). New devices get the host's defaults (all four unless changed in Settings → Remote access); a viewer gets none, and a device paired before permissions keeps all four until one is changed. The host grants, extends or removes each one per device: **This time** (until that device's last connection closes), **For 1 hour**, **For 1 day** or **Always**. A device can request a missing permission; only a person at the host can allow it (Settings → Remote access or `ramu devices allow`). **Never** removes it and declines that device's further requests for it until the host allows it again itself. The server refuses the call otherwise, whatever the client shows.
- **Pairing by request:** while the host is Discoverable (or a pairing offer is open), a nearby device can ask instead of typing a code. The device commits to an X25519 key before the host sends its own, then reveals it; both derive a six-digit number and the device token from the exchange, so the token never crosses the network and a relay cannot make the numbers agree except by a one-in-a-million chance per attempt that a person must also approve. A request appears at the host only after a valid reveal, and only a person at the host can allow it and choose its access: the desktop app asks in a dialog (or a system notification when it is in the background or closed), and a headless server prints the request for `ramu pair --approve <request>` or `--deny`. Requests are refused when the host is neither Discoverable nor has an offer open, limited to one per address and four in total, expire after two minutes, and failures count toward the same back-off. A declined address waits a minute before it can ask again. While an offer is open the host also advertises itself nearby, even when Discoverable is off.
- **Host pairings:** a person at host A can let its agents use host B. With a desktop pairing to B, A's row for B in Settings → Remote access requests **Agents**; once a person at B grants it, A pairs itself with a one-time code that lasts a minute and can only become a host pairing, and that pairing ends with the grant. Agents is off for existing devices and for new ones until a person turns on **New devices: Agents** on B. Without a desktop pairing, `ramu hosts add <address> <code>` uses a code from `ramu pair` on B. A pairs with B as a `host` device that B limits to four calls: start a thread, check or message threads that pairing started, and list project names, aliases and descriptions (no folder paths). Checking a thread returns its state and its latest reply, so A's agent sees what those threads report and nothing else. It holds no device permissions and receives no events, so it cannot read files, paths, Git, terminals, settings, the browser or any other thread. Every thread it starts gets at most B's **Most access for its threads** for that pairing (default Allow edits), B's own depth limit (two levels of agent-started threads) and an hourly limit of 8 threads and 20 messages; B checks all of these itself, whatever A sends. A asks the person before every start on another host and never sends uncommitted changes. A keeps the token in the OS credential store and renews it before it expires; **Forget** on A stops using it, and revoking the device on B ends it immediately. Hosts never sync settings or credentials.
- **Devices:** `ramu devices` lists them and `ramu devices revoke <id>` (or `all`) revokes, as does Settings → Remote access. Revocation is immediate and closes open event streams.
- **Credentials:** a device token expires after 90 days of inactivity (set `RAMU_DEVICE_TOKEN_DAYS` to a number of days or `never`). Paired clients renew the token about monthly with `POST /renew`; the host retires the old token two minutes after the new one is first used.
- **Browsers:** cross-origin browser access is off. `RAMU_BROWSER_ORIGINS` takes a comma-separated list of exact trusted HTTP(S) origins; origin checks supplement bearer authentication.
- **Network:** expose the server only on a trusted LAN or VPN, or behind authenticated HTTPS such as your own tunnel. Plain HTTP sends bearer tokens and workspace data unencrypted. A tunnel address must be `https://`. Ramu can run Cloudflare's quick tunnel, Tailscale Funnel or ngrok itself with the person's own tool and account; it only reads the address the tool prints. While a tunnel address is set, a request from loopback (where a tunnel on this computer delivers) is limited and paired by the visitor address in the tunnel's `CF-Connecting-IP` or last `X-Forwarded-For` header; that header is ignored from any other address. The tunnel's provider terminates HTTPS and can read the traffic. The mobile app does not pin TLS certificates, so use a trusted HTTPS certificate or your own authenticated VPN.
- **Webhook schedules:** a webhook schedule's address holds a random 24-byte token, and full-access devices are the only ones that can read it or its secret; viewers see neither. Requests are checked against the schedule's signature (HMAC-SHA256 over the exact body, or GitLab's token header) with a constant-time comparison, limited to 256 KB and 30 a minute per address, and logged with their outcome. What reaches the agent is the schedule's prompt plus the chosen fields, fenced as untrusted data with an instruction not to follow it; the run uses the schedule's own permission level. A GitHub webhook Ramu creates uses the repository's existing account, and a `gh` call receives the secret through a private temporary file, never its arguments.

See [Headless server](docs/guide/remote-hosts.md) for running a host.

Continue on another host is a person's action from an owner device: the device calls both hosts directly, viewer devices are refused, and paired hosts cannot reach the package, clone or start methods. The redacted conversation leaves the host, and can quote code and uncommitted content; files do not.

Any process running as your OS user can reach the host's local socket with owner access, and Ramu cannot tell which tool called it. `ramu thread` commands are therefore trusted like you: they are labelled with the name given by `--as` and default to **Allow edits**, but are not a security boundary.

### Host pairing

A host paired with another as `host` may call only `hostThreads.start`, `status`, `message` and `projects`, over calls-only sockets; retries and operation keys pass the same check. A person at the asking host approves each start; nobody at this host approves individual starts, and these choices follow from that:

- **Access ceiling.** Threads a pairing starts default to **Allow edits**. Raising the ceiling shows a warning, because the other host's agent writes the prompt and, if compromised, could run commands here at Auto or Full access.
- **What comes back.** `hostThreads.status` returns the latest reply of threads that pairing started, so those threads can pass file contents back. Their reports reach the asking agent labelled as not coming from the person.
- **Limits.** 2 levels of depth, 8 threads and 20 messages per hour per pairing. The message count is kept in memory and resets when this host restarts.
- **Labels.** A thread shows this host's own name for the pairing; the other host's name for itself and its thread title are context only.
- **Revocation.** Revoking a pairing stops new calls at once. Threads it already started keep running, visible with their origin label, until stopped here.
- **Transport and tokens.** The token is in the OS credential store on the asking host and hashed here. Plain HTTP needs `--private-network`. On a headless host without an unlocked credential store, `ramu hosts add` fails with a message to unlock it, and nothing is stored in plain text.
- **Agents permission.** A device granted **Agents** may pair its own computer here without a code from a person. That code is one-time, lasts a minute, only becomes a host pairing, and the pairing ends with the grant.

Test devices give agents fixed operations on simulators and emulators, not a shell: every command is a fixed program with checked arguments, app files must resolve inside the thread's workspace, logs are filtered to the launched app with known secrets removed, and a device belongs to one thread at a time.

## Isolated content

- **Theme preview:** the Code/Diff preview in the theme editor runs bundled Monaco code on its own `ramu-theme:` origin. It serves only the preview entry and bundled assets, cannot read workspace files, call the native bridge or reach the parent window, and accepts only validated palette and view messages.
- **Interactive content and pages:** agent-generated documents run in a separate `ramu-content:` origin with a restrictive content policy and cannot use the theme origin or any host API. See [Pages and interactive content](docs/guide/pages.md).
- **Page capabilities:** a page reaches records, AI, photos, notifications, a project folder or a thread only through messages its viewer forwards to the host, which checks that the page declared the capability, that the person allowed it, and its limits (records 10,000 and 20 MB per page, a daily model and notification budget, bounded run steps, writes and time). The page never receives credentials or another page's data. Page runs use only the page's own tools; records, fetched pages and tool results are passed to the model as data, deleting records needs the person's **Allow** in Ramu's own toolbar (not page code), and every run's record changes can be undone together. A project folder grant is read-only and confined to that folder after resolving links. Ramu data a page may read is read-only and limited to token activity totals, thread titles and states, and pull request summaries, each source allowed separately; never transcripts, files, credentials or settings. Photos are stored without JPEG location metadata.
- **Page share links and webhooks:** a share link is an unguessable token for devices already paired with the host; viewer-role devices may open it and, when the link allows, add records, nothing else. Links expire after 30 days unless renewed and can be revoked. A page webhook is an unguessable address accepting records for one declared collection, checked against its fields and limited to 30 requests a minute. - **Pages open to anyone:** a page opened to people without Ramu runs on its own loopback listener on a random port, reached through its own tunnel process, so it has a hostname that shares no origin, port or cookie with Ramu's API. The listener answers only `GET /` (and `HEAD`) with that page's exported bytes under the page's content policy plus `sandbox allow-scripts`, `nosniff`, `no-referrer`, `X-Frame-Options: DENY` and `no-store`; every other path is 404 and every other method 405. Only a page that declares no capability can be opened, and one whose newer version declares any answers 410. Tailscale Funnel and a fixed ngrok domain are refused, since they would serve the page under the host's own name. Closing it stops the tunnel and the listener.
- **Publishing pages:** a page with records or AI cannot be published. A static deploy sends only the page's exported HTML to the platform the person chose, with their own token (GitHub through the saved Git hosting login; Netlify, Vercel and Cloudflare tokens in the OS credential store, never in settings or the page). Hosting tokens are saved only from the host itself. Platform error bodies are not shown, since they can echo request details.
- **Page runs beyond the page:** web search sends only the query, to DuckDuckGo, through the same vetted DNS as page fetches. Shared MCP servers are offered to a page run only when the person allowed that server for that page, through a gateway bound to the page's model login and project, and every call is confirmed in Ramu's own toolbar. Runs nobody started from a device load the page on the host offline, in the sandboxed preview browser, where it can only read its own records.
