# Security

Security fixes target the latest release.

## Reporting a vulnerability

Use **Security → Report a vulnerability** on GitHub for a private report. If that is unavailable, open an issue asking for a private contact, without exploit details or secrets.

Include the version, OS, reproduction steps and impact. Remove credentials and private code from attachments.

## What Ramu can do

Agents run with your user permissions: they can read files, edit code and run commands. Providers receive the context you send them, including attached files and unsaved editor content. Closing the window leaves background agents and schedules running; stop them in Ramu when needed.

An [ability call](docs/guide/agents.md#abilities) sends another of your signed-in providers only the calling agent's prompt and the inputs it names: images or files inside the thread's folder, or attachments the thread already holds. It never sends the conversation, other files, memory or credentials. The run has no shell, file, Git or MCP tools; Codex runs read-only in an empty folder with every MCP server its login configures switched off, and Claude runs with no settings files or MCP servers. The thread's row shows what was sent, **Ask before using another provider** turns each call into an approval, and **Off** in Settings → Models → Abilities refuses one. Ramu's own web search sends only the query, to DuckDuckGo. An image or search ability mapped to a Shared MCP tool sends that tool only the prompt or query, through the thread's own Shared MCP access: the tool must be approved for the thread's provider login and project, and its approval rules apply as when the agent calls it. A video, speech, music or sound ability on a media account (Google Gemini, ElevenLabs or OpenAI) sends that service only the prompt or the words to say, with the person's API key: the key is checked against the service before it is kept, lives in the host's OS credential store, is added and removed only on the host, and goes only to that service's API (`x-goog-api-key`, `xi-api-key` or `Authorization`); a video Gemini returns as an address is downloaded only from Gemini's own API host. The file it returns is kept as an attachment of the thread.

## Ramu account

The account at `account.akalstack.com` is optional and is never access: signing in does not pair a device or grant anything on a host, and a pairing request it carries still ends with the person approving it on the host, with the same six-digit check as a nearby request.

- **What the service stores:** name, email and avatar from GitHub or Google, linked sign-ins and passkeys, sessions per device, sealed backups (ciphertext, size and time), the backup key sealed under the recovery code, key requests and relayed pairing messages for at most ten minutes, and each listed host's name, id and last-seen time. Identity providers' access tokens are not kept after sign-in. **Delete account** removes every row for the person at once.
- **Backups are sealed on the device** with XChaCha20-Poly1305 under a random 256-bit backup key kept in the host's credential store (the phone's secure store on a phone), with the slot bound as associated data; a slot's name is sealed the same way. The service never receives the key. A backup carries the portable settings export only; credentials never leave the host, sealed or not.
- **Getting the key to a new device:** the new device commits to an X25519 key, the approving device sends its own, the new device reveals its key, and both derive the six-digit number and a sealing key from the exchange; the backup key is sent sealed under it only after the person approves. The service relays envelopes it cannot open and deletes them on delivery or after ten minutes. The recovery code is 160 random bits; the copy of the key sealed under it is useless without the code.
- **Your hosts:** a listed host's addresses never reach the service. A relayed pairing runs the nearby exchange through the service; the host seals its addresses to that exchange in its approval, and the device checks the host's identity on each address. Only devices signed in to the same account reach a listed host; five requests wait per host at most and one device sends one a minute.
- **What a compromised service could do:** withhold or delete backups, see sign-in metadata, backup sizes and times and listed hosts' names, and delay or drop requests. It could not read settings, learn a host's address, open a backup without a device's key or the recovery code, or pair a device without the person's approval on the host.

## Remote access

A device paired with **full access** can read workspace data, run agents and terminals, edit files and use the host's provider credentials. Pair only devices you trust.

A **viewer** can read conversations and answer approval and question requests. Approving a request can authorize the agent to act on it, so use viewers for trusted reviewers, not public sharing. The host enforces the viewer role with a method allowlist (`viewerMayInvoke`, `packages/shared/src/viewerAccess.ts`); new methods are denied to viewers by default. Disabled controls in the apps are a convenience, not the boundary.

- **Pairing:** `ramu pair` creates a full-access code and `ramu pair --role viewer` a viewer code. The role belongs to the single-use code; a device cannot ask for more. Failed attempts are rate limited per peer with exponential backoff.
- **Device permissions:** a full-access device also needs a permission for each of computer use, the browser, terminals, changing settings and agents (reading status and settings stays open). New devices get the host's defaults (all four unless changed in Settings → Remote access); a viewer gets none, and a device paired before permissions keeps all four until one is changed. The host grants, extends or removes each one per device: **This time** (until that device's last connection closes), **For 1 hour**, **For 1 day** or **Always**. A device can request a missing permission; only a person at the host can allow it (Settings → Remote access or `ramu devices allow`). **Never** removes it and declines that device's further requests for it until the host allows it again itself. The server refuses the call otherwise, whatever the client shows.
- **Pairing by request:** while the host is Discoverable (or a pairing offer is open), a nearby device can ask instead of typing a code. The device commits to an X25519 key before the host sends its own, then reveals it; both derive a six-digit number and the device token from the exchange, so the token never crosses the network and a relay cannot make the numbers agree except by a one-in-a-million chance per attempt that a person must also approve. A request appears at the host only after a valid reveal, and only a person at the host can allow it and choose its access: the desktop app asks in a dialog (or a system notification when it is in the background or closed), and a headless server prints the request for `ramu pair --approve <request>` or `--deny`. Requests are refused when the host is neither Discoverable nor has an offer open, limited to one per address and four in total, expire after two minutes, and failures count toward the same back-off. A declined address waits a minute before it can ask again. While an offer is open the host also advertises itself nearby, even when Discoverable is off.
- **Host pairings:** a person at host A can let its agents use host B. With a desktop pairing to B, A's row for B in Settings → Remote access requests **Agents**; once a person at B grants it, A pairs itself with a one-time code that lasts a minute and can only become a host pairing, and that pairing ends with the grant. Agents is off for existing devices and for new ones until a person turns on **New devices: Agents** on B. Without a desktop pairing, `ramu hosts add <address> <code>` uses a code from `ramu pair` on B. A pairs with B as a `host` device that B limits to four calls: start a thread, check or message threads that pairing started, and list project names, aliases and descriptions (no folder paths). Checking a thread returns its state and its latest reply, so A's agent sees what those threads report and nothing else. It holds no device permissions and receives no events, so it cannot read files, paths, Git, terminals, settings, the browser or any other thread. Every thread it starts gets at most B's **Most access for its threads** for that pairing (default Allow edits), B's own depth limit (two levels of agent-started threads) and an hourly limit of 8 threads and 20 messages; B checks all of these itself, whatever A sends. A asks the person before every start on another host and never sends uncommitted changes. A keeps the token in the OS credential store and renews it before it expires; **Forget** on A stops using it, and revoking the device on B ends it immediately. Hosts never sync settings or credentials.
- **Devices:** `ramu devices` lists them and `ramu devices revoke <id>` (or `all`) revokes, as does Settings → Remote access. Revocation is immediate and closes open event streams.
- **Credentials:** a device token expires after 90 days of inactivity (set `RAMU_DEVICE_TOKEN_DAYS` to a number of days or `never`). Paired clients renew the token about monthly with `POST /renew`; the host retires the old token two minutes after the new one is first used.
- **Browsers:** cross-origin browser access is off. `RAMU_BROWSER_ORIGINS` takes a comma-separated list of exact trusted HTTP(S) origins; origin checks supplement bearer authentication.
- **Network:** expose the server only on a trusted LAN or VPN, or behind authenticated HTTPS such as your own tunnel. Plain HTTP sends bearer tokens and workspace data unencrypted. A tunnel address must be `https://`. Ramu can run Cloudflare's quick tunnel, Tailscale Funnel or ngrok itself with the person's own tool and account; it only reads the address the tool prints. While a tunnel address is set, a request from loopback (where a tunnel on this computer delivers) is limited and paired by the visitor address in the tunnel's `CF-Connecting-IP` or last `X-Forwarded-For` header; that header is ignored from any other address. The tunnel's provider terminates HTTPS and can read the traffic. The mobile app does not pin TLS certificates, so use a trusted HTTPS certificate or your own authenticated VPN.
- **Webhook schedules:** a webhook schedule's address holds a random 24-byte token, and full-access devices are the only ones that can read it or its secret; viewers see neither. Requests are checked against the schedule's signature (HMAC-SHA256 over the exact body, Vercel's HMAC-SHA1, Netlify's HS256 token whose claim is the body's SHA-256, or GitLab's token header) with a constant-time comparison, limited to 256 KB and 30 a minute per address, and logged with their outcome. What reaches the agent is the schedule's prompt plus the chosen fields, fenced as untrusted data with an instruction not to follow it; the run uses the schedule's own permission level. A GitHub webhook Ramu creates uses the repository's existing account, and a `gh` call receives the secret through a private temporary file, never its arguments.

See [Headless server](docs/guide/remote-hosts.md) for running a host.

Continue on another host is a person's action from an owner device: the device calls both hosts directly, viewer devices are refused, and paired hosts cannot reach the package, clone or start methods. The redacted conversation leaves the host, and can quote code and uncommitted content; files do not.

Any process running as your OS user can reach the host's local socket with owner access, and Ramu cannot tell which tool called it. `ramu thread` commands are therefore trusted like you: they are labelled with the name given by `--as` and default to **Allow edits**, but are not a security boundary.

### Host pairing

A host paired with another as `host` may call only `hostThreads.start`, `status`, `message` and `projects`, over calls-only sockets; retries and operation keys pass the same check. A person at the asking host approves each start; nobody at this host approves individual starts, and these choices follow from that:

- **Access ceiling.** Threads a pairing starts default to **Allow edits**. Raising the ceiling shows a warning, because the other host's agent writes the prompt and, if compromised, could run commands here at Auto or Full access.
- **What comes back.** `hostThreads.status` returns the latest reply of threads that pairing started, so those threads can pass file contents back. Their reports reach the asking agent labelled as not coming from the person.
- **Limits.** 2 levels of depth, 8 threads and 20 messages per hour per pairing. The message count is kept in memory and resets when this host restarts.
- **Labels.** A thread shows this host's own name for the pairing; the other host's name for itself and its thread title are context only.
- **Revocation.** Revoking a pairing stops new calls at once. Threads it already started keep running, visible with their origin label, until stopped here.
- **Transport and tokens.** The token is in the OS credential store on the asking host and hashed here. Plain HTTP needs `--private-network`. On a headless host without an unlocked credential store, `ramu hosts add` fails with a message to unlock it, and nothing is stored in plain text.
- **Agents permission.** A device granted **Agents** may pair its own computer here without a code from a person. That code is one-time, lasts a minute, only becomes a host pairing, and the pairing ends with the grant.

Test devices give agents fixed operations on simulators and emulators, not a shell: every command is a fixed program with checked arguments, app files must resolve inside the thread's workspace, logs are filtered to the launched app with known secrets removed, and a device belongs to one thread at a time.

## Deploys

- **Hosting accounts:** Vercel, Netlify, Neon and Expo tokens live in the host's OS credential store; settings keep only a reference and the account name. They are added, replaced and removed only on the host itself, are checked against the platform's account endpoint before they are kept, and are sent only to that platform's API in the `Authorization` header Platform error bodies are read to classify a failure and never shown.
- **CLI sign-in:** Ramu runs `vercel login` or `netlify login --request` as an argument list, with an environment limited to what the CLI needs and a private configuration folder that is deleted afterwards, so the person's own CLI login is never read or changed. `neon profile create ramu --mint` runs the same way in a private configuration folder and leaves only a minted API key, with no session. `eas login --device --non-interactive` runs the same way too; the Expo session it saves is exchanged through Expo's API for an access token named Ramu and then ended, so only the revocable token is kept. Vercel sign-ins are sessions Ramu renews with their refresh tokens through Vercel's OAuth endpoint for its CLI. Agents never drive a browser to create tokens.
- **Cloudflare DNS records:** a token pasted to create a domain's records at Cloudflare is used for that one request and not saved.
- **Linking:** linking Netlify adds a read-only deploy key and a build webhook to the GitHub repository through the repository's existing GitHub account; the GitHub token itself is never sent to the platform.
- **Domains:** domain names are checked as host names before any call. DNS records are created only in the platform's own DNS through the connected hosting account, never at another provider. A watched domain is checked from the host with public DNS lookups and, once the platform or DNS shows it pointing at the platform, one HTTPS `HEAD` request that reads no body and follows no redirect.
- **Databases:** the Neon API key is kept like a hosting token (host only, checked before it is kept, sent only to Neon's API). Connection values of a provisioned database are kept in the OS credential store and reach only this host's Environment variables and, through **Sync**, the places it writes; production's values go only to the platform's production variables and to a migration. Clients see variable names only. A migration runs as an argument list with production's values and only the process's path, home, user and locale variables, never Ramu's own secrets. Creating or deleting a database is not an agent tool; deleting is done on the provider's page.
- **Uptime checks:** the host sends one `GET` every five minutes to the production address the platform reports, on the health path from `ramu.json`, which can only name a path on that same origin. It sends no credentials or cookies, reads no body, stops after 10 seconds and follows redirects only on the same host name. The incident thread gets the build log as external text, and its agent can roll back only through the approval card.
- **Deploy watch:** a finished deployment wakes a thread with the platform's build log fenced as external text, after anything shaped like a credential (known token formats, `NAME=value` secrets, private keys, long random strings) is replaced by `[redacted]`. It follows only deploys, pushes and merges made from Ramu to the repository the project is linked to.
- **Store releases:** the Expo access token is kept like a hosting token (host only, checked against Expo's API before it is kept, sent only to Expo's API in the `Authorization` header). Build and upload logs are read from the signed storage links Expo returns, without the token, and only for builds of the project's own app. Release runs `eas build` as an argument list in the project's checkout, with the token as `EXPO_TOKEN` and an environment limited to the path, home, user, locale and shell variables, never Ramu's own secrets. It uses the `production` profiles, is refused while the submit profile names a Play track other than internal, and never submits an app for review; that and promoting a release stay the person's actions on each store. Its output is redacted before it is shown.
- **Usage:** usage is read with the same hosting and database accounts and only shown; there is no call in Ramu that changes a plan, a limit or a payment method, and `deploy_usage` is read-only. Vercel's billing charges are read for the linked account or team and summed per service on the host.
- **Apps published from this computer:** **Run on this computer** runs the app in a Docker container with no host network, `no-new-privileges`, none of Ramu's environment, and only its port published to `127.0.0.1` on a random port. Its tunnel is a separate process pointed at exactly that port, of the kind pages opened to anyone use, so the app gets a hostname of its own that shares no origin with Ramu's address; Tailscale Funnel and a fixed ngrok domain are refused. Ramu refuses to publish without Docker, since a process running as the person's user could reach Ramu's local socket. Stopping removes the tunnel before the container. Of the host's saved variables, the container gets only those the app's code reads, passed by name to `docker run` with their values in that one process's environment, never on a command line. Without Docker, only when the person chooses **Run without Docker** after the sheet says it has their permissions, a Node app's own scripts run as a program in its own process group with the project's variables and none of Ramu's environment, listening on loopback; it can read what the person can, so it is meant for code they trust. A lasting address uses a named Cloudflare Tunnel whose ingress names only the app's hostname and one loopback port, ending in a catch-all 404; Ramu's own port and wildcard hostnames are refused, the person's Cloudflare token and the tunnel's token stay in the OS credential store, and the tunnel token reaches `cloudflared` through its environment, not its command line.
- **Secrets sync:** **Sync** in the deploy sheet reads values from this host's Environment variables in the OS credential store and sends each only to the API of the place it is written: GitHub Actions secrets (sealed with the repository's public key before they leave the host, through the repository's existing GitHub account; `gh` receives the body through a private temporary file), and the linked platform's variables (Vercel encrypted variables, Netlify site variables). Only missing names are written. The status lists names only, for every client; values are never returned or logged.
- **Identities and moving settings:** an identity holds only references to accounts already connected on its host, so no credential is copied or moved; identities, their pins and account assignments are host settings that a paired device edits only with its settings changes permission. **Copy settings**, **Export settings** and **Import settings** carry only the portable groups (preferences, model sets, rules for every project or an identity, identities' Git author and rules, and everywhere notes when chosen), never executable paths, credentials, account tokens, workspace state or device permissions; an identity's accounts travel as their kind and sign-in email and are matched on the receiving host, never as ids. The guardrail's **Continue as ‹other›** allows one action for ten minutes on the host itself.
- **Plugins:** a plugin is installed only after the person's review of everything it adds, at a pinned commit; a source from an index that names a signing key installs only a commit `git verify-commit` accepts against that key alone, and the default index's commits must carry Akalstack's key, which ships in Ramu. Clones are shallow, never run hooks or submodules, and accept only https, ssh or local paths (no `ext::` transports). A plugin's code runs only as an MCP server (with Shared MCP's approvals) or as its CLI through `platform_cli`; hooks and other parts Claude Code or Codex run are listed and never run, and skill scripts are copied only with their own approval and never run by Ramu. Credentials are pasted or signed in only on the host, kept in its OS credential store, and reach only that plugin's MCP servers (as environment or headers), CLI (in its token variable, never as an argument) and data sources; every occurrence in CLI output is replaced before the agent reads it. `platform_cli` refuses sign-in commands and token arguments, runs with an environment limited to the path, user, locale and shell variables and a home folder of Ramu's own, and runs only the plugin's declared read-only prefixes without asking; every other command asks the person with a card, in every access mode. A data source calls one https origin fixed in the manifest or taken from the credential's address field, with the fields the manifest declares (others are refused), bounded in time and size; a POST must be declared read-only and is reviewed when the plugin is listed. An update that changes an MCP command, a credential, a read-only prefix or a script asks for approval again; an agent's `plugin_install` shows the same review as a card the agent cannot answer.
- **Approval-only actions:** `deploy_production`, `deploy_rollback`, `deploy_domain_add`, `deploy_domain_records`, `release_start` and every `platform_cli` command that is not read-only ask the person with a card naming the address, domain or DNS records and what changes, in every access mode; in the deploy sheet, pressing **Deploy to production**, **Roll back**, **Create records** or **Release** and confirming, or typing a domain and pressing **Add domain**, is that approval. A preview deploy asks outside Full access. Every action checks that the project's binding was made with the account connected now, and runs one at a time per project; a deploy whose reply is lost reads the deployment list instead of deploying again.

## CI

- **Set up CI** commits one generated workflow file on a new branch from a temporary worktree, with the repository's Git hooks switched off, and opens a pull request; nothing reaches the default branch until the person merges it. Generated workflows pin actions to a major version and grant the job read access to the repository only.
- **Branch protection:** requiring CI before merge is a person's choice in Set up CI, made with the repository's existing GitHub account; agents have no tool for it. Existing rules are only added to, never replaced.
- **Push watches:** a failing check on a pushed default branch is handed to the thread as external feedback, with its log tail redacted and an instruction not to follow commands in it.

## Isolated content

- **Theme preview:** the Code/Diff preview in the theme editor runs bundled Monaco code on its own `ramu-theme:` origin. It serves only the preview entry and bundled assets, cannot read workspace files, call the native bridge or reach the parent window, and accepts only validated palette and view messages.
- **Interactive content and artifacts:** agent-generated documents run in a separate `ramu-content:` origin with a restrictive content policy and cannot use the theme origin or any host API. See [Artifacts](docs/guide/artifacts.md).
- **Artifact capabilities:** an artifact's page reaches records, AI, photos, notifications, a project folder or a thread only through messages its viewer forwards to the host, which checks that the page declared the capability, that the person allowed it, and its limits (records 10,000 and 20 MB per page, a daily model and notification budget, bounded run steps, writes and time). The page never receives credentials or another page's data. An image a page's AI asks for (`ai.image`) needs the AI grant, counts against its daily budget and sends only the prompt to a signed-in provider with image generation, never through a Shared MCP tool. Page runs use only the page's own tools; records, fetched pages and tool results are passed to the model as data, deleting records needs the person's **Allow** in Ramu's own toolbar (not page code), and every run's record changes can be undone together. A project folder grant is read-only and confined to that folder after resolving links. Ramu data a page may read is read-only and limited to token activity totals, thread titles and states, and pull request summaries, each source allowed separately; never transcripts, files, credentials or settings. A page's plugin data source queries run on the host with the plugin's saved credential, only for data sources the page declared and the person allowed one by one, through the same request a dashboard makes, never from a share link; the page receives rows, never the token. Photos are stored without JPEG location metadata. A motion's music, sound effects and recorded voices are audio files a media account or a mapped Shared MCP tool returned, kept with the version and mixed on the host. A motion's narration is spoken on the host by its own speech command (`say` on macOS, `espeak-ng` on Linux), run as an argument list with the words in a temporary file, and never sent anywhere.
- **Docs, decks, dashboards, designs and motions:** these are drawn on the host into HTML with no script, network or capability, and exported (PDF, PowerPoint, Word, images and video) by the host's own offline preview browser. A dashboard's live table reads only its own project: its deployments, usage, uptime, thread titles and states or pull request summaries, or one CSV or JSON file inside the project folder, resolved like a project folder grant (links followed, `.git` refused) and never written, or the records of an App artifact in the same project, read only. An ability mapped to a Shared MCP tool sends it only the prompt, and for a long read the named files' text or for an image edit the named images, through the thread's own Shared MCP access and approvals. A table from a Shared MCP server calls only a tool the server marks read-only, through the gateway bound to the dashboard's project, so only servers and tools approved for that project in Shared MCP are reachable; no confirmation is asked for these reads. A table from a **plugin's data source** (such as Grafana, Amplitude or Salesforce) reads only for a kept dashboard you allowed to read that source, one grant per dashboard and source, given on the dashboard (**Allow**) and taken back in its menu; a dashboard naming a source it was not allowed shows the table empty. The request is the one the plugin declares (see **Plugins** above), at most 5,000 rows of the columns the table names, each cell cut to 500 characters. A sign-in slot (Salesforce's) runs OAuth with PKCE through the person's own client: the browser on the host returns to a loopback-only listener on port 7417 that Ramu opens just for that sign-in, checks the `state` it sent, and exchanges the code with the verifier; the tokens are kept like a hosting token and renewed at the plugin's token endpoint. The host's agent activity totals (turns, cost and tokens per provider and day) can be read by any dashboard; never transcripts. A dashboard in no project reads only those totals and records of an App in no project. An artifact file filled from an attachment can only name an image attachment its own thread holds. **Present** may ask to know the displays (the browser's window management permission, granted only to Ramu's own window) and opens one blank presenter window that Ramu fills with text; that window cannot navigate or open others.
- **Artifact share links and webhooks:** a share link is an unguessable token for devices already paired with the host; viewer-role devices may open it and, when the link allows, add records or (for a link that names its editor, on a doc, diagram or deck) save the text as that person, merged like any edit, with each version naming them, and take part in live typing on that one artifact, nothing else. Links expire after 30 days unless renewed and can be revoked. An artifact webhook is an unguessable address accepting records for one declared collection, checked against its fields and limited to 30 requests a minute. - **Pages open to anyone:** a page opened to people without Ramu runs on its own loopback listener on a random port, reached through its own tunnel process, so it has a hostname that shares no origin, port or cookie with Ramu's API. The listener answers only `GET /` (and `HEAD`) with that page's exported bytes under the page's content policy plus `sandbox allow-scripts`, `nosniff`, `no-referrer`, `X-Frame-Options: DENY` and `no-store`; every other path is 404 and every other method 405. Only a page that declares no capability can be opened, and one whose newer version declares any answers 410. Tailscale Funnel and a fixed ngrok domain are refused, since they would serve the page under the host's own name. Closing it stops the tunnel and the listener.
- **Publishing artifacts:** a page with records or AI cannot be published. A static deploy sends only the page's exported HTML to the platform the person chose, with their own token (GitHub through the saved Git hosting login; Netlify and Vercel through the hosting accounts below; Cloudflare Pages through the Cloudflare plugin's token). Hosting tokens are pasted only on the host itself; a paired owner device may start Vercel's or Netlify's own sign-in, which runs on the host and keeps the token there. Platform error bodies are not shown, since they can echo request details.
- **Artifact runs beyond the artifact:** web search sends only the query, to DuckDuckGo, through the same vetted DNS as page fetches. Shared MCP servers are offered to a page run only when the person allowed that server for that page, through a gateway bound to the page's model login and project, and every call is confirmed in Ramu's own toolbar, except tools the server marks read-only (MCP's `readOnlyHint`) on a server the person separately allowed to read without asking for that page; the hint is the server's own claim, so the choice is per server and off by default. Runs nobody started from a device load the page on the host offline, in the sandboxed preview browser, where it can only read its own records.
